# 项目文档与讨论管理规则

> 项目：A股量化研究与信号决策平台
> 文档状态：已确认
> 生效日期：2026-07-29
> 当前基线：`ef0782b`
> 适用范围：全部需求、设计、开发、测试、部署、运行和验收活动

## 1. 目的

本规则用于保证项目在加速推进后仍然做到：

```text
结论有出处
实现有依据
验证有证据
变更可追溯
下一步明确
```

项目不再按“一次只讨论一个小问题”推进，而是按六个加速步骤交付。每个步骤可以同时形成多份设计、代码、测试和部署成果，但不能取消证据、门禁和验收。

## 2. 权威信息层级

发生冲突时按信息类型判断，不使用一套顺序覆盖所有事实。

### 2.1 业务目标和范围

优先级：

```text
路线图
→ 已确认需求与范围文档
→ 项目决策记录
→ 详细设计
→ 实现
```

已有代码不能反向改变已确认业务目标。

### 2.2 当前实现事实

优先级：

```text
运行环境实测
→ 数据库实测
→ 当前提交代码
→ 自动化测试
→ 实施文档
→ 历史说明
```

文档写“已实现”，必须有代码、数据库或运行证据。

### 2.3 当前推进状态

优先级：

```text
Git主分支提交
→ 路线图当前推进位置
→ 统一开发任务总表
→ 专题文档状态
```

## 3. 文档分类

| 类型 | 作用 | 必须包含 |
|---|---|---|
| 路线图 | 项目唯一推进主线 | 阶段、状态、索引、下一步 |
| 资源审计 | 记录真实资源和限制 | 命令、时间、结论、缺口 |
| 需求确认 | 固定业务边界 | 目标、范围、非目标、验收 |
| 决策记录 | 固定重大选择 | 候选、决定、依据、影响 |
| 设计文档 | 指导实现 | 对象、流程、接口、异常、验收 |
| 实施文档 | 记录落地 | 文件、迁移、配置、操作 |
| 测试文档 | 记录验证 | 场景、输入、预期、实际、证据 |
| 部署运维 | 记录长期运行 | 部署、升级、回滚、监控、恢复 |
| 验收文档 | 形成阶段结论 | 验收项、证据、遗留问题、结论 |

规范目录：

```text

├─ 00_项目管理/
├─ 01_项目立项与需求分析/
├─ 02_可行性研究与资源评估/
├─ 03_总体设计/
├─ 04_详细设计/
├─ 05_开发实施/
├─ 06_测试验证/
├─ 07_部署上线/
├─ 08_运行维护/
├─ 09_优化升级/
├─ 11_AI协同/
├─ 12_多用户开放与实时桥接/
├─ 13_自动执行与高级智能/
├─ 14_综合验收与运行/
└─ 99_历史归档/
```

后续新增目录必须由路线图或决策记录批准。

## 5. 文件命名

统一格式：

```text
NN_主题.md
```

要求：

- 同一目录内编号唯一；
- 名称直接表达业务内容；
- 不使用“最终版2”“最新修改版”等名称；
- 历史文档移入 `99_历史归档`，不靠文件名区分；
- 证据文件可以使用日期和用途，但必须由专题文档索引。

## 6. 文档头信息

正式专题文档至少包含：

```text
路线图阶段
文档状态
形成日期
适用基线
适用范围
配套文档
```

涉及当前实现时增加：

```text
证据来源
已实现范围
未实现范围
待核实项
```

## 7. 事实分类

文档中的事实必须属于以下一种：

```text
已实测
代码已证明
数据库已证明
已确认设计
计划实施
待核实
不在当前范围
```

禁止使用模糊表述：

```text
应该已经
大概支持
理论上可以
可能没有问题
```

## 8. 加速步骤工作方式

每个加速步骤一次完成：

```text
调查
→ 完整设计
→ 开发任务
→ 代码实现
→ 自动测试
→ 真实环境验证
→ 文档
→ 路线图更新
→ 阶段验收
```

同一步内允许并行：

- 数据库；
- 后端；
-任务执行器；
- API；
- 前端；
- 测试；
- 部署；
- 文档。

不允许绕过的门禁：

1. 当前事实与目标设计必须分开；
2. 数据库结构变更必须有迁移；
3. 正式状态必须可追溯；
4. 数据相关功能必须进行真实数据库验证；
5. 部署必须可回滚；
6. 阶段结束必须形成验收证据。

## 9. ChatGPT、OpenCode和用户职责

### 9.1 ChatGPT

负责：

- 读取仓库和一手证据；
- 业务与架构分析；
- 形成完整设计和验收包；
- 审查OpenCode结果；
- 更新路线图和项目文档；
- 给出一次可复制的操作命令。

不直接替代OpenCode长期开发业务代码，除非用户明确要求。

### 9.2 OpenCode

负责：

- 读取设计包；
- 修改代码和数据库迁移；
- 编写测试；
- 执行本地开发验证；
- 输出实现和测试证据；
- 不自行改变已确认业务范围。

OpenCode由用户手工启动，不设计自动启动OpenCode的流程。

### 9.3 用户

负责：

- 下载并应用交付包；
- 本地执行命令；
- 启动OpenCode；
- 提交和推送Git；
- 执行需要人工授权的服务器操作；
- 提供真实运行输出。

## 10. 交付包规则

文档交付优先使用完整文件覆盖包，不使用脆弱的文本补丁。

每个包至少包含：

```text
README.md
MANIFEST.json
payload/
```

MANIFEST记录：

- 文件路径；
- 文件大小；
- SHA256。

包命令必须：

- 检查当前提交；
- 检查工作区；
- 校验ZIP哈希；
- 覆盖指定文件；
- 执行 `git diff --check`；
- 只暂存目标文件；
- 提交；
- 推送；
- 输出最终提交。

## 11. 代码和数据库规则

- 所有代码修改进入Git；
- 所有Schema修改进入Alembic；
- 不在服务器容器内直接改代码；
- 不以人工临时SQL替代正式迁移；
- 不把测试数据写入稳定环境；
- 不提交Token、密码和私钥；
- 不使用旧quantStock作为在线依赖；
- 不使用日志替代正式状态、血缘或审计；
- 不覆盖正式历史版本和已完成Run。

## 12. 验证证据

可接受的验证证据：

- 自动测试输出；
- 数据库查询结果；
- API请求与响应；
- Docker服务状态；
- 迁移版本；
- 文件Checksum；
- 备份和恢复记录；
- 性能基准；
- 页面截图；
- 故障注入与恢复记录。

仅有“代码已写完”不能标记为完成。

## 13. 状态规则

统一状态：

```text
待讨论
讨论中
已确认
实施中
待验证
已完成
阻塞
暂缓
```

加速步骤可以直接从“已确认”进入“实施中”，不需要为每个小任务再次开会。

“已完成”必须同时满足：

- 范围已确认；
- 实现已进入主分支；
- 自动测试通过；
- 真实环境验证通过；
- 遗留问题已记录；
- 路线图已更新。

## 14. 变更规则

已确认结论发生变化时：

1. 在《项目变更记录》增加记录；
2. 在《项目决策记录》新增或替代决策；
3. 更新受影响专题文档；
4. 更新路线图；
5. 明确是否需要数据迁移、重算或回归测试。

不能直接覆盖原结论而不留下变化原因。

## 15. 每次新会话起点

每次继续项目时先读取：

```text
00_A股量化分析平台建设路线图.md
05_六步加速执行计划.md
07_统一开发任务总表.md
当前步骤对应设计与验收文档
```

然后核对：

```text
本地HEAD
远程main
工作区
服务器实际版本
```

## 16. 本规则结论

后续采用：

```text
一次完成一个加速步骤
+
步骤内并行
+
证据门禁不减少
+
完整文件交付
+
Git主分支作为交接点
```

速度通过减少重复讨论和重复交付提高，不通过省略设计、测试和验收提高。
