# 开发补丁与真实验证规则

> 日期：2026-07-28
> 状态：已生效
> 适用范围：quantStock1 后续全部开发、修复、部署和真实验证

## 1. 目的

本规则用于减少重复修改、无效部署和服务器试错。

项目仍以开发为主。测试、服务器运行和文档记录都是开发闭环的一部分，不得把开发阶段验证表述为项目验收。

## 2. 已发生问题及固定改进

### 2.1 补丁交付与 Windows 路径

已发生：

- ZIP 实际位于仓库目录，但命令只从 Downloads 查找；
- PowerShell 5.1 对中文路径输出发生乱码；
- ZIP 自身被识别为工作区未提交文件；
- 补丁中途失败后留下半修改工作区。

以后固定执行：

- ZIP 内部脚本和目录只使用 ASCII 名称；
- 不解析本地化后的 `git status` 中文路径；
- 补丁只检查目标提交和已跟踪文件差异；
- 所有替换先在临时目录完成并校验，再一次覆盖仓库；
- 补丁失败必须保持仓库原状态；
- ZIP 使用 SHA256 校验。

### 2.2 代码检查不完整

已发生：

- Markdown 行尾空格在暂存后才发现；
- 质量规则版本升级后仍有旧测试断言；
- Python 测试文件格式问题在提交后才发现。

以后提交前必须通过：

1. `git diff --check`；
2. Python 语法检查；
3. Ruff 检查；
4. 本次修改相关的全部测试；
5. 全仓库搜索旧版本号和旧状态口径；
6. 暂存内容再次执行 `git diff --cached --check`。

### 2.3 容器只读目录

已发生：

- 测试目录以只读方式挂载；
- `compileall` 尝试创建 `__pycache__`，导致验证失败。

以后固定执行：

- 只读目录使用 `python -B`；
- 语法检查使用 `ast.parse`；
- 不在只读挂载目录生成缓存或临时文件。

### 2.4 数据库 SQL 契约

已发生：

- `(:trade_date IS NULL OR ...)` 同时承担“全量”和“按日”查询；
- 参数为 NULL 时 PostgreSQL 无法推断参数类型；
- 单元测试只覆盖计算逻辑，没有覆盖真实 SQL 分支。

以后固定执行：

- 有条件和无条件查询分别构造 SQL；
- 禁止依赖无类型 NULL 参数推断；
- 日期参数使用明确日期类型；
- 每个数据库查询至少覆盖“有参数”和“无参数”分支；
- 部署构建前先使用服务器现有数据库执行 SQL 契约预检；
- SQL 契约预检失败时不构建镜像、不重启服务。

### 2.5 验证范围和状态口径

已发生：

- 北交所目标范围是 18 只，但查询曾可能统计全部北交所样本；
- 有 WARN 的质量运行实际状态是 `WARNED`，文档曾写成 `PASSED`；
- 开发阶段真实验证曾被表述为项目验收。

以后固定执行：

- 验证查询必须明确锁定目标对象清单；
- 预期数量必须由目标清单得出；
- 运行状态以数据库真实状态机为准；
- 开发阶段统一使用“真实验证”；
- 只有路线图最终综合验收阶段使用“项目验收”。

### 2.6 长时间命令无状态输出

已发生：

- 构建或基准运行期间终端长时间无输出；
- 无法判断正在运行还是卡住。

以后服务器脚本必须：

- 每个主要步骤开始前输出 `START|step=<name>`；
- 成功后输出 `DONE|step=<name>`；
- 失败输出 `FAILED|step=<name>|rc=<code>`；
- 大日志写入 `/tmp/*.log`；
- 终端只输出阶段状态、数量和短错误摘要。

## 3. 后续统一开发流程

### 第一步：证据和范围

- 读取 GitHub 当前 main；
- 明确目标提交、修改文件、版本和数据库迁移；
- 先确认真实根因，不根据报错表面猜测。

### 第二步：原子补丁

- 在临时目录生成全部修改；
- 完成替换数量、编码、行尾和文件存在性检查；
- 校验全部通过后再写入仓库；
- 失败不允许留下半修改文件。

### 第三步：本地门禁

- 语法；
- Ruff；
- 相关单元测试；
- 版本一致性；
- 文档和路线图一致性；
- `git diff --check`。

### 第四步：服务器构建前预检

使用服务器已有容器和真实数据库，但挂载新代码执行：

- 模块导入；
- 有参数和无参数 SQL；
- 本次相关测试；
- 数据库迁移兼容性。

预检通过后才允许构建镜像。

### 第五步：部署和真实验证

- `git bundle + scp` 同步；
- 构建并启动服务；
- 运行最小真实样本；
- 再运行扩大样本；
- 输出目标范围、成功数量、失败数量和短错误；
- 详细日志保存在 `/tmp`。

### 第六步：文档收口

- 记录真实结果；
- 更新路线图状态和下一项；
- 记录尚未解决的问题；
- 不把临时测量结果写成最终结论。

## 4. 当前故障形成的永久规则

本次 P4-3 容量基准故障形成以下永久规则：

```text
禁止使用无类型 NULL 参数同时控制 SQL 是否过滤。
全量查询与按条件查询必须分别构造。
数据库代码必须在镜像构建前通过真实数据库契约预检。
```
