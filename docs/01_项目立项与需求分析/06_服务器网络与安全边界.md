# 服务器网络与安全边界

> 路线图阶段：P1.3
> 状态：已确认现状；整改方案待总体设计
> 形成日期：2026-07-29
> 依赖文档：`05_svr3服务器资源审计.md`
> 文档作用：把服务器审计中的网络、端口、访问、密钥和生产安全边界单独固化

## 1. 当前网络拓扑

当前已确认的运行关系：

```text
Tushare
    ↑ HTTPS出站
svr3
    ├─ API：127.0.0.1:18000
    ├─ PostgreSQL：0.0.0.0:5432、[::]:5432
    ├─ Worker：无宿主机公开端口
    └─ Scheduler：无宿主机公开端口
```

当前API只绑定本机回环地址。

当前PostgreSQL监听全部IPv4和IPv6网卡。监听全部网卡不等于已经从互联网可达，但说明数据库监听范围大于当前已证明的业务需要。

外部是否能够连接数据库，还取决于：

- 服务器所在网络；
- 上级路由和安全设备；
- 主机防火墙；
- `pg_hba.conf`；
- 数据库用户和密码；
- TLS；
- 来源IP限制。

上述外围控制当前没有形成完整证据。

## 2. 当前访问边界

P1.1已经确认：

```text
单用户
受信任网络内使用
V1不开放公网
V1不提供外部API
V1不接入真实交易
```

因此当前最小访问原则是：

- API继续只允许本机或受控反向代理访问；
- 数据库不应向不明确的网络范围提供访问；
- Worker和Scheduler不发布管理端口；
- 服务器只保留必要的SSH管理入口；
- 不为方便调试扩大生产端口暴露面。

## 3. API边界

当前API：

```text
127.0.0.1:18000
```

这是符合V1最小暴露面的现状。

在以下条件完成前，不得直接改成`0.0.0.0`：

- 身份认证；
- HTTPS；
- 反向代理；
- 来源网络限制；
- 请求审计；
- 登录失败限制；
- 敏感响应脱敏；
- 安全测试。

未来需要局域网访问时，应通过受控入口实现，不能直接把开发端口暴露给整个网络。

## 4. PostgreSQL边界

当前宿主机端口：

```text
0.0.0.0:5432
[::]:5432
```

当前项目运行组件位于同一Docker Compose环境，正常业务通信可以使用容器网络，不需要依赖数据库宿主机端口向全部网卡开放。

后续总体设计必须在以下方案中作出明确决定：

1. 不发布数据库宿主机端口，只允许容器网络访问；
2. 仅绑定`127.0.0.1`，通过SSH隧道管理；
3. 绑定指定管理网卡，并使用来源IP白名单；
4. 采用其他经过审批的受控访问方式。

没有业务证据时，默认选择最小暴露面。

## 5. 出站网络

当前已确认服务器可以访问：

```text
https://api.tushare.pro
```

审计时HTTP状态为200，总连接耗时约0.224秒。

该证据只说明当时可用，不能证明长期稳定。

采集系统必须处理：

- DNS失败；
- TCP连接失败；
- TLS失败；
- 请求超时；
- Tushare服务错误；
- 限频；
- 返回空数据；
- 网络恢复后的断点续传。

## 6. SSH和管理入口

当前通过：

```text
ssh svr3
```

进行服务器管理。

当前没有取得以下证据：

- 是否禁止密码登录；
- 是否只允许密钥登录；
- 是否禁止root直接登录；
- 是否限制来源IP；
- 是否有失败登录防护；
- 是否记录管理操作；
- 是否有人员离职和密钥回收机制。

因此只能确认SSH可用，不能认定SSH已经安全加固。

## 7. 密钥边界

已确认的敏感配置名称包括：

```text
QUANTSTOCK1_DB_PASSWORD
QUANTSTOCK1_TUSHARE_TOKEN
QUANTSTOCK1_DATABASE_URL
```

审计文档和证据没有保存密钥明文。

后续强制要求：

- 密钥不得写入Git；
- 密钥不得写入镜像；
- 日志不得输出完整密钥；
- 错误响应不得返回连接串中的密码；
- 开发、验证和生产使用不同凭据；
- 密钥能够轮换；
- 备份中敏感配置需要单独保护。

当前环境变量注入是运行方式，不等于已经完成正式密钥治理。

## 8. 数据授权边界

Tushare分钟权限已实测可用，但购买主体、到期时间和商业授权范围未确认。

当前P1.1把项目限定为自用研究平台。

因此：

- 当前不得对外分发Tushare原始数据；
- 不得开放数据下载服务给第三方；
- 不得把未确认许可的数据用于商业客户服务；
- 数据导出、备份和日志也属于数据副本，应受同样限制；
- 用途发生变化时必须重新审查数据许可。

## 9. 日志与审计

当前项目具有任务、质量和审计相关数据库结构，但没有取得完整的主机和容器日志治理证据。

生产化前需要明确：

- API访问日志；
- 登录和鉴权日志；
- 管理操作日志；
- 数据导出日志；
- 密钥变更日志；
- 数据库异常日志；
- SSH登录日志；
- 日志保留周期；
- 日志轮转；
- 日志访问权限；
- 告警规则。

日志中禁止保存Token、密码、完整连接串和不必要的业务数据。

## 10. 备份安全

当前未确认有效备份和恢复演练。

备份安全至少包括：

- 备份文件访问权限；
- 是否加密；
- 是否与主数据库位于不同故障域；
- 是否存在异机副本；
- 是否定期验证；
- 是否能在没有原运行容器的情况下恢复；
- 密钥和数据库备份是否分开管理。

`/backup`目录存在不能作为备份完成证据。

## 11. 当前风险分级

### P0：生产化前解决

- PostgreSQL监听全部宿主机网卡；
- 防火墙和`pg_hba.conf`规则未确认；
- 数据库TLS未确认；
- SSH安全加固未确认；
- 正式密钥管理未确认；
- 备份和恢复未确认；
- CentOS Linux 8停止维护。

### P1：进入局域网共享访问前解决

- API认证；
- HTTPS或受控反向代理；
- 来源网络限制；
- 操作审计；
- 登录保护；
- 导出权限。

### P2：进入实时或实盘前解决

- 券商凭据隔离；
- 交易通道白名单；
- 双向证书或等效认证；
- 紧急停止；
- 订单审计；
- 管理操作双重确认；
- 实时风险告警。

## 12. OpenCode强制约束

OpenCode后续不得：

- 为方便调试直接公开API；
- 默认发布数据库端口；
- 把密码写入compose或代码；
- 输出Token；
- 用公网访问代替正式接入设计；
- 假设当前防火墙已经可靠；
- 假设备份已经存在；
- 把OpenCode作为服务器常驻运行组件。

OpenCode后续必须：

- 默认最小端口暴露；
- 配置与密钥分离；
- 支持不同环境；
- 对敏感字段脱敏；
- 保留安全审计接口；
- 为部署变更提供回滚；
- 把网络和安全配置形成正式部署文档。

## 13. 当前结论

当前网络足以支持：

```text
服务器内部组件通信
+
服务器出站访问Tushare
+
受控SSH管理
+
本机API调试
```

当前网络尚不能认定支持：

```text
公网应用
局域网多人共享
对外开放API
商业数据服务
实盘交易
生产数据库远程管理
```

本专题只确认边界，不实施端口、防火墙、TLS、SSH和密钥整改。
