# 数据容量与性能初步评估

> 路线图阶段：P1.5
> 状态：已确认初步边界；最终参数待全量基准
> 形成日期：2026-07-29
> 当前仓库基线：`25399e0`
> 证据文件：`evidence/quantstock1_capacity_estimate_20260729.json`

## 1. 专题结论

当前服务器足以承担：

- 全量股票基础信息；
- 全历史日线；
- 全历史复权因子；
- 全历史每日指标；
- 停复牌、涨跌停等日频事件；
- 普通财务数据；
- 分钟数据的小规模和分阶段建设；
- 单用户研究和回测验证。

当前服务器和当前存储方式不能安全承诺：

```text
2009年至今
+
全市场1分钟
+
RAW长期保留
+
CLEAN长期保留
+
完整备份
+
运行余量
```

在现有未压缩规划下，上述组合需要约：

```text
8.9—10.7 TiB
```

当前服务器可用空间：

```text
系统盘约266 GiB
/mnt/2t_ssd约1.1 TiB
/mnt/1t_back约768 GiB
```

因此P1.5的核心结论是：

```text
日频和财务可以全历史建设
1分钟数据必须分阶段、压缩、分层和归档
不能直接在当前系统盘执行2009年至今全市场初始化
```

## 2. 证据分类

本文所有数字分为三类。

### 2.1 实测值

来自当前服务器数据库和真实Tushare请求：

- 2026-07-24日线5526只股票；
- 完整股票日1分钟为241条；
- 101只股票1天分钟样本为24341行；
- RAW分钟表24341行总占用12271616字节；
- RAW分钟表平均每行约504.15字节；
- 数据库逻辑大小约78 MiB；
- PostgreSQL物理卷约169 MiB；
- TimescaleDB分钟超表当前1个chunk；
- chunk interval为7天；
- 压缩未启用。

### 2.2 计算值

由实测值直接乘算：

```text
股票数 × 每日bar数 × 年交易日数
```

### 2.3 规划假设

为形成安全容量边界采用：

- 年交易日数：242；
- 当前市场规模：5526只；
- 历史分钟起点：2009-01-05；
- 历史计算终点：2026-07-24；
- CLEAN分钟行宽：250—400字节；
- 备份和运行规划：主数据1份+完整备份1份+30%余量；
- 分钟安全调用速率：400次/分钟；
- 历史分钟窗口：30个交易日。

规划假设不是最终实施参数。正式初始化前必须用更大样本校准。

## 4. 全市场1分钟行数

当前市场规模：

```text
5526只股票
```

完整股票日1分钟：

```text
241行
```

所以一个交易日：

```text
5526 × 241
= 1,331,766行
```

按242个交易日：

```text
1,331,766 × 242
= 322,287,372行/年
```

即：

```text
约3.22亿行/年
```

2009-01-05至2026-07-24约17.55年。

如果整个历史期间都按当前5526只股票计算，上界为：

```text
约5.656138194999999591061623505083844065666198730468750000000000000000十亿行
```

该数值是当前规模上界。早期上市股票较少，实际历史行数应低于该上界，但当前没有逐年股票数量证据，不能给出准确历史总行数。

## 5. 分钟存储容量

### 5.1 仅RAW分钟

按实测每行504.15字节：

| 范围 | 估算占用 |
|---|---:|
| 全市场1个交易日 | 0.63 GiB |
| 全市场1年 | 151.32 GiB |
| 2009年至2026年当前规模上界 | 2.59 TiB |

这还没有包含CLEAN分钟、特征、分析、WAL、临时空间和备份。

### 5.2 RAW+CLEAN分钟

当前证据没有单独取得TimescaleDB内部chunk的完整物理行宽。

根据相邻CLEAN表实测，每行约244—399字节。本次将CLEAN分钟按250—400字节规划。

RAW+CLEAN：

| 范围 | 估算占用 |
|---|---:|
| 全市场1年 | 226.4—271.4 GiB |
| 2009年至2026年当前规模上界 | 3.88—4.65 TiB |

### 5.3 加备份和运行余量

规划公式：

```text
主数据1份
+
完整备份1份
+
30%运行余量
=
2.3倍
```

因此2009年至今分钟数据规划空间：

```text
8.9—10.7 TiB
```

该规划尚未加入：

- 多个备份版本；
- WAL归档；
- 数据库临时文件；
- 5/15/30/60分钟独立副本；
- 分钟特征；
- 分钟分析结果；
- 索引调整；
- 操作系统和Docker增长。

## 6. 当前磁盘承载结论

### 6.1 系统盘

系统盘剩余：

```text
约266 GiB
```

RAW+CLEAN分钟单年规划：

```text
约226—271 GiB
```

结论：

```text
系统盘最多接近承载1年分钟主数据
但没有足够备份和运行余量
```

因此不得继续把全量分钟历史初始化到当前系统盘Docker卷。

### 6.2 `/mnt/2t_ssd`

剩余：

```text
约1.1 TiB
```

在未压缩RAW+CLEAN规划下，只够约4年左右当前市场规模分钟数据，不足以覆盖2009年至今和备份。

### 6.3 `/mnt/1t_back`

剩余：

```text
约768 GiB
```

适合作为备份或归档候选位置，但不足以单独保存2009年至今完整分钟主数据和多个备份版本。

### 6.4 综合结论

当前三块空间不能简单相加作为一个可用数据库空间。

原因：

- 数据库主卷需要稳定高性能磁盘；
- 备份需要与主数据分离；
- 系统盘必须保留操作系统和Docker余量；
- 跨挂载点组合需要明确存储设计；
- 备份盘不能同时被当作主数据安全余量。

## 7. TimescaleDB压缩

当前：

```text
clean.stock_minute压缩未启用
```

Timescale官方说明，时间序列转为列式存储后可能显著节省空间，官方示例常见超过90%的压缩，但压缩效果高度依赖：

- 字段类型；
- 数据重复度；
- `segmentby`；
- `orderby`；
- chunk；
- 索引；
- 查询方式；
- 数据修订频率。

因此不能直接把官方示例压缩比写入容量承诺。

正式决定前必须对当前分钟Schema完成：

1. 至少1000只股票、20—60个交易日样本；
2. 记录压缩前表、索引和总大小；
3. 设计`security_code`为候选segment；
4. 设计`trade_time`为候选order；
5. 测试单股区间查询；
6. 测试全市场单日查询；
7. 测试聚合查询；
8. 测试补采和更正；
9. 测试压缩和解压耗时；
10. 记录真实压缩率。

Timescale官方同时说明，chunk大小会影响写入、查询和计划时间；过多小chunk也会产生负担。当前7天chunk只能保留为待测参数，不能直接认定为最终值。

## 8. RAW分钟保留策略

RAW分钟当前每行实测约504.15字节，是容量的主要来源。

如果RAW和CLEAN全部永久保留在PostgreSQL：

- 容量重复；
- 索引重复；
- 备份重复；
- 全历史初始化压力大；
- 当前磁盘不够。

P2/P4必须在以下方案中决策：

### 方案A：RAW和CLEAN都长期在数据库

优点：

- 查询简单；
- 追溯直接；
- 补洗方便。

缺点：

- 占用最大；
- 备份最大；
- 当前硬件不支持全历史。

### 方案B：RAW近期数据库+历史归档

例如：

```text
近期RAW保留在PostgreSQL
历史RAW归档到压缩文件
CLEAN保留在TimescaleDB
```

优点：

- 保留追溯；
- 显著降低数据库压力；
- 适合当前单用户平台。

缺点：

- 需要归档格式、校验和恢复工具；
- 历史重洗需要先恢复RAW。

### 方案C：只永久保留CLEAN

容量最低，但削弱原始证据和重洗能力，不符合当前全链路追溯目标，不建议作为默认方案。

本专题不直接选定方案，但容量证据表明：

```text
方案A不能直接在当前硬件上覆盖2009年至今全市场1分钟
```

## 9. 多频率数据

Tushare支持：

```text
1、5、15、30、60分钟
```

如果已经保存完整1分钟数据，5/15/30/60分钟原则上可以按统一交易时间规则聚合。

如果将所有频率都独立永久保存，按时间比例理论上会额外增加约32%的行数，实际取决于Tushare各频率bar规则。

P2/P4应优先考虑：

```text
1分钟作为基础事实
+
高频率按需聚合
+
高频使用结果选择性物化
```

不能在没有业务需求时把五个频率全部永久复制。

## 10. 特征和分析容量

分钟行数约3.22亿/年。

每增加一个`DOUBLE PRECISION`分钟特征，仅数值本身为：

```text
2.40 GiB/年
```

未包含：

- 行开销；
- 主键；
- 时间；
- 股票代码；
- 索引；
- 版本；
- 质量状态；
- 备份。

50个分钟特征的纯数值约：

```text
120.1 GiB/年
```

因此：

- 不能默认物化所有分钟特征；
- 临时研究特征不进入公共长期存储；
- 公共分钟特征必须有复用价值；
- 支持按股票池和时间范围计算；
- 支持按需重算；
- 特征版本和依赖需要登记；
- 稀疏结果应使用稀疏存储；
- 回测中间状态默认不永久保存。

日频特征行数约134万/年，远小于分钟特征，可以更积极地物化。

## 11. 回测结果容量

回测容量取决于是否保存每个bar的完整账户状态。

推荐分层：

### 永久保存

- 回测定义；
- 参数；
- 代码版本；
- 数据版本；
- 股票池版本；
- 汇总指标；
- 交易记录；
- 每日权益；
- 风控事件；
- 关键解释；
- 运行日志摘要。

### 按需保存或限期保存

- 每分钟账户快照；
- 每分钟全部股票信号；
- 全部中间因子；
- 调试级日志；
- 重复可生成结果。

单用户平台不应默认永久保存所有中间矩阵。

## 12. 采集调用量与时间

### 12.1 日常1分钟采集

`stk_mins`一次请求一个股票。

当前市场规模：

```text
5526次请求/交易日
```

当前日单股票探测耗时约1.045秒。

单线程理论耗时：

```text
约96.2分钟
```

按项目安全频率400次/分钟，纯限频下界：

```text
约13.8分钟
```

实际还包括：

- 网络波动；
- 空返回；
- 重试；
- RAW写入；
- CLEAN处理；
- 质量校验；
- 数据库提交；
- 任务状态。

因此日常分钟采集应设计为受控并发，目标窗口可初步设为：

```text
30—120分钟
```

最终目标必须通过全市场真实运行确定。

### 12.2 历史分钟初始化

30个交易日窗口下，按当前市场规模上界：

```text
约782,315次请求
```

按400次/分钟，纯接口限频下界：

```text
约32.6小时
```

该数值没有包含数据写入、质量处理、失败重试和早期股票数量变化。

历史初始化实际可能持续数天。

必须支持：

- 分批；
- 暂停；
- 续跑；
- 按年份；
- 按市场；
- 按股票；
- 按频率；
- 失败隔离；
- 进度统计；
- 磁盘水位停止。

## 17. P2/P4强制设计输入

后续设计必须：

1. 数据库主卷不继续使用当前系统盘作为全量分钟最终位置；
2. 为分钟数据定义RAW、CLEAN和归档生命周期；
3. 为磁盘设置预警和停止阈值；
4. 大规模初始化支持容量预估和剩余空间检查；
5. TimescaleDB chunk和压缩通过真实样本确定；
6. 1分钟作为优先基础频率；
7. 其他频率优先聚合，不默认重复存储；
8. 分钟特征按需物化；
9. 回测中间状态按生命周期管理；
10. 备份容量单独计算；
11. 初始化、日常采集和研究计算资源隔离；
12. 所有容量参数配置化；
13. 每批记录行数、字节数、耗时和压缩率；
14. P1.5结果不能被解释为最终性能验收。

## 18. P1.5结论

资源判断：

| 数据范围 | 当前服务器结论 |
|---|---|
| 日频全历史 | 可支持 |
| 财务和事件全历史 | 可支持 |
| 分钟样本 | 可支持 |
| 全市场近期1分钟 | 有条件支持 |
| 全市场3—5年1分钟 | 需要迁盘、压缩和验证 |
| 2009年至今RAW+CLEAN分钟 | 当前不支持直接实施 |
| 全历史分钟+完整备份 | 当前容量不足 |
| 大规模分钟特征 | 必须选择性建设 |
| 多用户高并发 | 当前不在范围 |
| 实时和实盘 | 当前不在范围 |

P1.5完成的是容量边界，不是最终存储方案。

下一步进入P2，先确认V1最终场景和阶段范围，再决定：

- 分钟正式历史范围；
- RAW保留周期；
- 数据库磁盘位置；
- 压缩；
- chunk；
- 备份；
- 特征物化；
- 查询和回测性能目标。
