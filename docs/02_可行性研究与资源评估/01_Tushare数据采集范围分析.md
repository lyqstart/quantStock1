# Tushare数据采集范围分析

> 文档阶段：P1 可行性研究与资源评估  
> 核查日期：2026-07-26  
> 账户条件：2120积分 + A股历史分钟独立权限 + 集合竞价独立权限  
> 目标：确定第一阶段应采集的Tushare数据范围、接口限制和实施约束
> Token状态：已由用户历史实际验证可正常使用，本阶段不重复验证

---

## 1. 结论

第一阶段采用以下原则：

1. Tushare作为主要数据源。
2. 对当前账户**正式权限范围内、与A股研究直接相关的数据全部采集**。
3. 不把“试用权限”视为正式采集权限。
4. 对需要单独付费、但当前未购买的接口，不进入第一阶段采集。
5. 对Tushare官网未明确写出单次返回量或接口级频率的接口，实施前必须用当前Token实测。
6. 采集程序不能假设“一个接口一次调用可以取全量”，必须支持按日期、股票、市场等维度拆分，以及断点续采、重试、限流和去重。
7. Tushare官网存在旧权限总表与当前接口页描述不一致的情况，本文判断优先级为：
   - 当前具体接口页面；
   - 当前《积分与频次权限对应表》；
   - 项目内保存的Tushare参考资料；
   - 实施阶段当前Token实测结果。
8. 最终是否真正具备权限，以当前Token实际调用返回为最终证据。

## 2. 当前账户总权限

### 2.1 积分权限

当前积分：**2120积分**。

Tushare当前积分频次表规定：

| 积分等级 | 每分钟总频次 | 每天总量上限 |
|---|---:|---:|
| 2000积分以上 | 200次 | 100000次/个API |

说明：

- 这是积分接口的通用上限。
- 某些具体接口有独立的频率限制，应以接口页面的更具体规定为准。
- 部分接口虽然最低积分低于2000，但仍可能有自己的每分钟流控。

### 2.2 独立购买权限

当前已确认购买：

| 权限 | 状态 | 官方频率 |
|---|---|---|
| A股历史分钟 | 已购买 | 500次/分钟，单次8000行，总量不限制 |
| 集合竞价 | 已购买 | 500次/分钟，总量不限制 |

未确认购买的独立权限一律按“无权限”处理。

1分钟数据量最大，不能按“单股票全部历史”一次请求。

- 股票维度拆分；
- 时间窗口拆分；
- 8000行硬上限保护；
- 已采时间游标；
- 断点续传；
- 区间重叠校验；
- 去重；
- 缺口检测；
- 失败区间单独补采。

第一阶段数据库容量评估必须以**全A股1分钟数据**作为最大压力场景单独测算。

# 10. 免费爬虫类实时接口

项目参考资料中存在以下0积分爬虫接口：

- `realtime_quote`
- `realtime_tick`
- `realtime_list`

这些接口虽然可以采，但定位必须与Tushare Pro结构化历史数据分开：

1. 作为辅助实时数据源；
2. 单独记录来源；
3. 不把其稳定性视为与Pro正式接口相同；
4. 失败不能影响核心历史数据采集；
5. 数据库中必须保留来源标识。

# 12. 关键字段结构分析

本节只分析**会影响采集、增量、去重、修订版本和后续数据库设计的关键字段**。

本阶段不展开每个接口全部业务字段。全部字段名称、类型、单位、是否为空、目标数据库字段映射，进入详细设计阶段后形成独立的《Tushare接口字段与数据表映射设计》。

## 12.1 字段分析原则

每个接口至少要确认六类字段：

| 字段类别 | 作用 |
|---|---|
| 对象标识 | 判断数据属于哪只股票、哪个指数、哪个公司或哪个市场 |
| 业务时间 | 判断数据属于哪个交易日、分钟、公告日或报告期 |
| 增量字段 | 决定下一次从哪里继续采 |
| 去重字段 | 决定一条数据是否已经存在 |
| 版本字段 | 判断旧数据是否被修订 |
| 状态字段 | 判断上市、停牌、公告状态、实施状态等变化 |

平台不能把“API返回的一行”直接等同于“数据库中永远唯一的一行”。

## 12.2 股票基础与公司信息关键字段

| 数据/API | 对象标识 | 时间/状态关键字段 | 建议去重依据 | 增量/更新依据 | 设计注意 |
|---|---|---|---|---|---|
| 股票基础 `stock_basic` | `ts_code`、`symbol` | `list_status`、`list_date`、`delist_date` | `ts_code` | 上市状态、上市/退市日期变化 | 股票名称、行业、实控人等属性可能变化，不能只初始化一次后永久不更新 |
| 上市公司 `stock_company` | `ts_code` | 公司状态及基础资料更新时间以实际返回为准 | `ts_code` | 定期全量比对 | 公司名称、法人、注册资本、注册地址等属于可变化维度 |
| 管理层 `stk_managers` | `ts_code` + 人员标识/姓名 | 任职起止日期、公告日期等 | 不能仅用姓名；实施前按官方字段确认组合键 | 公告/任职变化 | 同一人可能多次任职，同名人员也可能存在 |
| 管理层薪酬持股 `stk_rewards` | `ts_code` + 人员 | 报告期/公告期 | `ts_code + 报告期 + 人员`候选 | 报告期 | 实施前用Token返回确认最终唯一键 |
| 北交所代码映射 `bse_mapping` | 新旧代码 | 映射生效信息 | 新代码+旧代码 | 定期全量比对 | 用于历史代码连续性，不应直接覆盖历史代码 |
| IPO新股 `new_share` | `ts_code` | `ipo_date`、`issue_date`等 | `ts_code` | 新发行日期 | 上市前数据与正式股票列表需要关联 |
| 股票曾用名 `namechange` | `ts_code` | 名称变更起止日期/公告信息 | `ts_code + 名称 + 生效区间`候选 | 名称变更时间 | 不能把旧名称覆盖掉，应保留历史 |
| 交易日历 `trade_cal` | `exchange` | `cal_date`、`is_open`、`pretrade_date` | `exchange + cal_date` | 向未来补齐并定期复核 | 是所有日级采集任务的时间基准 |

## 12.4 分钟行情关键字段

A股历史分钟属于独立购买权限，是第一阶段数据量最大的接口之一。

关键字段：

| 字段 | 作用 |
|---|---|
| `ts_code` | 股票 |
| `trade_time` | 分钟时间 |
| `freq` | 1/5/15/30/60分钟频率，部分调用方式由请求参数给出 |
| `open/high/low/close` | 分钟OHLC |
| `vol` | 分钟成交量 |
| `amount` | 分钟成交额 |

建议逻辑唯一键：

```text
ts_code + freq + trade_time
```

即使官方返回结果中没有把`freq`作为独立列保存，平台也必须把请求频率写入数据库。

否则：

```text
600000.SH + 2026-07-01 10:00:00
```

无法判断这条记录究竟是：

- 1分钟K线；
- 5分钟K线；
- 15分钟K线；
- 30分钟K线；
- 60分钟K线。

### 分钟时间边界

Tushare官方说明：

- 时间参数需要包含时分秒；
- `end_date`如果只输入日期，不包含时间，返回结果不包含该日期当天；
- 单次最多8000行。

因此分钟采集游标不能只保存日期，必须保存：

```text
ts_code
freq
last_trade_time
```

## 12.5 集合竞价关键字段

`stk_auction_o`和`stk_auction_c`官方字段结构基本一致：

- `ts_code`
- `trade_date`
- `open`
- `high`
- `low`
- `close`
- `vol`
- `amount`
- `vwap`

建议逻辑唯一键：

开盘竞价：

```text
ts_code + trade_date + auction_type=open
```

收盘竞价：

```text
ts_code + trade_date + auction_type=close
```

数据库不能仅依靠：

```text
ts_code + trade_date
```

因为同一只股票同一天同时存在开盘集合竞价和收盘集合竞价。

平台应额外保存来源/类型字段，例如：

```text
auction_type
source_api
```

## 12.6 财务报表关键字段

利润表、资产负债表、现金流量表是最需要保留版本的数据。

核心字段结构：

| 字段 | 作用 |
|---|---|
| `ts_code` | 股票 |
| `ann_date` | 公告日期 |
| `f_ann_date` | 实际公告日期，接口存在时必须保存 |
| `end_date` | 报告期 |
| `report_type` | 报表类型 |
| `comp_type` | 公司类型 |
| `end_type` | 报告期类型，接口存在时保存 |
| `update_flag` | 是否最新版本 |

### 财务报表不能采用的错误唯一键

禁止只使用：

```text
ts_code + end_date
```

因为同一股票、同一报告期可能同时存在：

- 合并报表；
- 单季合并；
- 调整后报表；
- 调整前报表；
- 母公司报表；
- 后续修订数据。

### 原始层建议唯一性思路

原始层应优先保留：

```text
ts_code
end_date
ann_date / f_ann_date
report_type
```

必要时再增加接口实际返回的版本字段。

`update_flag=1`表示最新版本，但原始层**不能因此删除旧版本**。

旧版本对于历史回测非常重要。

## 12.7 财务指标关键字段

`fina_indicator`当前官方关键字段包括：

- `ts_code`
- `ann_date`
- `end_date`
- `update_flag`
- 大量财务指标字段

单次最多100条。

建议原始层版本识别：

```text
ts_code + end_date + ann_date
```

并保存：

```text
update_flag
```

不能只保留`update_flag=1`。

原因：

历史回测必须知道：

> 在当时那个交易日，市场实际能看到的是哪一版财务指标。

## 12.8 业绩、分红和披露类关键字段

| API | 对象 | 时间字段 | 去重/版本重点 |
|---|---|---|---|
| `forecast` | `ts_code` | 公告日期 + 报告期 | 同一报告期可能多次预告/修正，必须保留公告时间 |
| `express` | `ts_code` | 公告日期 + 报告期 | 不能只按报告期覆盖 |
| `dividend` | `ts_code` | 公告日、报告期、实施相关日期 | 同一报告期可能存在方案变化，需保存方案状态 |
| `fina_audit` | `ts_code` | 公告日 + 报告期 | 按股票、报告期、公告版本保留 |
| `fina_mainbz` | `ts_code` | 报告期 | 还需要产品/地区/业务类别字段参与唯一性判断 |
| `disclosure_date` | `ts_code` | 报告期、计划披露日、实际披露日 | 计划日期会调整，必须保存最终披露状态或变化记录 |

这类数据的共同原则：

> 报告期不是“市场知道这条信息的时间”。

回测和策略计算使用时，必须以公告/实际披露时间控制可见性。

## 12.12 龙虎榜与大宗交易

### 龙虎榜 `top_list`

逻辑上至少包含：

```text
ts_code
trade_date
```

但同一股票同一天可能存在不同上榜原因/席位事实，因此数据库唯一性不能未经验证直接设为：

```text
ts_code + trade_date
```

必须把：

- 上榜原因；
- 交易明细维度；
- 官方当前返回的区分字段

纳入详细设计。

### 大宗交易 `block_trade`

同样不能只按：

```text
ts_code + trade_date
```

因为同一股票同一交易日可能发生多笔成交。

实施阶段需要根据：

- 成交价；
- 成交量；
- 买方营业部；
- 卖方营业部；
- 官方记录字段

确定稳定组合键；若官方没有业务唯一编号，原始层应增加平台自己的记录哈希。

## 12.14 免费实时爬虫数据关键字段

`realtime_quote`、`realtime_tick`、`realtime_list`属于辅助数据源。

除了接口本身返回字段，平台必须额外增加：

```text
source
source_api
fetch_time
trade_time
```

其中：

- `trade_time`：市场事件发生时间；
- `fetch_time`：平台实际获取时间。

二者不能混用。

实时爬虫数据还必须允许：

- 重复记录；
- 短时缺失；
- 来源字段变化；

因此不能直接采用“覆盖式写入”。

后续原始数据层建议每张采集表至少具备平台侧审计字段：

```text
_fetch_time
_batch_id
_raw_hash
```

含义：

| 字段 | 作用 |
|---|---|
| `_source` | 数据来源，例如Tushare |

这些字段不是Tushare业务字段，是平台自己的数据治理字段。

## 12.16 字段层面对后续架构的结论

现在已经可以确定：

### 第一类：天然快照数据

典型：

```text
daily
daily_basic
moneyflow
margin_detail
index_daily
```

基本可以按：

```text
对象 + 交易日
```

管理。

### 第二类：时间序列高频数据

典型：

```text
stk_mins
```

必须按：

```text
对象 + 频率 + 精确时间
```

管理。

### 第三类：版本型财务数据

典型：

```text
income
balancesheet
cashflow
fina_indicator
```

必须同时保存：

```text
报告期
公告时间
报表类型
更新版本
```

不能覆盖历史版本。

### 第四类：事件型数据

典型：

```text
repurchase
share_float
pledge_detail
stk_holdertrade
block_trade
top_list
```

不能简单套用统一主键，必须根据事件字段建立组合键或记录指纹。

### 第五类：关系有效期数据

典型：

```text
index_member_all
namechange
管理层
行业成分
```

必须保存：

```text
生效时间
失效时间
```

而不是只保存当前状态。

# 13. 接口限制对采集系统的直接要求

上述限制已经足以影响总体设计，因此不能留到开发阶段再考虑。

采集系统必须从设计阶段就具备以下能力。

## 13.1 全局限流器

至少需要两类限流池：

### 积分接口

按当前2120积分：

- 默认不超过200次/分钟；
- 默认不超过100000次/日/每个API；
- 接口有更低专属频率时按更低值；
- `daily`等明确允许更高接口级频率时，也不能写死，应配置化。

### 独立权限接口

历史分钟：

- 500次/分钟；
- 单次8000行。

集合竞价：

- 500次/分钟；
- 总量不限制；
- 历史开/收盘接口单次10000行。

---

## 13.2 所有接口限制必须配置化

禁止在代码中写死：

```text
sleep(0.3)
limit=5000
```

每个接口应该有独立元数据，例如：

```text
api_name
permission_type
min_points
max_rows_per_request
max_calls_per_minute
max_calls_per_day
update_time
split_dimension
supports_pagination
history_start
enabled
```

这样Tushare以后调整规则时只修改配置，不改采集程序主体。

---

## 13.3 分片策略

接口至少分为以下几类：

### 按交易日提取

适用于：

- `daily`
- `daily_basic`
- `adj_factor`
- `stk_limit`
- `moneyflow`
- `margin_detail`

优势：

每天一次可以获得全市场数据，最适合日常增量。

### 按股票提取

适用于：

- 财务报表；
- `fina_indicator`
- `fina_mainbz`
- 前十大股东；
- 管理层；
- 历史分钟。

### 按股票 + 时间窗口

主要适用于：

- `stk_mins`

必须动态缩小窗口，保证任何请求都不会碰到8000行上限。

### 按指数 + 时间

适用于：

- `index_daily`
- `index_weight`

---

## 13.4 返回行数不能等同于“数据完整”

如果返回行数正好等于接口上限，例如：

```text
6000
3000
2000
1000
100
8000
10000
```

采集器必须把它视为：

> 可能被截断

不能直接标记任务成功。

应该自动：

1. 缩小日期窗口；
2. 或切换股票/市场维度；
3. 重新请求；
4. 直到结果明显低于上限；
5. 再进行完整性检查。

# 14. 实施阶段必须进行的接口级Token探测

Token本身的有效性已经历史实际验证通过，本阶段不再重复验证。

但具体接口权限、返回边界和Tushare后续规则变化仍需要在实施阶段通过当前账户实际调用确认。

必须建立自动接口权限探测程序，对每个候选API执行最小查询，记录：

```text
api_name
test_time
request_params
return_code
return_message
returned_rows
elapsed_ms
permission_result
```

判断规则：

- `code = 0`：接口可用；
- 权限错误：关闭接口；
- 参数错误：修正参数后重新验证；
- 返回空数据：不能直接判断无权限，要换有已知历史数据的参数复测。

重点实测：

- `namechange`
- `trade_cal`
- `suspend_d`
- `pledge_detail`
- `hsgt_top10`
- `ggt_top10`
- `ggt_daily`
- `stk_auction`
- 所有当前官网没有明确写出接口级限量的候选接口。

# 15. 第一阶段最终采集策略

第一阶段不是“先做几个最常用接口”，而是：

> 建立一个通用采集框架，然后把当前正式权限内的全部A股相关接口逐步接入。

顺序建议：

### A级：平台基础依赖

- 股票基础信息；
- 交易日历；
- 日线；
- 复权因子；
- 每日指标；
- 停复牌；
- 涨跌停价格。

### B级：财务与公司行为

- 三大财务报表；
- 财务指标；
- 业绩预告/快报；
- 分红；
- 股东；
- 回购；
- 解禁；
- 质押。

### C级：资金和市场行为

- moneyflow；
- 融资融券；
- 沪深港通；
- 龙虎榜；
- 大宗交易。

### D级：指数和行业

- 指数行情；
- 指数成分；
- 申万行业分类和成分；
- 市场交易统计。

### E级：高数据量专项

- A股历史分钟；
- 集合竞价。

这里的A~E仅代表**实施先后顺序**，不代表后面的数据不采。

# 16. 本阶段结论

目前已经确认：

1. 2120积分属于Tushare 2000积分以上档位。
2. 积分接口通用额度为200次/分钟、100000次/日/每个API。
3. 具体接口存在独立频率和单次返回限制，采集器必须按接口配置。
4. A股历史分钟是独立购买权限：
   - 500次/分钟；
   - 8000行/次；
   - 必须分股票、分时间区间采集。
5. 集合竞价是独立购买权限：
   - 500次/分钟；
   - `stk_auction_o`、`stk_auction_c`单次10000行；
   - 历史数据可按日期循环。
6. 2120积分无法覆盖所有Tushare A股接口，5000/6000/8000积分和其他独立权限数据明确排除。
7. 当前正式权限内的接口全部进入采集规划。
8. Token基础有效性已经历史验证；实施阶段建立接口级自动权限探测，作为当期“实际可采接口清单”的运行基线。
9. 本文的限制条件必须进入后续采集架构设计，不应等到编码时再临时处理。
10. 已完成会影响架构的关键字段分类：对象标识、业务时间、增量、去重、版本和状态字段。
11. 全部接口的逐字段类型、单位、空值和数据库映射留到详细设计阶段完成。
