# 7. 当前依赖治理问题

同一量化平台内部已经出现小范围版本分叉：

```text
FastAPI     0.136.3 / 0.136.1
Uvicorn     0.48.0 / 0.47.0
SQLAlchemy  2.0.50 / 2.0.49
Starlette   1.1.0 / 1.0.1
```

后续正式建设应做到：

1. 所有业务服务统一Python主版本；
2. 公共依赖使用统一版本基线；
3. API、Scheduler、Worker尽量从同一基础镜像构建；
4. 依赖版本固定；
5. 重新部署时不能自动漂移到未知版本。

本阶段只记录问题，不修改正在运行的环境。

# 20. 遗留项目资源复用规则

旧quantStock的利用遵守以下规则：

## 可以复用

- 历史数据；
- 已验证的数据接口经验；
- 已确认正确的字段口径；
- 可证明正确的算法或处理规则；
- 运行和性能数据；
- 故障经验；
- 技术选型实证。

## 不能直接复用为新项目运行依赖

- 旧数据库实例；
- 旧Redis实例；
- 旧容器网络；
- 旧端口；
- 旧部署目录；
- 旧任务状态表；
- 旧服务之间的调用关系；
- 未经重新验证的旧代码。

## 新项目部署原则

新quantStock1必须拥有独立的：

```text
项目目录
Docker Compose项目名
容器名
Docker网络
数据库
数据库用户
Redis
端口
配置
日志
备份路径
任务状态
```

旧quantStock和新quantStock1可以在同一台svr3上共存，但不能互相形成运行依赖。

# 21. 本阶段结论

## 结论一

当前服务器已经具备运行量化平台所需的大部分基础软件能力；旧quantStock也提供了实际运行证据。新quantStock1仍需独立创建自己的运行环境。

## 结论二

旧quantStock已实际验证以下后端技术可在svr3运行：

```text
Python 3.11
FastAPI
Uvicorn
SQLAlchemy
Alembic
Celery
Redis
PostgreSQL / TimescaleDB
Pandas / NumPy / PyArrow
Docker Compose
Nginx
```

## 结论三

PostgreSQL + TimescaleDB已经被旧项目实际验证，作为新项目主数据库的优先候选：

```text
PostgreSQL + TimescaleDB
```

本阶段没有发现需要更换数据库的证据。

## 结论四

第一阶段数据采集、数据清洗和数据存储可以直接在现有技术体系上继续建设。

## 结论五

当前主要问题不是“缺少技术”，而是：

```text
依赖版本需要统一
镜像版本需要固定
数据库实例需要明确
任务调度职责需要明确
```

这些问题进入总体设计和开发实施阶段处理。

## 结论六

当前前端框架证据不足。

以后续quantStock1仓库代码为准，不在本阶段猜测。
