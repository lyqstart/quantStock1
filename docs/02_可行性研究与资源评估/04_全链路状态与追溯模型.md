> 路线图阶段：P2.2 核心业务对象与生命周期
> 项目：A股量化研究与信号决策平台
> 形成日期：2026-07-29
> 状态：已确认
> 当前仓库基线：`f4add37`
> 配套文档：`03_核心业务对象与生命周期.md`

## 1. 文档目的

本文件定义平台正式结果如何跨模块追溯。

任何正式对象都必须能够回答：

```text
它是什么
谁产生
何时产生
在哪个环境产生
用了哪些数据
用了哪版规则和代码
由哪次任务执行
中间发生了哪些状态变化
最终为什么得到该结果
```

追溯不是日志堆积。

追溯是：

```text
业务对象之间的稳定引用
+
不可变版本
+
执行记录
+
状态事件
+
可重建的上下游关系
```

## 2. 当前追溯事实与缺口

当前数据库已经能够间接表达：

```text
DataSource / DataItem / SourceBinding
↓
CollectTask / CollectRun
↓
RequestSlice / SliceAttempt
↓
RawBatch
↓
CleanBatch
↓
QualityRun / QualityIssue / DataGap
↓
AuditEvent
```

当前主要缺口：

- `lineage` schema没有正式基础表；
- RAW到CLEAN的记录级和批次级关系需要统一；
- 数据质量失败对下游对象的影响关系尚未形成；
- DataSnapshot尚未建立；
- Feature、Analysis、StockPool、Strategy和Backtest尚未形成正式追溯；
- Signal和UserDecision尚未形成；
- 当前AuditEvent不能代替完整血缘。

P2.2确定建设正式追溯模型，但不要求本阶段直接修改数据库。

## 4. 标识体系

### 4.1 object_id

表示稳定业务对象：

```text
我是谁
```

例如：

- strategy_id；
- data_item_id；
- stock_pool_id。

### 4.2 version_id

表示正式不可变版本：

```text
使用的是哪一版
```

例如：

- strategy_version_id；
- feature_version_id；
- risk_rule_version_id。

### 4.3 run_id

表示一次真实执行：

```text
是哪一次运行
```

例如：

- collect_run_id；
- feature_run_id；
- backtest_run_id。

### 4.4 batch_id

表示一次运行处理或产生的数据集合：

```text
是哪一批数据
```

例如：

- raw_batch_id；
- clean_batch_id；
- archive_batch_id。

### 4.5 trace_id

表示一条跨模块业务链：

```text
这些对象属于哪条完整业务活动
```

一个trace可以包含多个run和batch。

### 4.6 request_id和provider_request_id

`request_id`表示平台内部一次请求。

`provider_request_id`表示外部数据源或券商返回的请求标识。

二者不能替代run_id和trace_id。

## 5. 正式事实来源

追溯关系采用两层存储：

```text
领域表明确外键
+
通用lineage_edge遍历索引
```

规则：

1. 关键直接关系必须保存在领域表或明确关联表；
2. `lineage_edge`用于跨模块查询和影响分析；
3. `lineage_edge`不是唯一事实源；
4. 通用血缘可以根据领域表重建；
5. AuditEvent记录变化，不承担数据依赖关系。

例如：

```text
Signal.trade_plan_id
RiskEvaluation.trade_plan_id
BacktestRun.strategy_version_id
```

必须是明确字段，不能只放在通用JSON或lineage表中。

## 6. lineage_edge设计

建议建立：

```text
lineage.lineage_edge
```

核心字段：

```text
lineage_edge_id
trace_id
upstream_object_type
upstream_object_id
upstream_version_id
downstream_object_type
downstream_object_id
downstream_version_id
relation_type
run_id
environment_id
created_at
metadata
```

建议relation_type：

```text
DERIVED_FROM
PRODUCED_BY
USED_AS_INPUT
VERSION_OF
VALIDATED_BY
GENERATED_FROM
EVALUATED_BY
DECIDED_ON
MIGRATED_FROM
REPLACED_BY
INVALIDATED_BY
ARCHIVED_TO
```

relation_type必须受控，不允许业务代码任意创建新字符串。

## 7. 数据采集追溯

一条RAW记录至少能追溯到：

```text
DataItem
DataSource
SourceBinding
CollectTask
CollectRun
RequestSlice
SliceAttempt
RawBatch
```

必须能够查询：

- 数据源；
- 接口；
- 请求参数摘要；
- 请求时间；
- 业务范围；
- 返回行数；
- 是否命中上限；
- 是否拆分；
- 重试次数；
- 外部错误；
- 原始内容哈希。

### 7.1 调用上限追溯

如果返回行数等于接口上限：

```text
Slice
↓
possible_truncation
↓
SPLIT
↓
子Slice
```

父Slice、子Slice和最终RawBatch必须保持关系。

## 8. RAW到CLEAN追溯

CleanBatch必须记录输入RawBatch集合。

建议关联表：

```text
lineage.clean_batch_input
```

或等价明确关系：

```text
clean_batch_id
raw_batch_id
relation_type
record_scope
```

记录级追溯按数据价值分层：

### 必须记录级追溯

- 财务修订；
- 多源冲突；
- 数据迁移；
- 人工修正；
- 发生质量争议的数据。

### 可以批次级追溯

- 来源唯一；
- 规则确定；
- 批次内一对一转换；
- 能通过业务主键和批次重建关系的数据。

不能要求所有分钟记录都建立逐行血缘边，避免产生比业务数据更大的血缘表。

## 9. 质量门禁与发布追溯

正式数据不能只有“存在或不存在”。

质量流程：

```text
CleanBatch
↓
QualityRun
├─ PASSED
├─ WARNING
└─ FAILED
```

只有满足发布规则的结果才能进入DataSnapshot。

必须记录：

```text
quality_rule_version
quality_run_id
issue_count
gap_count
release_decision
release_reason
released_at
```

WARNING是否允许发布由DataItem质量策略决定。

FAILED不能自动进入正式研究。

## 10. 财务数据追溯

财务数据必须同时记录：

```text
report_period
announcement_date
actual_announcement_time
available_at
revision_no
source_version
valid_from
valid_to
is_current
```

回测时：

```text
研究时点T
只能读取available_at <= T的数据版本
```

后续修订不能覆盖历史可见事实。

## 11. 行情与分钟数据追溯

行情至少包含：

```text
security_code
trade_date或trade_time
frequency
source_binding_id
raw_batch_id
clean_batch_id
quality_status
```

分钟频率必须明确：

```text
1min
5min
15min
30min
60min
```

高周期由1分钟聚合时必须记录：

```text
aggregation_rule_version
source_frequency
target_frequency
```

## 12. DataSnapshot追溯

DataSnapshot不是复制所有数据。

它表示可重复定位的数据视图。

必须保存：

```text
snapshot_scope
as_of_time
available_at_cutoff
data_item_version_set
quality_policy_version
watermark_set
content_fingerprint
```

重跑回测时必须能够重新得到同一输入集合，或明确证明原数据已经归档和恢复。

DataSnapshot被INVALIDATED后：

- 已有BacktestRun仍保留；
- 新任务默认不能继续使用；
- 必须记录失效原因；
- 需要时创建替代Snapshot。

## 13. 特征和分析追溯

```text

```

AnalysisResultSet至少绑定：

```text

parameter_snapshot
analysis_run_id
```

## 16. 回测追溯

BacktestRun必须不可变绑定：

```text
strategy_version_id
data_snapshot_id
stock_pool_version_id
parameter_snapshot
time_range
cost_model_version
risk_rule_version
runtime_version
code_commit
trace_id
```

回测结果包括：

- 汇总指标；
- 交易记录；
- 每日权益；
- 风控事件；
- 异常；
- 运行日志摘要。

重新运行产生新BacktestRun。

不能覆盖旧结果。

```text
↓
Order
↓

↓

↓
```

每个对象必须保存：

## 20. 状态变化审计

所有关键状态变化写入：

```text
audit.audit_event
```

至少记录：

```text
event_id
event_type
object_type
object_id
old_status
new_status
actor_type
actor_id
reason
trace_id
run_id
request_id
environment_id
occurred_at
metadata
```

关键状态包括：

- 启用、停用和退役；
- 版本激活和废弃；
- 任务开始、失败、取消和重跑；
- 数据隔离、发布和失效；
- 质量问题豁免；
- 风控通过或阻断；
- 信号发布、取消和过期；
- 用户决策；
- 高风险配置修改；
- 归档和删除。

## 21. 失效与影响传播

发现上游问题后不能静默修正。

处理链：

```text
发现问题
↓
QualityIssue / AuditEvent
↓
标记受影响批次
↓
查询lineage下游
↓
评估影响
↓
INVALIDATE或RECOMPUTE
↓
形成新版本或新Run
```

可能受影响：

- DataSnapshot；
- FeatureResultSet；
- AnalysisResultSet；
- StockPoolVersion；
- BacktestRun；
- TradePlan；
- Signal。

传播不是无条件自动删除。

必须按对象类型决定：

```text
只告警
禁止新使用
标记INVALIDATED
重新计算
人工复核
```

## 22. 归档追溯

大容量分钟数据归档必须产生ArchiveBatch。

至少记录：

```text
archive_batch_id
source_object_type
source_scope
destination
format
compression
checksum
record_count
archive_time
verification_result
delete_after_archive
```

必须先验证归档可读取，再允许删除热存储副本。

归档后DataSnapshot仍需能够定位归档位置。

## 23. 旧quantStock迁移追溯

```text
LegacyMigrationBatch
```
```text
↓

↓

↓

↓
```


## 24. 环境和归属追溯

所有执行、批次、审计和血缘记录必须明确：

```text
environment_id
owner_user_id或system_owner
```

至少区分：

```text
dev
test
prod
legacy
```

dev和test对象不得直接成为prod正式结果。

从test或dev晋级到prod的是：

```text
代码版本
配置版本
规则版本
迁移脚本
```

不是把测试状态记录直接改成prod状态。

## 25. AI操作追溯

AI属于actor_type之一。

AI动作必须记录：

```text
actor_type = AI
model_provider
model_name
prompt_version
tool_name
requested_by_user_id
result_summary
```

AI只能：

- 查询；
- 解释；
- 生成草案；
- 请求系统执行受控动作。

AI不能：

- 直接改数据库；
- 绕过状态机；
- 绕过风控；
- 直接下单；
- 隐藏真实操作人。

## 27. 追溯接口要求

上层页面和AI不直接拼接跨Schema SQL。

平台提供统一追溯服务：

```text
get_upstream(object_type, object_id)
get_downstream(object_type, object_id)
get_trace(trace_id)
get_status_history(object_type, object_id)
get_impact(object_type, object_id)
```

返回结果必须区分：

```text
直接事实关系
通用血缘索引关系
推导影响关系
```

## 28. 性能和容量原则

追溯不能为每条分钟记录建立完整图节点。

采用：

```text
定义级
版本级
Run级
Batch级
必要时记录级
```

五级粒度。

默认：

- 分钟行情使用Batch级；
- 财务修订使用记录级；
- 策略、回测、信号使用对象级；
- 状态变化使用事件级。

Lineage表按：

```text
upstream
downstream
trace_id
created_at
```

建立索引。

## 30. 验证用例

P2后续实施至少验证：

1. 任一RawBatch能查到来源接口和请求；
2. 任一CleanBatch能查到输入RawBatch；
3. 任一QualityIssue能查到影响批次；
4. 任一DataSnapshot能定位数据版本；
5. 任一BacktestRun能定位策略、参数、代码和数据；
6. 任一Signal能回查到数据源；
7. 任一UserDecision能回查系统建议；
8. 上游数据失效能列出下游影响；
9. 重跑不会覆盖原Run；
10. 归档后仍能定位数据；
11. dev、test、prod追溯不混淆；
12. AI动作能够识别真实用户和模型。

## 31. 禁止事项

禁止：

- 用日志文本代替血缘；
- 用AuditEvent代替依赖关系；
- 只保存trace_id而不保存直接外键；
- 把所有分钟记录建成血缘节点；
- 用“当前最新版”代替版本ID；
- 覆盖失败Run；
- 删除被正式结果引用的版本；
- 上游修正后静默重写下游结果；
- 让AI生成不可审计的正式状态；
- 让旧quantStock进入新平台在线主链。

## 32. P2.2完成结论

平台追溯模型确定为：

```text
领域表直接引用
+
统一object/version/run/batch/trace标识
+
可重建lineage_edge
+
只追加AuditEvent
+
质量失效影响分析
```

当前数据底座继续作为第一实施批次。

P2.2完成后，下一步进入P2.3总体系统架构，确定模块、进程、数据库、存储、缓存、环境和部署拓扑如何承载这些对象。
