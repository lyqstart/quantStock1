# 6. 单服务器多环境带来的约束

当前模式在个人项目阶段可用，但必须明确其风险。

## 6.1 运行冲突风险

开发或测试过程中可能：

- 占用正式环境CPU；
- 占用内存；
- 占用磁盘IO；
- 占用端口；
- 影响正式采集任务。

## 6.2 数据风险

如果开发、测试直接连接正式数据库，可能造成：

- 测试数据污染正式数据；
- 错误SQL修改正式数据；
- 调试任务重复采集；
- 清洗程序误处理正式数据。

## 6.3 部署风险

同一服务器直接开发并运行正式系统，错误版本可能影响正在运行的服务。

## 6.4 运维风险

服务器故障时同时失去：

```text
开发能力
测试能力
正式服务
```

因此svr3是当前项目的单点资源。

# 7. 当前阶段的环境策略

当前阶段不要求立即购买新的服务器。

原因：

- 项目由一人维护；
- 当前主要目标是数据采集和数据清洗；
- svr3现有计算资源足以支撑第一阶段；
- 增加服务器会增加维护成本。

但是后续总体设计必须在同一台svr3内部做到逻辑隔离：

```text
开发
测试
正式
```

至少不能让测试任务直接影响正式数据和正式采集任务。

具体隔离方式进入总体设计阶段确定。

# 10. 免费备用数据源：AKShare

当前还可以使用：

```text
AKShare
```


- 网站页面变化；
- 反爬策略；
- 接口变化；
- 数据源结构变化

影响。

因此第一阶段不把AKShare替代Tushare，而是作为第二数据源能力保留。

# 11. 多数据源带来的架构要求

既然项目已经明确存在：

```text
Tushare
AKShare
```

后续数据架构不能把业务逻辑直接绑定到Tushare字段结构。

采集架构需要形成：

```text
数据源
   ↓
数据源适配
   ↓
原始数据
   ↓
标准化/清洗
   ↓
统一数据模型
```

例如：

```text
Tushare日线
        ↓
        ├──→ 标准A股日线
        ↑
AKShare日线
```

这样以后增加第三个数据源时，不需要重写整个量化平台。

具体标准数据模型进入总体设计阶段设计。

# 14. 后续QMT接入必须保持系统边界

未来接入QMT时，应保持：

```text
策略判断
↓
信号
↓
交易计划
↓
风险检查
↓
交易执行
```

交易执行不能直接嵌入数据采集或策略计算程序。

QMT属于：

```text
执行层资源
```

而不是：

```text
数据层
策略层
```

这样才能保持：

- 策略研究与实盘隔离；
- 回测与实盘隔离；
- 自动交易可独立启停；
- 风险控制可插入；
- 后续替换券商接口时不影响策略主体。

# 17. 当前主要资源风险

## 16.1 单人维护

所有关键知识和操作集中在一个人。

因此系统必须降低人工维护依赖。

## 16.2 单服务器

svr3同时承担：

```text
开发
测试
正式
```

属于单点资源。

## 16.3 开发与正式环境混用

后续必须建立逻辑隔离和部署边界。

## 16.4 数据源依赖

Tushare存在：

- 权限限制；
- 调用频率限制；
- 单次返回量限制。

AKShare存在公开网站接口稳定性风险。

因此平台必须支持：

```text

限流
重试
断点续采
数据校验
```

## 16.5 AI开发任务长时间运行

OpenCode可能执行长时间开发任务。

这类开发任务不能与正式量化任务争抢全部计算资源。

后续需要明确开发任务的运行边界。

# 19. 对下一阶段的影响

```text
业务目标
+
数据资源
+
计算资源
+
软件技术资源
```

下一步应进行：

```text

```

重点回答：

1. 当前权限范围内历史数据大约需要多少存储；
2. 1分钟数据需要多少空间；
3. 每天新增数据量大约多少；
4. 2TB NVMe数据盘是否足够；
5. 现有4核CPU是否能在合理时间内完成首次全量采集和日常增量；
6. PostgreSQL / TimescaleDB需要怎样规划容量。
