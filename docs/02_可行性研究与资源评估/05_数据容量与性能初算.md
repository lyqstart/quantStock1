# 数据容量与性能初算

> 文档阶段：P1 可行性研究与资源评估  
> 项目：A股量化研究与信号决策平台  
> 核查时间：2026-07-27  
> 依据：svr3实际数据库、磁盘、TimescaleDB状态和Tushare接口限制

---

# 1. 分析目的

本文件用于回答以下问题：

1. 当前quantstock数据库已经占用多少空间；
2. 当前2TB NVMe数据盘还剩多少安全容量；
3. A股分钟数据的年增量大约有多大；
4. raw、clean双层保存后容量压力有多大；
5. 当前1TB备份盘是否足够；
6. 4核CPU、64GB内存、NVMe是否能够支撑第一阶段；
7. 后续总体设计必须解决哪些容量和性能问题。

本阶段属于可行性初算，不替代后续真实压力测试。

---


# 重要边界：776GB属于旧quantStock遗留数据库

本次测得的：

```text
quantstock数据库 = 776GB
```

属于svr3上仍在运行的旧quantStock项目，不是新quantStock1已经产生的数据。

因此这776GB在本项目中的意义是：

1. 证明真实A股历史数据和现有存储模型会产生很大的空间占用；
2. 提供实际每行、索引、TimescaleDB chunk和压缩效果的容量参考；
3. 其中已经下载的历史数据可能成为新项目的重要可复用资产；
4. 同时它已经占用了2TB NVMe的大量空间，会直接限制新项目可用容量。

新项目不能直接把旧数据库作为正式数据库继续使用。

历史数据应采用：

```text
旧数据库只读
↓
盘点
↓
质量验证
↓
迁移
↓
新项目独立存储
```

# 12. 历史分钟全量压力

Tushare历史分钟权限覆盖长期历史数据。

如果为了做容量极限判断，使用“当前5600只股票规模”反推18年历史，这是一个明显偏大的压力上界，因为早期A股股票数量远少于现在。

即便如此，该上界有助于判断磁盘是否可能无限存储。

## 只保存1分钟，raw + clean

上界约：

```text
5TB以上
```

## 五种频率全部保存，raw + clean

上界约：

```text
6.7TB以上
```

这不是实际历史数据量预测，而是压力上界。

结论非常明确：

> 当前2TB数据盘不能支持“所有分钟频率、全部历史、raw和clean长期完整双份、永不归档”的存储模式。

因此后续必须做生命周期和压缩设计。

# 13. Raw压缩的实际意义

当前：

```text
raw.stk_mins
compression_enabled = true
```

因此raw分钟数据实际占用会低于上述未压缩计算。

但是：

```text
clean.stk_mins
compression_enabled = false
```

同时：

- raw和clean都存在大量chunk；
- 数据库已经达到776GB。

所以不能因为raw已压缩就认为当前存储不存在风险。

后续必须实际测量：

```text
raw.stk_mins压缩前容量
raw.stk_mins压缩后容量
压缩比
clean.stk_mins真实容量
```

并据此确定最终生命周期策略。

# 24. 当前规模一年1分钟数据的理论最低请求量

一年1分钟数据：

```text
325,248,000行
```

如果每次都恰好拿满8000行：

```text
至少约40,656次请求
```

按500次/分钟理论上限：

```text
理论最低约81分钟
```

但真实运行一定更慢。

原因包括：

- 必须按股票拆分；
- 必须按时间窗口拆分；
- 很多请求不会正好返回8000行；
- 网络延迟；
- API响应时间；
- 数据解析；
- PostgreSQL写入；
- 索引维护；
- 去重；
- 数据质量检查；
- clean处理。

因此：

> 不能用81分钟作为实际一年数据采集时间。

它只能证明API频率上限本身不是唯一瓶颈。

# 26. 4核CPU是否足够

## 日常增量

结论：

```text
足够
```

原因：

- 当前系统已经长期运行采集、清洗和API服务；
- 日常新增只处理当天数据；
- 64GB内存充足；
- 数据库位于NVMe。

## 首次全量历史初始化

结论：

```text
有限具备
```

能够完成，但必须：

- 分批；
- 可暂停；
- 可恢复；
- 限制并发；
- 与正式日常任务错峰；
- 不追求短时间暴力跑完。

## 大规模并行回测/机器学习

当前：

```text
4核4线程
```

不是高并发计算资源。

后续如果研究和回测规模上升，再单独扩展计算资源。

# 27. 当前最重要的性能瓶颈判断

本阶段证据表明，第一阶段主要风险优先级是：

```text
1. 存储容量
2. 数据重复保存
3. 分钟数据索引容量
4. 压缩与生命周期
5. 数据库写入和维护
6. CPU
```

也就是说：

> 当前最先需要解决的不是CPU升级，而是数据存储模型。

---

# 28. 对后续总体设计的强制约束

后续总体设计必须解决以下问题。

## 28.1 Raw和Clean不能无限双份扩张

需要明确：

- 哪些数据raw永久保存；
- 哪些raw压缩；
- clean保存多久；
- 哪些频率可以由低周期聚合得到；
- 是否所有频率都必须raw和clean双份长期保留。

---

## 28.2 分钟数据必须使用TimescaleDB能力

继续利用：

- Hypertable；
- 时间分区；
- 压缩；
- Chunk生命周期；
- 合理索引。

不能把数十亿分钟记录当成普通小型PostgreSQL表管理。

---

## 28.3 高频数据必须和普通业务数据区别治理

建议逻辑上分为：

```text
高容量时间序列
    stk_mins

普通行情
    daily
    daily_basic
    adj_factor
    moneyflow

财务和事件
    income
    balancesheet
    dividend
    shareholder
    event

系统数据
    tasks
    logs
    audit
```

不同类型不能使用相同生命周期策略。

数据库所在盘不能持续写到接近100%。

后续系统必须设置：

```text
磁盘预警
数据库容量预警
分钟数据增长速度监控
```

## 28.5 必须重新设计备份容量

当前：

```text
数据库776GB
备份盘剩余768GB
```

已经没有足够安全余量。

后续必须在以下方向中选择方案：

- 扩大备份盘；
- 增加新的备份存储；
- 压缩逻辑备份；
- 分层备份；
- 远端/对象存储；
- 历史数据冷存储。

具体方案进入总体设计和运维设计阶段确定。

| 资源 | 状态 | 判断 |
|---|---|---|
| CPU | 有限具备 | 日常采集足够，全量和大规模回测需控制并发 |
| 内存 | 已具备 | 64GB满足第一阶段 |
| NVMe性能 | 已具备 | 当前数据库已稳定运行 |
| 数据盘当前运行 | 已具备 | 尚有1.1TB可用 |

| 首次全量能力 | 有限具备 | 需要分批、错峰、可恢复 |
| 大规模并行回测 | 有限具备 | 4核CPU形成约束 |

# 30. P1.5结论

## 结论一

当前quantstock数据库已经达到：

```text
776GB
```

数据容量已经不是未来问题，而是当前必须纳入架构设计的问题。

## 结论二

2TB NVMe当前还能继续使用：

```text
剩余约1.1TB
```

但不能作为所有历史分钟数据长期无限扩张的最终存储方案。

## 结论三

按当前市场规模压力估算：

```text
1分钟
约3.25亿行/年

全部五种分钟频率
约4.28亿行/年
```

分钟数据是第一容量风险。

## 结论四

按当前数据库实际存储效率约470字节/行估算：

```text
全部分钟频率
raw + clean
未压缩规划值约375GiB/年
```

所以必须依靠：

```text
压缩
生命周期
去重复存储
归档
```

控制长期增长。

## 结论五

当前raw分钟已经压缩，但clean分钟未压缩。

这是后续存储设计必须重点处理的问题。

## 结论六

当前1TB备份盘已经不能安全覆盖当前776GB数据库的完整物理备份需求。

备份资源需要补充或重新设计。

## 结论七

当前4核CPU、64GB内存、NVMe：

```text
可以支撑日常数据采集和清洗
```

首次全量历史初始化：

```text
可以做
但必须批处理、限并发、断点续传、错峰执行
```

## 结论八

当前最紧迫的资源问题不是升级CPU，而是：

```text
数据库容量
+
分钟数据存储策略
+
备份容量
```

# 32. 对P2总体设计的输入

进入总体设计后，必须把以下事实作为硬约束：


# 33. 遗留历史数据的容量策略

旧quantStock已经下载的大量历史数据具有明显复用价值。

但复用前必须把数据分为：

```text
可直接迁移
需要重新清洗后迁移
只能作为校验参考
应重新从Tushare采集
```

判断依据至少包括：

- 来源接口；
- 字段完整性；
- 时间范围；
- 是否存在重复；
- 是否存在缺口；
- 是否保留原始版本；
- 财务数据是否保留公告时间和修订版本；
- 分钟数据频率和时间边界是否正确；
- 是否能够追溯到来源。

在完成验证前：

```text
旧数据 != 新项目正式可信数据
```

如果验证通过，应优先迁移可用历史数据，减少重复下载时间和Tushare调用量。

迁移后必须记录：

```text
source_system = legacy_quantstock
migration_batch_id
legacy_table
legacy_record_key / legacy_hash
import_time
validation_status
```

旧数据库不作为新项目长期在线依赖。
