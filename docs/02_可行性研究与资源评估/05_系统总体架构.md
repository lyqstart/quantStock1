# 系统总体架构

> 路线图阶段：P2.3 总体系统架构
> 项目：A股量化研究与信号决策平台
> 形成日期：2026-07-29
> 状态：已确认
> 当前仓库基线：`b365afd`
> 适用范围：V1总体架构，并为V2、V3保留稳定扩展边界

## 1. 架构结论

quantStock1采用：

```text
模块化单体
+
按运行角色分进程
+
一个主业务数据库
+
数据库任务队列
+
文件归档与备份
```

V1核心运行角色：

```text
API
Scheduler
Data Worker
Research Worker
PostgreSQL + TimescaleDB
```

其中：

- 当前已运行的是API、Scheduler、统一Worker和PostgreSQL/TimescaleDB；
- Data Worker和Research Worker来自同一代码库、同一领域模型和同一发布版本；
- 当前统一Worker可继续运行数据任务；
- 研究、特征和回测能力进入实施时，再按任务类型启动Research Worker；
- Worker角色拆分是运行隔离，不是微服务拆分；
- Scheduler只负责创建到期任务，不处理业务数据；
- PostgreSQL保存全部正式业务状态；
- 文件系统只保存归档、备份、导出和大文件制品，不替代业务数据库。

V1不采用：

```text
微服务群
Kubernetes
Celery核心队列
Redis核心状态
Kafka
RabbitMQ
Spark
Hadoop
Elasticsearch核心依赖
多数据库分片
```

## 2. 设计依据

P1已经确认：

- 当前为单用户自用研究平台；
- V1不开放公网、不对外服务、不自动下单；
- `svr3` Docker可见4 CPU、约62 GiB内存；
- 当前应用运行API、Worker、Scheduler和PostgreSQL/TimescaleDB；
- 当前数据库逻辑约78 MiB，仍属于样本规模；
- 全市场分钟数据是主要容量压力；
- 数据库当前位于系统盘；
- 备份恢复、监控告警和生产安全边界尚未完成。

P2.1已经确认：

- V1完成研究、回测、风控、信号和人工决策闭环；
- V2建设实时、模拟和交易桥接验证；
- V3在单独批准后建设受控实盘和高级自动化。

P2.2已经确认：

- 稳定对象与不可变版本分离；
- 业务目标与执行实例分离；
- 正式结果不可覆盖；
- 领域表保存直接引用；
- Lineage支持跨模块追溯；
- AuditEvent记录状态变化。

因此当前架构优先级为：

```text
正确
>
可恢复
>
可追溯
>
可维护
>
性能
>
分布式扩展
```

## 3. 总体逻辑架构

```text
┌───────────────────────────────────────────────┐
│                  用户与AI协同                  │
│ Web工作台 / API客户端 / AI工具 / 运维入口      │
└──────────────────────┬────────────────────────┘
                       │
                       ▼
┌───────────────────────────────────────────────┐
│                 应用接口层                     │
│ API / 身份 / 权限 / DTO / 命令 / 查询 / 追溯   │
└──────────────────────┬────────────────────────┘
                       │
                       ▼
┌───────────────────────────────────────────────┐
│                 应用编排层                     │
│ 数据任务 / 研究任务 / 回测 / 风控 / 信号流程    │
└──────────────────────┬────────────────────────┘
                       │
                       ▼
┌───────────────────────────────────────────────┐
│                 领域模块层                     │
│ Catalog / Collect / Clean / Quality / Lineage │
│ Query / Feature / Analysis / Pool / Strategy  │
│ Backtest / Risk / Signal / Decision / Ops     │
└───────────────┬───────────────────────┬───────┘
                │                       │
                ▼                       ▼
┌──────────────────────────┐  ┌──────────────────────────┐
│ 数据源与外部适配层         │  │ 基础设施层                │
│ Tushare / Legacy Import   │  │ PostgreSQL / TimescaleDB │
│ V2实时与券商适配预留       │  │ 文件归档 / 日志 / 备份      │
└──────────────────────────┘  └──────────────────────────┘
```

依赖方向必须从上向下。

底层模块不得反向依赖API、页面或具体AI模型。

## 4. 模块化单体边界

建议应用代码按以下业务边界组织：

```text
core
identity
catalog
datasource
collection
raw
clean
quality
lineage
query
feature
analysis
pool
strategy
research_task
backtest
risk
signal
decision
execution
ops
audit
migration
api
```

### 4.1 core

只保存通用基础能力：

- 配置；
- 时间；
- ID；
- 数据库事务；
- 错误基类；
- 日志上下文；
- 环境标识；
- 安全工具。

禁止把业务逻辑集中到core。

### 4.2 catalog和datasource

负责：

- DataSource；
- DataItem；
- SourceBinding；
- StoragePolicy；
- 数据源适配器；
- 能力状态；
- 接口配置。

上层模块依赖DataItem，不依赖Tushare接口名称。

### 4.3 collection、raw、clean和quality

负责完整数据接入链：

```text
CollectTask
↓
CollectRun
↓
RequestSlice
↓
SliceAttempt
↓
RawBatch
↓
CleanBatch
↓
QualityRun
↓
正式发布
```

### 4.4 lineage

负责：

- 批次关系；
- 对象上下游；
- trace查询；
- 影响分析；
- 状态历史聚合。

Lineage不代替领域表中的直接引用。

### 4.5 query

负责统一DataContext和DataSnapshot读取。

上层研究、策略、回测、前端和AI禁止直接查询RAW。

### 4.6 feature、analysis和pool

负责公共研究资产：

- 定义；
- 版本；
- 运行；
- 结果；
- 依赖；
- 股票池快照。

### 4.7 strategy、research_task和backtest

负责：

- StrategyDefinition；
- StrategyImplementation；
- StrategyVersion；
- ResearchTaskRun；
- BacktestRun；
- 交易成本和复现信息。

### 4.8 risk、signal和decision

负责：

```text
TradePlan
↓
RiskEvaluation
↓
Signal
↓
UserDecision
```

V1到UserDecision结束，不产生真实订单。

### 4.9 execution

V1只保留接口边界和对象命名，不启用真实执行。

V2、V3再增加：

- Account；
- ExecutionIntent；
- Order；
- Fill；
- Position；
- Reconciliation。

### 4.10 ops、audit和migration

负责：

- Scheduler；
- Worker；
- 任务Lease；
- 健康状态；
- 运行控制；
- AuditEvent；
- 旧quantStock只读迁移。

## 5. 模块依赖规则

### 5.1 数据依赖

```text
DataSource
→ RAW
→ CLEAN
→ DataContext
→ Feature / Analysis
→ Pool
→ Strategy / Backtest
→ TradePlan
→ Risk
→ Signal
→ UserDecision
```

禁止跨层倒置。

### 5.2 直接数据库访问

每个模块通过自己的Repository访问所属表。

禁止：

- 策略直接拼接RAW SQL；
- API直接操作业务表；
- Feature绕过DataContext；
- Signal直接创建Order；
- AI直接连接数据库。

### 5.3 模块间调用

同一进程内优先使用明确的Python接口和DTO。

不为模块之间增加HTTP调用。

只有出现独立部署事实后，才将某模块拆成网络服务。

## 6. 运行角色

## 6.1 API

职责：

- 用户和系统接口；
- 查询；
- 创建命令；
- 参数校验；
- 权限；
- 状态展示；
- 追溯；
- 前端接口；
- AI受控工具接口。

API不得：

- 执行历史全量采集；
- 执行大规模清洗；
- 运行特征全量计算；
- 运行回测；
- 长时间占用请求线程；
- 直接调用券商下单。

长任务统一创建正式任务后返回任务ID。

## 6.2 Scheduler

Scheduler只回答：

```text
什么时候创建什么任务
```

职责：

- 交易日历驱动；
- 数据可用时间驱动；
- 周期任务；
- 延迟任务；
- 维护任务；
- 超时任务扫描；
- 任务补偿创建。

Scheduler不得处理业务数据，不维护唯一进程内状态。

多实例时必须通过数据库Leader Lease避免重复调度。

## 6.3 Data Worker

执行：

- 采集；
- RAW写入；
- 清洗；
- 质量校验；
- 补采；
- 重洗；
- 迁移；
- 归档；
- 数据维护。

当前统一Worker可作为Data Worker继续运行。

## 6.4 Research Worker

在V1研究能力实施时启动。

执行：

- DataSnapshot；
- Feature；
- Analysis；
- StockPool；
- Strategy；
- Backtest；
- TradePlan；
- Risk；
- Signal生成。

Research Worker和Data Worker：

- 使用同一代码版本；
- 使用不同任务类型；
- 使用不同并发上限；
- 使用不同资源限制；
- 使用不同任务优先级；
- 可以独立暂停和扩容。

## 6.5 前端

前端是API客户端，不访问数据库。

P2.3固定边界：

```text
Browser
→ 统一Web入口
→ API
→ 应用服务
```

当前仓库没有足够证据锁定React、Vue或其他前端框架。

前端框架在P10详细设计时选定，不影响当前后端和API边界。

## 6.6 AI协同

AI通过正式API或工具契约访问平台。

必须继承当前用户权限。

AI不能：

- 直接访问数据库；
- 直接变更正式状态；
- 绕过风控；
- 直接下单；
- 成为API、Scheduler或Worker运行依赖。

## 7. 任务架构

V1任务队列采用PostgreSQL。

```text
API / Scheduler
↓
创建Task
↓
PostgreSQL
↓
Worker原子领取
↓
Lease + Heartbeat
↓
执行
↓
Run / Batch / Audit / Lineage
```

任务领取应使用数据库原子并发控制，例如：

```text
FOR UPDATE SKIP LOCKED
```

或现有等价实现。

必须具备：

- 幂等键；
- 优先级；
- 任务类型；
- 环境；
- 所有者；
- Lease；
- 心跳；
- 超时；
- 重试；
- 取消；
- Checkpoint；
- 失败原因；
- trace_id。

不使用进程内队列保存唯一任务事实。

## 8. 在线服务与重任务隔离

隔离原则：

```text
API低延迟查询
≠
大规模数据与研究计算
```

实施方式：

1. API和Worker使用独立容器；
2. Data Worker和Research Worker使用独立容器角色；
3. 配置独立并发上限；
4. 容器配置CPU和内存限制；
5. 数据任务优先保证日常增量和质量；
6. 回测和全量特征默认低优先级；
7. 大任务可暂停、取消和分片；
8. 查询设置超时；
9. 临时文件设置独立目录和容量限制。

## 9. 数据库架构

主数据库：

```text
PostgreSQL 16
+
TimescaleDB
```

目标Schema：

```text
meta
raw
clean
quality
lineage
research
decision
execution
ops
audit
migration
```

当前已存在：

```text
meta
raw
clean
quality
ops
audit
```

当前 `lineage` 尚无正式表。

### 9.1 普通PostgreSQL表

用于：

- 定义；
- 版本；
- 任务；
- 批次；
- 财务；
- 事件；
- 股票池；
- 策略；
- 回测元数据；
- 风控；
- 信号；
- 决策；
- 审计。

### 9.2 TimescaleDB

用于高容量时间序列：

- CLEAN 1分钟行情；
- 后续经验证适合的高频时序结果。

不要求所有行情、财务和事件表都使用Hypertable。

### 9.3 数据库是正式事实源

以下对象必须持久化：

- 任务状态；
- 运行状态；
- 对象版本；
- 质量结果；
- 数据水位；
- Lineage；
- 审计；
- 用户决策；
- 未来订单和成交。

Redis、内存和日志不能替代正式数据库。

## 10. 文件存储架构

V1文件存储只用于：

- RAW历史归档；
- 数据导出；
- 回测大制品；
- 报告；
- 数据库备份；
- 配置备份；
- 迁移证据；
- 校验清单。

每个文件制品至少保存：

```text
artifact_id
object_type
object_id
path
format
size
checksum
created_at
retention_class
encryption_status
```

V1先使用服务器受控文件目录。

出现多节点、远程灾备或大量对象存储需求后，再引入S3兼容对象存储。

## 11. 缓存架构

V1没有共享缓存强依赖。

允许：

- API进程内短期只读缓存；
- 不影响正确性的元数据缓存；
- 明确TTL；
- 缓存失效后重新读取数据库。

禁止缓存：

- 唯一任务状态；
- 风控正式结果；
- 信号正式状态；
- 用户决策；
- 数据质量发布状态。

出现实际查询瓶颈后，可以引入Redis作为：

- 只读查询缓存；
- 短期会话；
- Pub/Sub；
- 非正式临时状态。

Redis仍不能成为业务事实源。

## 12. API边界

统一接口前缀建议：

```text
/api/v1
```

API输入输出使用DTO，不直接暴露ORM模型。

接口分为：

```text
Command
Query
Admin
Trace
Health
```

长任务接口模式：

```text
POST 创建任务
↓
返回task_id
↓
GET查询状态
↓
GET查询结果
```

后续对外开放接口必须复用同一权限、审计和应用服务，不能旁路内部规则。

## 13. 数据访问与DataContext

上层模块必须通过统一查询服务读取：

```text
CLEAN
Feature
Analysis
```

DataContext至少约束：

- as_of_time；
- available_at_cutoff；
- 股票范围；
- 市场范围；
- 频率；
- 复权；
- 数据版本；
- 质量策略；
- 环境。

回测不得读取当前最新版替代历史可见版本。

## 14. Lineage和审计

追溯采用：

```text
领域表直接外键
+
lineage_edge
+
AuditEvent
```

领域表是直接关系事实。

lineage_edge用于跨模块遍历。

AuditEvent记录状态变化和操作。

禁止三者互相替代。

## 15. 多用户和权限预留

V1为单用户。

所有新核心对象仍需预留：

```text
owner_user_id
created_by
workspace_id
visibility
environment_id
```

API层建立身份上下文。

V1不建设复杂组织和租户系统。

V2需要多人协作时，在现有归属字段上增加权限策略，不重做全部对象。

## 16. V2、V3扩展边界

### 16.1 实时数据

实时行情通过新的SourceAdapter进入。

历史和实时数据统一进入DataContext，不让策略分别维护两套数据语义。

### 16.2 券商桥接

券商接口通过ExecutionAdapter。

研究、风控和信号模块不直接依赖QMT或券商SDK。

### 16.3 自动执行

V3增加Execution Worker或Bridge进程。

只有出现真实接入和可靠性要求后才单独部署。

## 17. 旧quantStock边界

旧quantStock定位：

```text
只读历史来源
+
经验参考
```

唯一允许的正式连接：

```text
LegacyMigrationBatch
```

禁止：

- 新系统在线查询旧库作为正式数据；
- 新系统调用旧API；
- 新系统依赖旧Redis；
- 新系统复用旧任务状态；
- 直接复制整个旧数据库；
- 让旧系统决定新系统业务规则。

## 18. 扩展顺序

应用扩展：

```text
单API
+
单Scheduler
+
单Data Worker
+
单Research Worker
↓
同角色增加实例
↓
按任务类型增加Worker池
↓
独立计算节点
↓
确有必要时拆服务
```

存储扩展：

```text
单PostgreSQL/TimescaleDB
↓
数据库移出系统盘
↓
压缩与归档
↓
读写和计算优化
↓
独立存储节点
```

不提前采用最终复杂形态。

## 19. 禁止架构

V1禁止：

- 为每个模块建立独立服务；
- 为内部模块建立HTTP调用链；
- 同时使用多套任务队列；
- 使用Redis保存正式状态；
- 使用日志代替状态和审计；
- API直接执行长任务；
- 研究代码直接访问RAW；
- AI直接写数据库；
- 前端直接访问数据库；
- dev/test连接prod数据库；
- 直接复制旧quantStock运行架构。

## 20. P2.3结论

系统总体架构确定为：

```text
模块化单体
+
API / Scheduler / Data Worker / Research Worker
+
PostgreSQL任务队列
+
PostgreSQL 16 / TimescaleDB
+
受控文件存储
+
统一DataContext
+
Lineage与Audit
```

当前API、Scheduler、统一Worker和数据库继续作为现状基础。

Research Worker、前端、Lineage正式表和上层研究模块属于后续实施目标，不得写成当前已实现能力。
