> 路线图阶段：P2.3 总体系统架构

> 形成日期：2026-07-29
> 状态：已确认
> 当前仓库基线：`b365afd`
> 配套文档：`05_系统总体架构.md`

## 1. 选型原则

技术选择按以下顺序判断：

```text
满足业务正确性
↓
符合现有真实环境
↓
单人能够长期维护
↓
故障后能够恢复
↓
能够形成证据和追溯
↓
性能满足阶段目标
↓
未来能够按需扩展
```

不以技术流行度决定选型。

## 3. Python 3.11

选择原因：

- 当前应用已在Python 3.11.15运行；
- Tushare、Pandas、SQLAlchemy、FastAPI等依赖已验证；
- 避免宿主机Python版本差异；
- 容器内可以统一版本。

要求：

- 所有应用角色使用同一Python主次版本；
- 统一基础镜像；
- 依赖锁定；
- 不依赖宿主机Python；
- 升级通过测试环境验证。

当前不主动升级到新的Python主版本。

## 4. FastAPI和Uvicorn

FastAPI用于：

- 管理API；
- 查询API；
- 任务创建；
- 状态；
- 追溯；
- 前端后端接口；
- AI受控工具接口。

选择原因：

- 当前已运行；
- 与Pydantic 2和Python类型系统一致；
- 单人维护成本较低；
- 支持同步和异步接口；
- OpenAPI便于前端和AI理解。

限制：

- API不得直接执行重任务；
- 不把领域逻辑写入路由；
- 不直接暴露数据库模型；
- 不依赖API进程内状态。

## 5. Pydantic 2

用于：

- API DTO；
- 配置；
- 外部接口响应校验；
- 任务参数；
- 规则配置；
- 结构化策略定义。

禁止用Pydantic模型替代数据库正式对象和版本记录。

## 6. SQLAlchemy 2和psycopg 3

SQLAlchemy用于：

- Repository；
- 事务；
- 普通业务查询；
- 数据库模型；
- 数据迁移配合。

复杂批量写入、TimescaleDB管理和性能敏感SQL允许使用明确的SQL。

原则：

```text
ORM不是禁止SQL
SQL也不能绕过业务规则
```

选择psycopg 3，避免同时维护psycopg2和psycopg3两套驱动。

## 7. Alembic

所有Schema变更通过Alembic。

要求：

- 迁移文件进入Git；
- 迁移不可依赖人工临时SQL；
- 升级前备份；
- 测试环境预演；
- 明确回滚或前向修复方式；
- 大表迁移单独评估锁和空间；
- 数据迁移与结构迁移区分。

## 8. PostgreSQL 16

选择原因：

- 当前已运行16.14；
- 同时支持关系对象、JSON元数据、事务、锁、索引和任务队列；
- 适合任务、版本、质量、审计和用户决策；
- 单数据库降低维护复杂度；
- 支持P2.2对象和追溯模型。

PostgreSQL是：

```text
正式业务状态源
任务状态源
对象版本源
审计源
```

不增加MySQL等第二业务数据库。

## 9. TimescaleDB

用于高容量时序数据。

当前明确用途：

- CLEAN 1分钟行情；
- 经真实基准证明适合的高频结果。

选择原因：

- 当前已运行2.28.3；
- 当前分钟表已建立Hypertable；
- 与PostgreSQL统一事务、权限、备份和查询；
- 避免第一阶段引入独立时序数据库。

限制：

- 不把所有表改成Hypertable；
- chunk、压缩和保留策略必须实测；
- 不使用官方示例压缩率作为承诺；
- 大规模分钟数据先迁出系统盘。

## 10. PostgreSQL任务队列

V1采用数据库任务队列。

选择原因：

- 当前已有Task、Run、Slice、Attempt、Lease和Worker状态；
- 单服务器和低并发；
- 任务事实天然持久化；
- 无需Redis和Celery双重状态；
- 容易追溯和恢复；
- 事务内可以同时创建任务和业务状态。

必须具备：

- 原子领取；
- Lease；
- Heartbeat；
- 超时回收；
- 幂等；
- 重试；
- 优先级；
- Checkpoint；
- LOST识别；
- 任务分片。

退出条件：

只有在真实基准证明数据库任务队列不能满足吞吐、延迟或多节点需求时，才评估外部队列。

## 11. 不采用Celery

V1不采用Celery。

原因：

- 当前没有多服务器高吞吐任务需求；
- Scheduler、Celery Beat和数据库任务容易职责重叠；
- Redis和Celery会增加运行、升级和故障面；
- 当前数据库任务模型已经形成；
- 单人维护优先。

未来若引入外部队列，仍需保持PostgreSQL是业务任务事实源。

## 12. Redis边界

V1不依赖Redis运行。

未来仅在出现实际需求时用于：

- 查询缓存；
- 短期会话；
- Pub/Sub；
- 分布式限流；
- 大量短生命周期状态。

Redis不得保存：

- 唯一任务状态；
- 正式质量结论；
- 风控正式结果；
- 信号状态；
- 用户决策；
- 订单正式状态。

## 13. Pandas、NumPy和PyArrow

Pandas和NumPy用于：

- 外部数据解析；
- 批量转换；
- 特征计算；
- 研究和回测。

PyArrow/Parquet用于：

- 历史RAW归档；
- 数据交换；
- 大制品；
- 列式压缩；
- 离线迁移。

限制：

- 不把整个全市场历史数据一次性加载到内存；
- 任务按股票、日期、批次分片；
- 中间DataFrame有明确生命周期；
- 大结果优先流式或分批写入；
- Parquet不是正式任务状态库。

## 14. Docker和Docker Compose

当前服务器已验证：

```text
Docker 26.1.3
Docker Compose 2.27.0
```

V1继续使用。

要求：

- 使用 `docker compose`；
- 固定镜像版本；
- 生产镜像由Git提交构建；
- API、Scheduler和Worker尽量使用同一应用镜像；
- 数据库使用明确版本；
- 不使用浮动latest标签；
- 服务有健康检查；
- 设置资源限制；
- 设置日志轮转；
- 配置和密钥外置；
- 数据卷路径明确。

## 15. Nginx边界

当前API只绑定：

```text
127.0.0.1:18000
```

V1需要浏览器或局域网访问时，使用Nginx或等价反向代理作为唯一入口。

负责：

- 静态前端；
- API反向代理；
- TLS；
- 请求大小；
- 超时；
- 安全头；
- 访问日志；
- 来源网络限制。

API容器不直接暴露公网。

## 16. 前端技术决策

P2.3只确定：

```text
独立Web客户端
+
REST/JSON API
+
统一Web入口
```

不在证据不足时锁定React、Vue或其他框架。

P10选型必须比较：

- 工作台复杂度；
- 图表；
- 表格；
- 长任务状态；
- 追溯图；
- 维护成本；
- 构建和升级成本；
- 移动端后续边界。

前端框架不应影响领域对象和API契约。

## 17. 测试技术

确认：

- pytest；
- 单元测试；
- 数据库集成测试；
- Alembic迁移测试；
- API契约测试；
- 数据质量测试；
- 端到端验收脚本。

数据库相关功能不能只用Mock证明。

关键任务必须在真实PostgreSQL/TimescaleDB测试环境验证。

## 18. 依赖和制品治理

必须：

- 锁定依赖版本；
- 保存锁文件；
- 记录应用版本；
- 记录Git提交；
- 记录数据库迁移版本；
- 记录镜像Digest；
- 同一发布使用同一应用镜像；
- 禁止部署时临时安装未知新版本。

OpenCode生成的代码必须先进入Git、测试和发布流程，不能直接进入运行容器。

## 19. 日志、指标和审计

日志：

```text
结构化stdout/stderr
```

容器负责收集和轮转。

业务状态和AuditEvent进入PostgreSQL。

P2.4再确定：

- 指标；
- 告警阈值；
- 保留周期；
- RTO；
- RPO；
- SLA或非SLA目标。

日志不得保存Token、密码和完整连接串。

## 20. 文件与对象存储

V1选择受控文件目录，不引入MinIO或其他对象存储。

原因：

- 当前单服务器；
- 当前单用户；
- 当前文件规模可通过目录管理；
- 减少一个长期运行组件。

文件必须有：

- 元数据记录；
- Checksum；
- 所有者；
- 生命周期；
- 备份状态。

出现多节点、异机归档和大量对象访问后再引入对象存储。

## 21. 暂不采用的技术

| 技术 | V1决定 | 原因 |
|---|---|---|
| Kubernetes | 不采用 | 单服务器和少量进程 |
| 微服务 | 不采用 | 单人维护，领域仍在建设 |
| Kafka | 不采用 | 无事件吞吐证据 |
| RabbitMQ | 不采用 | 数据库队列可满足 |
| Celery | 不采用 | 避免双重任务状态 |
| Redis核心依赖 | 不采用 | 无必要证据 |
| Spark/Hadoop | 不采用 | 4 CPU单机不匹配 |
| Elasticsearch | 不采用 | 当前无全文检索瓶颈 |
| ClickHouse | 不采用 | 现有PostgreSQL/TimescaleDB尚未证明不足 |
| MySQL | 不采用 | 不增加第二业务数据库 |
| MinIO | 不采用 | 单机文件存储足够V1 |
| Graph数据库 | 不采用 | Lineage可由关系表实现 |
| 通用工作流引擎 | 不采用 | 当前任务模型足够 |
| Notebook作为正式运行平台 | 不采用 | 不利于版本、调度和审计 |

## 22. 技术引入门禁

新技术必须同时回答：

1. 解决哪个已确认问题；
2. 现有技术为什么不能解决；
3. 增加哪些运行组件；
4. 增加哪些故障模式；
5. 如何备份和恢复；
6. 谁维护；
7. 如何测试；
8. 如何退出或替换。

没有真实问题，不增加新技术。

## 23. P2.3技术结论

V1技术基线确定为：

```text
Python 3.11
FastAPI / Uvicorn
Pydantic 2
SQLAlchemy 2 / psycopg 3
Alembic
PostgreSQL 16
TimescaleDB
Pandas / NumPy / PyArrow
Docker / Docker Compose
PostgreSQL任务队列
受控文件存储
```

Redis、Celery、对象存储、消息总线、微服务和Kubernetes不作为V1核心技术。

前端框架推迟到P10，接口和部署边界已经固定。
