## 2. 目标环境层级

采用四个环境身份：

```text
local-dev
server-test
server-stable
legacy
```

未来需要正式生产时，`server-stable`经过P2.4和P10验收后可以升级为：

```text
prod
```

环境身份不是随意字符串，必须进入配置、数据库对象和审计。

## 3. local-dev

位置：

```text
用户本地Windows
```

用途：

- OpenCode开发；
- 代码检查；
- 单元测试；
- 小规模数据库测试；
- 文档；
- Docker构建；
- 迁移生成；
- 本地接口调试。

数据：

- 模拟数据；
- 小样本；
- 脱敏样本；
- 不使用正式Token时可以使用Mock或受控测试Token。

禁止：

- 把本地数据库当作正式状态；
- 从本地直接连接稳定数据库执行开发；
- 把密钥提交Git；
- 在本地自动启动OpenCode以外的高风险生产操作。

## 4. server-test

位置：

```text
svr3逻辑隔离环境
```

用途：

- Docker镜像验证；
- Alembic迁移预演；
- PostgreSQL/TimescaleDB集成测试；
- API、Scheduler、Worker联调；
- 数据质量验证；
- 性能小样本；
- 备份恢复演练；
- 发布候选验收。

特点：

- 需要时启动；
- 使用独立数据库；
- 使用独立端口；
- 使用独立网络；
- 使用小样本；
- 不复制完整分钟历史；
- 不运行长期正式调度；
- 不写server-stable数据库。

## 5. server-stable

位置：

```text
svr3逻辑稳定运行环境
```

用途：

- 当前单用户正式研究数据；
- 日常增量；
- 稳定API；
- 稳定Scheduler；
- Data Worker；
- 后续Research Worker；
- 备份；
- 监控；
- V1验收。

进入条件：

- P2.4非功能目标确认；
- 数据库从系统盘迁移方案确认；
- 备份和恢复通过；
- 网络和密钥边界处理；
- 日志和监控完成；
- 发布和回滚流程完成；
- 当前P0风险关闭或批准。

在上述条件完成前，只能称为当前运行或验证环境。

```text

数据库

端口

```

建议Compose项目名：


当前已有 `quantstock1-dev` 命名，应在正式环境治理时决定保留为test还是迁移为stable，不直接改名覆盖。

## 9. 网络拓扑

### 9.1 容器内部

```text
gateway
↓
api
↓
db

scheduler
↓
db

worker-data
↓
db
↓
Tushare HTTPS

worker-research
↓
db
↓
文件制品目录
```

服务通过环境独立Docker网络通信。

### 9.2 对外入口

稳定环境只允许：

```text
Browser / 管理端
↓
Nginx或等价网关
↓
API
```

数据库不作为用户入口。

目标要求：

- PostgreSQL不发布到全部宿主机网卡；
- 管理连接使用本机、SSH隧道或指定管理网；
- API不直接暴露公网；
- V1不开放公网；
- TLS和认证在统一网关处理；
- 来源网络受控。

## 10. 端口规划

端口必须配置化，并避免与其他服务冲突。

建议逻辑：

| 环境 | Gateway | API本机 | PostgreSQL管理 |
|---|---:|---:|---:|
| test | 按需分配 | 18100 | 默认不发布 |
| stable | 按需分配 | 18000 | 默认不发布 |
| legacy | 保持现状 | 保持现状 | 保持现状 |

具体端口由部署时核对服务器占用后确定。

PostgreSQL容器内部仍使用5432。

## 14. 配置与密钥

分为：

```text
代码默认值
环境配置
业务配置
密钥
```

### 14.1 代码默认值

进入Git：

- 安全默认值；
- 配置结构；
- 示例文件；
- 非敏感常量。

### 14.2 环境配置

环境独立：

- 端口；
- 数据库地址；
- 环境名；
- 日志级别；
- 资源上限；
- 目录；
- Worker角色。

### 14.3 业务配置

进入数据库版本管理：

- 数据更新规则；
- 质量规则；
- 存储规则；
- 特征和策略参数；
- 风控规则。

### 14.4 密钥

不得进入Git、镜像、日志和错误响应。

- 数据库密码；

- 后续API密钥；
- 券商凭据；
- TLS私钥。

test和stable使用不同密钥。

## 15. 镜像与发布制品

API、Scheduler和Worker使用同一应用镜像。

差异通过启动命令和角色配置实现。

发布制品必须记录：

```text
应用版本
Git提交
镜像Digest
依赖锁
数据库迁移版本
配置版本
构建时间
```

禁止：

- 服务器现场修改容器代码；
- 从未提交工作区构建stable镜像；
- 使用浮动latest；
- 不记录Digest；
- API和Worker使用不同代码提交。

## 17. 回滚流程

应用回滚：

```text
停止新任务
↓
保留运行状态
↓
切回上一个镜像Digest
↓
健康检查
↓
恢复任务领取
```

数据库变更：

- 简单可逆迁移可以执行downgrade；
- 大表和不可逆迁移优先前向修复；
- 发布前必须备份；
- 回滚方案在迁移文件合并前确认；
- 不允许只回滚代码而数据库语义不兼容。


## 21. 日志

容器日志输出结构化JSON或稳定键值格式。

至少包含：

```text
timestamp
level
service
environment
trace_id
run_id
task_id
request_id
message
error_code
```

Docker设置日志轮转。

AuditEvent和业务状态进入数据库，不依赖容器日志长期保存。

## 22. 资源限制

`svr3` Docker当前可见4 CPU、约62 GiB内存。

V1必须为容器设置资源上限，避免研究任务影响数据库和API。

原则：

- 数据库保留最高稳定优先级；
- API保留响应资源；
- Scheduler资源较小；
- Data Worker限制并发；
- Research Worker默认低并发；
- 全量回测不与全量采集同时无限运行；
- 大任务由调度策略错峰。

具体CPU、内存和并发数通过P2.4基准确定。

## 23. 数据库连接

每个运行角色使用独立数据库连接池配置。

要求：

- API连接池小而稳定；
- Scheduler连接池最小；
- Worker连接池按并发计算；
- 设置连接超时；
- 设置事务超时；
- 大查询设置statement_timeout；
- 禁止无限连接；
- test和stable用户分离。

## 24. server-test数据来源

- 生成测试数据；
- 从stable导出有限范围；
- 脱敏；

## 27. OpenCode边界

OpenCode用于开发，不是服务器运行组件。

OpenCode不得：

- 自动修改stable；
- 自动启动生产服务；
- 直接连接stable数据库修改数据；
- 直接修改密钥；
- 绕过Git构建镜像；
- 把测试结果写入stable；
- 自动清理生产数据。

OpenCode产生的变更必须：

```text
Git
↓
测试
↓
发布候选
↓
server-test
↓
用户批准
↓
stable
```

## 28. P2.3部署结论

当前 `svr3` 继续作为开发验证和后续稳定运行的硬件基础。

采用：

```text
本地开发
+
svr3逻辑test
+
svr3逻辑stable
+
legacy独立
```

V1不要求三套物理服务器。

但必须做到：

```text
环境
数据库
网络
端口
密钥
数据卷
日志
备份
任务状态
```

全部逻辑隔离。

当前运行环境尚未达到正式生产条件。P2.4和P10完成非功能目标、备份恢复、监控、安全和发布治理后，才能将stable正式认定为生产环境。
