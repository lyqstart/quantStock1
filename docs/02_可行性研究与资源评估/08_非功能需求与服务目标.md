# 非功能需求与服务目标

> 路线图阶段：P2.4 非功能要求
> 项目：A股量化研究与信号决策平台
> 文档状态：已确认
> 形成日期：2026-07-29
> 当前基线：`ef0782b`
> 适用范围：V1稳定环境；V2、V3只能提高标准，不能降低核心数据和安全要求

## 1. 定位

V1是单用户自用研究平台，不承诺商业SLA。

本文件定义工程验收目标，不构成对外服务承诺。

目标优先级：

```text
数据正确
>
不丢状态
>
可恢复
>
可追溯
>
安全
>
性能
>
可用性
```

## 2. 服务等级

### 2.1 稳定环境可用性

V1 stable进入正式运行后：

```text
月度可用性目标 ≥ 99.0%
```

排除：

- 用户批准的计划维护；
- Tushare等外部数据源不可用；
- 服务器物理故障且尚未建立异机容灾；
- 用户主动停止。

这不是合同SLA，但属于内部运行目标。

### 2.2 计划维护

- 常规维护提前记录；
- 维护前停止新任务；
- Worker进入DRAINING；
- 维护后执行健康检查；
- 数据库变更先在test预演；
- 每次维护形成记录。

## 3. 数据准确性

### 3.1 强制指标

| 指标 | 目标 |
|---|---:|
| 正式业务主键唯一性 | 100% |
| 正式外键和对象引用完整性 | 100% |
| 正式批次可追溯来源 | 100% |
| 版本对象被静默覆盖 | 0 |
| 已知未来函数 | 0 |
| 关键单位和代码口径未登记 | 0 |
| 未通过质量门禁直接发布 | 0 |
| test数据进入stable | 0 |

### 3.2 数据对账

对首批DataItem执行：

- 来源返回量与RAW写入量对账；
- RAW输入量与CLEAN处理量对账；
- CLEAN发布量与质量结果对账；
- 更新、跳过、拒绝和异常数量相加一致；
- 数据水位与实际最大业务时间一致；
- 归档前后记录数和Checksum一致。

### 3.3 财务和事件数据

必须保留：

```text
报告期
公告时间
可用时间
修订版本
有效区间
来源版本
```

任一历史查询只能读取当时已经可用的数据版本。

### 3.4 行情数据

必须明确：

- 频率；
- 时区；
- 交易日；
- 停牌；
- 涨跌停；
- 成交量和成交额单位；
- 未复权价格；
- 复权因子；
- 聚合规则。

## 4. 数据时效性

### 4.1 调度

配置的可用时间到达后：

```text
95%的日常增量任务在15分钟内被创建
```

### 4.2 完成

外部来源正常、数据量处于批准范围时：

```text
95%的日频增量在来源可用后2小时内完成
99%的日频增量在来源可用后4小时内完成
```

### 4.3 分钟数据

V1分钟数据定位为研究型T+1或批量数据，不承诺实时。

实时延迟目标在第5步根据真实供应商和券商资源重新确认。

## 5. 任务可靠性

| 指标 | 目标 |
|---|---:|
| 幂等重跑产生不可控重复 | 0 |
| 任务无终态且无Lease/心跳 | 0 |
| 失败原因不可查询 | 0 |
| 重试覆盖原Attempt | 0 |
| 任务终态回到RUNNING | 0 |
| 业务状态仅存在内存 | 0 |

### 5.1 故障识别

- Worker心跳中断后10分钟内识别为LOST或Lease过期；
- 15分钟内进入自动恢复、重试或明确人工处置状态；
- Scheduler重复启动不得重复创建同一幂等任务；
- API重启不得丢失已创建任务；
- 数据库短暂不可用后不得静默跳过任务。

### 5.2 重试

- 重试策略版本化；
- 外部限频与业务失败区分；
- 永久错误不无限重试；
- 每次Attempt保留；
- 达到上限后生成明确告警和DataGap。

## 6. 查询性能

以下在当前 `svr3` 4 CPU条件下验证，数据已正确索引且无其他全量重任务。

| 场景 | 目标 |
|---|---:|
| 健康检查p95 | ≤ 300 ms |
| 任务状态和详情p95 | ≤ 1 s |
| 单股票10年日线p95 | ≤ 2 s |
| 100只股票5年日线p95 | ≤ 5 s |
| 单股票1年1分钟p95 | ≤ 5 s |
| 单次对象上游或下游追溯p95 | ≤ 3 s |
| 常用元数据目录p95 | ≤ 1 s |

测试必须：

- 预热和冷启动分别记录；
- 至少运行30次；
- 报告p50、p95和最大值；
- 记录数据量、索引和服务器负载。

## 7. 回测性能

代表性基准：

```text
500只股票
5年日线
单一基础策略
基础成本和A股交易规则
4 CPU当前服务器
```

目标：

```text
单次完成时间 ≤ 10分钟
峰值内存 ≤ 16 GiB
运行期间API核心查询p95不超过空闲时2倍
```

复杂策略和分钟回测必须单独建立基准，不能套用日线目标。

## 8. 容量目标

- 稳定数据盘保持至少30%可用空间；
- 任一挂载点使用率达到70%进入预警；
- 达到80%阻止新的大规模初始化；
- 达到90%停止非必要写入并告警；
- 全市场分钟扩展前完成SSD迁移、压缩、归档和恢复；
- 系统盘不承载长期全市场分钟增长；
- 归档后必须可恢复；
- 备份空间不与主数据库共用唯一故障点。

## 9. 安全

### 9.1 网络

- V1不开放公网；
- PostgreSQL不得监听全部外部网卡；
- 管理访问使用本机、指定管理网或SSH隧道；
- API通过统一入口访问；
- test和stable网络隔离；
- 旧quantStock网络和数据独立。

### 9.2 密钥

必须做到：

```text
Git中明文密钥 = 0
镜像中明文密钥 = 0
日志中明文密钥 = 0
API错误中明文密钥 = 0
```

- test和stable使用不同凭据；
- 数据库角色最小权限；
- Token支持轮换；
- 密钥变化记录审计，但不记录密钥内容。

### 9.3 权限

V1虽然单用户，正式对象仍保存owner和actor。

高风险动作至少包括：

- 删除；
- 归档后清理；
- 质量豁免；
- 版本激活；
- stable迁移；
- 恢复覆盖；
- 启用实时或自动执行。

高风险动作必须确认并审计。

## 10. 审计和追溯

100%的以下事件进入AuditEvent：

- 登录和身份变化；
- 配置变化；
- 数据源启停；
- 任务取消和人工重跑；
- 质量豁免；
- 数据发布和失效；
- 策略版本激活；
- 风控规则变化；
- 信号发布和取消；
- 用户决策；
- 未来订单操作；
- 备份恢复；
- 数据迁移。

Signal必须可以回查至DataSource。

## 11. 可观测性

### 11.1 必须监控

- API健康和延迟；
- Scheduler心跳和Leader；
- Worker心跳、角色和当前任务；
- 任务积压、失败率和重试；
- 数据水位；
- 数据缺口；
- 质量失败；
- 数据库连接、锁、长事务和WAL；
- CPU、内存、磁盘和文件系统；
- TimescaleDB chunk和压缩；
- 备份最后成功时间；
- 归档最后验证时间。

### 11.2 告警

| 级别 | 含义 | 发现后目标 |
|---|---|---:|
| P0 | 数据损坏、安全暴露、自动执行失控 | 立即停止相关功能 |
| P1 | 核心服务不可用、备份失败、磁盘≥90% | 5分钟内可见 |
| P2 | 任务持续失败、质量失败、磁盘≥80% | 15分钟内可见 |
| P3 | 趋势风险和非关键异常 | 当日可见 |

当前单用户阶段允许通过明确的页面、日志摘要和消息渠道告警，不强制建设大型监控平台。

## 12. 备份和恢复

### 12.1 分类目标

| 数据类别 | RPO | RTO |
|---|---:|---:|
| 配置、策略、风控、信号、用户决策和审计 | ≤ 4小时 | ≤ 4小时 |
| 可重新采集的市场数据 | ≤ 24小时 | ≤ 24小时 |
| 回测和报告制品 | ≤ 24小时 | ≤ 24小时 |
| Git代码和文档 | 以远程主分支为准 | ≤ 2小时 |

### 12.2 备份要求

- stable数据库自动备份；
- 备份有时间、版本、大小和Checksum；
- 至少保留一个服务器外副本后才能认定生产；
- 配置、Compose和网关配置备份；
- 备份不包含未加密明文密钥；
- 每月至少一次恢复演练；
- 每次重大迁移前执行专项备份。

### 12.3 恢复验收

恢复到独立环境后验证：

- 数据库可启动；
- Alembic版本正确；
- 关键表行数一致；
- Checksum一致；
- API可查询；
- Scheduler和Worker不误连stable；
- 关键端到端场景通过。

## 13. 发布和回滚

- 每个stable发布绑定Git提交、镜像Digest和迁移版本；
- 不从未提交工作区发布；
- test先执行迁移和集成测试；
- 发布前备份；
- 发布后健康检查；
- 应用可回滚到上一镜像；
- 数据库不可逆变化有前向修复方案；
- 失败发布不能继续运行不兼容Worker。

## 14. 可维护性

目标：

- 新开发者或新会话从路线图和任务总表恢复上下文；
- 关键操作有一键复制命令；
- 配置有示例和校验；
- 错误有稳定错误码和业务说明；
- 模块间不通过隐式表结构耦合；
- 业务规则有单元和集成测试；
- 重任务可暂停、取消和恢复；
- 不依赖个人电脑常驻；
- 不依赖OpenCode运行生产系统。

## 15. 测试覆盖门禁

不以单一覆盖率数字代替质量。

必须100%覆盖的场景：

- 幂等；
- 状态机合法流转；
- 防未来；
- 财务修订；
- 质量发布门禁；
- 风控旁路阻断；
- 用户决策与信号分离；
- 权限隔离；
- 重复订单防护；
- 备份恢复；
- 迁移升级。

普通业务代码行覆盖率目标：

```text
≥ 80%
```

核心状态机、风控和执行模块分支覆盖率目标：

```text
≥ 90%
```

## 16. 外部依赖降级

Tushare不可用时：

- 不伪造成功；
- 任务进入明确等待或失败状态；
- 保留请求证据；
- 不发布不完整数据；
- 已有研究数据仍可只读；
- 系统页面仍可查看状态和历史。

AI模型不可用时：

- 核心研究和决策功能继续运行；
- AI入口显示不可用；
- 不影响正式任务。

## 17. 生产门禁

当前运行环境只有同时满足以下条件才能标记为stable正式运行：

1. 数据库迁出系统盘；
2. PostgreSQL不对全部网卡开放；
3. test和stable隔离；
4. 自动备份和服务器外副本建立；
5. 恢复演练通过；
6. 日志轮转；
7. 基础监控和告警；
8. 密钥治理；
9. 发布和回滚验证；
10. P2.4关键指标实测。

## 18. P2.4结论

V1采用非商业SLA的内部服务目标。

核心底线：

```text
数据错误不发布
任务状态不丢失
历史版本不覆盖
结果可以追溯
故障可以恢复
密钥不泄露
AI和自动执行不能旁路规则
```

P2总体设计到此完成。
