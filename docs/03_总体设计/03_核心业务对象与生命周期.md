# 核心业务对象与生命周期

> 路线图阶段：P2.2 核心业务对象与生命周期  
> 项目：A股量化研究与信号决策平台  
> 日期：2026-07-27  
> 状态：已确认

---

# 1. 设计目标

本文件定义平台未来各阶段共同使用的核心业务对象。

目的不是现在一次开发全部对象，而是先把对象边界稳定下来，避免后续：

- 数据对象和任务对象混在一起；
- 策略定义和策略代码混在一起；
- 回测结果覆盖历史版本；
- 信号无法追溯；
- 旧quantStock数据直接污染新项目；
- 多用户扩展时重新推翻底层对象模型。

核心原则：

```text
对象有唯一身份
版本有明确边界
状态有明确流转
归属有明确主体
结果可追溯到上游
```

平台核心对象分为九组：

```text

决策对象

迁移与审计对象
```

# 3. 数据源对象

## 3.1 DataSource 数据源

表示一个外部或内部数据来源。

当前：

```text
Tushare
AKShare
legacy_quantstock
```

未来可增加其他来源。

核心属性：

```text
source_id
source_code
source_name
source_type
status
credential_ref
capability_version
created_at
updated_at
```

状态：

```text
draft
↓
enabled
↓
degraded
↓
disabled
↓
retired
```

其中：

```text
legacy_quantstock
```

只能作为：

```text
只读迁移来源
```

不能成为新项目长期在线业务依赖。

# 4. DataItem 数据项

DataItem表示平台要管理的一种数据。

例如：

```text
A股日线
复权因子
每日指标
1分钟行情
利润表
股票基础信息
```

它不是某一张物理表，而是业务数据目录中的稳定对象。

核心属性：

```text
data_item_id
code
name
domain
frequency
primary_source
backup_sources
schema_version
update_policy
retention_policy
quality_policy
status
```

生命周期：

```text
draft
↓
validated
↓
enabled
↓
deprecated
↓
retired
```

数据项和具体Tushare API不能永久绑定。

例如：

```text
A股日线
    ↓
Tushare daily
或
AKShare对应接口
```

---

# 5. SourceBinding 数据源绑定

表示：

```text
某个DataItem
如何从某个DataSource获取
```

例如：

```text
A股日线
+
Tushare
+
daily接口
```

绑定信息包括：

```text
api_name
request_policy
field_mapping_version
rate_limit
max_rows
history_range
availability_time
priority
status
```

这样以后更换数据源时，不需要修改DataItem身份。

# 7. CollectRun 采集任务实例


# 10. DataSnapshot 数据快照

对于回测和正式研究，需要能够冻结某个时点的数据视图。

DataSnapshot表示：

```text
在某个可见时间点
平台允许研究使用的那一版数据集合
```

作用：

- 防止回测后来重跑时数据悄悄变化；
- 防止财报修订导致历史结果无法复现；
- 支撑完整追溯。

# 14. StockPool 股票池

# 21. BacktestRun 回测

# 22. TradePlan 交易计划

策略结果不能直接变成订单。


- 方向；
- 目标仓位；
- 价格/时间约束；
- 计划原因；
- 来源策略；
- 来源任务。

状态：

```text

↓

↓

├─→ approved
└─→ rejected
```

# 26. Execution 执行对象

```text

↓
```

# 27. User 用户

当前只有一个用户，但仍保留：

```text
user_id
status
```

所有需要归属的对象都绑定owner或creator。

这样未来增加用户时不改变核心对象身份。

---

# 28. Permission 权限

权限属于系统能力，不属于AI。

AI只能继承当前用户已经拥有的权限。

原则：

```text
AI权限 ⊆ 当前用户权限
```

# 29. LegacyMigrationBatch 遗留数据迁移批次

由于旧quantStock存在大量可利用历史数据，新项目增加专门的迁移对象：

```text
legacy_migration_batch_id
source_system
source_database
source_table
source_range
target_data_item_id
validation_rule_version
started_at
finished_at
record_count
accepted_count
rejected_count
status
```

生命周期：

```text
planned
↓
scanning
↓
validated
├─→ import_ready
│      ↓
│    importing
│      ↓
│    completed
└─→ rejected
```

迁移必须是显式动作。

禁止：

```text
新项目业务代码
长期直接查询旧quantStock数据库
```

---

# 30. 遗留记录追溯字段

从旧quantStock导入的数据至少记录：

```text
source_system = legacy_quantstock
legacy_migration_batch_id
legacy_table
legacy_record_key
legacy_content_hash
validation_status
imported_at
```

如果旧数据不能证明完整性或时间语义正确，则：

```text
重新从Tushare采集
```

而不是强行迁移。

---

# 31. 对象标识原则

所有核心对象使用平台自己的稳定ID。

禁止使用以下内容作为长期业务主键：

- 名称；
- 显示文字；
- 数据库自增序号跨系统直接继承；
- 旧quantStock对象ID；
- 外部API临时ID。

外部标识作为：

```text
external_key
```

或来源字段保存。

---

# 32. 版本原则

需要版本化的对象包括：

```text
DataItem Schema
清洗规则
Feature
Analysis
StockPool
Strategy
成本模型
Risk Rule
```

正式结果必须绑定具体版本。

原则：

```text
定义可以继续演化
历史执行绑定不可变版本
```

---

# 33. 状态原则

状态必须表达业务事实。

禁止用：

```text
0
1
2
3
```

而没有明确语义。

状态流转必须：

- 有合法入口；
- 有合法出口；
- 可审计；
- 失败状态可解释；
- 不能任意跳转。

---

# 34. 归属原则

当前单用户也要保留：

```text
owner_id
created_by
```

但不提前建设复杂组织结构。

未来多用户时再扩展：

```text
workspace
team
role
```

---

# 35. 删除原则

已经进入正式追溯链的对象原则上不物理删除。

采用：

```text
deprecated
retired
cancelled
```

等状态。

可以物理清理的主要是：

- 临时缓存；
- 可重建中间文件；
- 超过保留期的技术日志。

---

# 36. 当前第一实施批次需要真正落地的对象

当前数据底座批次优先实现：

```text
DataSource
DataItem
SourceBinding
CollectTask
CollectRun
RawBatch
CleanBatch
QualityResult
LegacyMigrationBatch
AuditEvent
```

Feature、Strategy、Backtest、Signal等：

```text
现在只稳定对象边界
后续P阶段再实现
```

# 37. P2.2结论

核心对象体系确定为：

```text
数据源
↓
数据项
↓
采集任务定义
↓
采集实例
↓
Raw批次
↓
Clean批次 / 数据快照
↓
Feature / Analysis
↓
股票池
↓
策略定义 / 实现 / 版本
↓
任务实例 / 回测
↓
交易计划
↓
风控结果
↓
信号
↓
用户决策
↓
未来QMT执行
```

旧quantStock通过独立：

```text
LegacyMigrationBatch
```

进入新项目。

旧项目不是新项目的运行依赖。
