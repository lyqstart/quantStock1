# 总体系统架构

> 路线图阶段：P2.3 总体系统架构  
> 项目：A股量化研究与信号决策平台（quantStock1）  
> 日期：2026-07-27  
> 状态：已确认

---

# 1. 架构目标

quantStock1 是对旧 quantStock 的重新建设。

核心目标：

```text
复用有价值资源
+
彻底隔离旧项目
+
降低系统复杂度
+
保证数据可靠
+
为后续完整研究闭环预留扩展能力
```

本项目不继续修补旧 quantStock 架构。

---

# 2. 总体架构原则

## 2.1 新旧项目完全隔离

旧 quantStock：

```text
遗留系统
+
历史数据来源
+
经验来源
```

新 quantStock1：

```text
独立代码
独立数据库
独立容器
独立配置
独立任务
独立日志
独立备份
```

两者唯一允许的正式连接：

```text
受控历史数据迁移
```

禁止新项目长期直接依赖旧项目服务或数据库。

---

## 2.2 单人维护优先

当前项目只有一人维护。

架构优先级：

```text
稳定
>
可理解
>
可恢复
>
可追溯
>
性能
>
分布式扩展
```

不提前引入没有现实必要的中间件和微服务。

---

## 2.3 模块化单体优先

第一阶段采用：

```text
模块化单体
```

而不是：

```text
微服务
```

含义：

- 一个代码仓库；
- 一个统一领域模型；
- 一套数据库迁移；
- 一套公共配置；
- 模块边界清晰；
- 可以启动成多个独立进程角色。

以后某个模块出现明确性能或部署需求时，再拆分服务。

# 4. 第一阶段运行架构

第一阶段只保留三个应用运行角色：

```text
API
Scheduler
Worker
```

外加数据库：

```text
PostgreSQL + TimescaleDB
```

即：

```text
                ┌─────────────┐
                │     API     │
                └──────┬──────┘
                       │
                       ▼
┌─────────────┐   ┌──────────────┐   ┌─────────────┐
│  Scheduler  │──▶│ PostgreSQL   │◀──│   Worker    │
└─────────────┘   │ +TimescaleDB │   └─────────────┘
                  └──────────────┘
```

---

# 5. API职责

API只负责：

- 查询数据目录；
- 查询采集状态；
- 查询清洗状态；
- 创建人工补采任务；
- 创建重试任务；
- 查询任务执行结果；
- 查询质量结果；
- 查询迁移状态；
- 后续提供前端接口。

API不直接执行大规模采集和清洗。

---

# 6. Scheduler职责

Scheduler只负责：

```text
什么时候应该创建任务
```

包括：

- 根据交易日历创建日常增量任务；
- 根据数据可用时间创建任务；
- 创建定期校验任务；
- 创建容量检查任务；
- 创建必要的维护任务。

Scheduler不直接处理业务数据。

---

# 7. Worker职责

第一阶段使用统一Worker。

Worker负责执行：

```text
采集
清洗
质量校验
补采
历史迁移
```

不同任务通过：

```text
task_type
```

区分。

第一阶段不拆成：

```text
collect-worker
clean-worker
strategy-worker
...
```

避免重复进程、重复配置和复杂调用关系。

未来如果某类任务形成明确性能瓶颈，再按任务类型增加独立Worker进程。

---

# 8. 为什么第一阶段不使用Celery

旧 quantStock 已经存在：

```text
Scheduler
Celery
Redis
多个Worker
```

的复杂运行体系。

新项目第一阶段没有多服务器、大规模横向扩展和高并发任务队列需求。

因此第一阶段：

```text
不采用Celery
```

任务统一存放在PostgreSQL任务表。

Worker通过数据库领取任务。

目的：

- 减少一个任务框架；
- 减少Redis强依赖；
- 避免Scheduler和Celery Beat职责重复；
- 所有任务状态天然持久化；
- 故障后容易恢复；
- 单人维护更简单。

---

# 9. 为什么第一阶段不把Redis作为核心依赖

Redis不是第一阶段必需组件。

当前核心需求：

- 任务状态；
- 任务领取；
- 重试；
- 断点；
- 幂等；
- 审计。

全部可以先由PostgreSQL可靠保存。

因此：

```text
第一阶段核心运行不依赖Redis
```

以后出现：

- 高频缓存；
- Pub/Sub；
- 大量短期状态；
- 大规模队列吞吐；

再引入Redis。

---

# 10. PostgreSQL任务队列

任务表作为唯一任务事实来源。

Worker领取任务使用数据库并发控制。

逻辑：

```text
pending
↓
Worker原子领取
↓
running
├─ succeeded
├─ partial
├─ failed
└─ cancelled
```

即使Worker进程退出：

```text
任务事实仍在数据库
```

系统可以识别超时running任务并恢复。

---

# 12. meta Schema

保存平台定义类对象：

- DataSource；
- DataItem；
- SourceBinding；
- 数据字段版本；
- 清洗规则版本；
- 更新策略；
- 保留策略。

这里保存：

```text
系统知道什么
```

而不是大量市场事实数据。

---

# 13. raw Schema

保存：

```text
外部数据源返回的原始事实
```

原则：

- 尽量不做业务修正；
- 保留来源；
- 保留采集批次；
- 保留抓取时间；
- 保留源接口；
- 保留版本；
- 可判断是否重复；
- 可重新清洗。

---

# 14. clean Schema

保存：

```text
标准化后、通过规定质量门禁的数据
```

clean层面向：

- Feature；
- Analysis；
- Strategy；
- Backtest；
- API查询。

上层研究禁止直接把raw作为正式数据入口。

---

# 15. quality Schema

保存：

- 数据质量规则；
- 质量检查结果；
- 缺口；
- 重复；
- 异常；
- 截断风险；
- 隔离数据引用。

质量问题不能只写在日志中。

---

# 16. ops Schema

保存运行事实：

- CollectTask；
- CollectRun；
- CleanRun；
- Scheduler状态；
- Worker心跳；
- Checkpoint；
- 系统状态。

---

# 17. audit Schema

保存：

- 关键状态变化；
- 用户操作；
- 系统操作；
- AI触发动作；
- 配置变化；
- 迁移审批和结果。

---

# 18. migration Schema

专门管理：

```text
旧quantStock -> 新quantStock1
```

包括：

- LegacyMigrationBatch；
- 来源表；
- 来源范围；
- 校验结果；
- 导入结果；
- 内容Hash；
- 拒绝记录。

旧库不得伪装成普通DataSource长期在线使用。

---

# 19. 时间序列存储

分钟行情等高容量数据使用：

```text
TimescaleDB Hypertable
```

优先用于：

- 1分钟行情；
- 必要的其他高频时间序列。

普通基础信息、财务、事件数据使用普通PostgreSQL表。

不能所有表都强制Hypertable。

---

# 20. 分钟频率存储原则

后续详细设计默认优先考虑：

```text
1分钟 = 基础分钟事实
```

5/15/30/60分钟属于可从1分钟聚合的数据。

因此不默认长期保存五套完整raw+clean数据。

是否保存派生频率由后续存储设计根据：

- 查询性能；
- 计算成本；
- 空间；
- Tushare原始语义；

最终确定。

目的：

```text
避免无意义数据复制
```

---

# 21. 数据访问原则

所有上层模块统一通过：

```text
Data Access
```

访问标准数据。

禁止：

```text
策略直接拼SQL访问任意raw表
```

也禁止：

```text
业务代码直接依赖Tushare字段
```

统一路径：

```text
外部API字段
↓
Source Adapter
↓
Raw
↓
标准化
↓
Clean Contract
↓
上层业务
```

---

# 22. 数据源适配层

每个外部来源拥有自己的Adapter。

例如：

```text
TushareAdapter
AKShareAdapter
LegacyMigrationAdapter
```

Adapter负责：

- 请求参数；
- 调用；
- 限频；
- 外部错误转换；
- 返回字段解析；
- 外部接口版本差异。

Adapter不负责：

- 业务清洗；
- 策略判断；
- 数据质量最终判定。

---

# 23. Tushare调用治理

Tushare统一经过：

```text
TushareAdapter
+
RateLimiter
```

不能让每个业务模块自己调用Tushare SDK。

统一控制：

- 每分钟频率；
- 每日次数；
- 最大返回行数；
- 时间窗口拆分；
- 股票拆分；
- 重试；
- 退避；
- 接口级能力探测；
- 调用审计。

---

```text

备用
```

不要求一次接入全部接口。

AKShare数据同样必须：


# 25. 遗留数据复用架构

```text
        │
```


---

# 26. 遗留数据迁移优先级

按复用价值排序：

```text
1. 历史1分钟数据
2. 长周期历史日线
3. 历史每日指标和复权因子
4. 财务历史数据
5. 其他事件数据
```

实际顺序以后按：

- 数据完整性；
- 重新下载成本；
- 当前磁盘容量；

确定。

---

# 27. 不直接复制776GB旧数据库

新项目不能：

```text
直接复制整个旧数据库
```

原因：

- 会复制旧设计问题；
- 会复制无用表和索引；
- 会造成巨大空间占用；
- clean数据质量未重新确认；
- 新旧Schema不同；
- 新项目追溯链会失真。

采用：

```text
按DataItem迁移
```

# 33. 扩展策略

未来出现瓶颈时按顺序扩展：

```text
单Worker
↓
同代码多Worker
↓
按任务类型拆Worker
↓
Redis/Celery等队列（确有必要）
↓
独立计算节点
```

数据库：

```text
单PostgreSQL/TimescaleDB
↓
冷热数据分层
↓
独立归档
↓
必要时再扩展存储节点
```

不提前走最后一步。

---

# 34. 第一阶段故障恢复原则

任何长任务必须：

- 可重试；
- 可断点；
- 可幂等；
- 有任务状态；
- 有错误原因；
- 有心跳；
- 有超时恢复；
- 不依赖进程内内存保存唯一状态。

因此Worker重启后：

```text
系统事实仍在数据库
```

# 35. 配置原则

配置分为：

```text

环境配置
密钥
```

其中：

# 36. 备份原则

新项目从第一天独立备份。

不能依赖：

```text
旧quantStock备份
```

新项目备份对象包括：

- 数据库；
- 关键配置；
- 数据目录；
- 迁移记录。

历史大容量分钟数据需要冷热和归档策略，避免完整热备份无限增长。

# 37. P2.3结论

新quantStock1采用：

```text
模块化单体
+
三个运行角色
+
一个主数据库
```

第一阶段：

```text
API
Scheduler
Worker
PostgreSQL + TimescaleDB
```

不引入：

```text
Celery
Redis核心依赖
多种Worker服务
微服务
```

旧quantStock：

```text
只作为受控迁移来源
```

整个设计目标是：

> 用最少的运行组件完成可靠的数据闭环，再按真实瓶颈扩展。
