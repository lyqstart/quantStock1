# 部署与环境隔离架构

> 路线图阶段：P2.3 总体系统架构  
> 项目：A股量化研究与信号决策平台（quantStock1）  
> 日期：2026-07-27  
> 状态：已确认

---

# 1. 目标

当前只有一台服务器：

```text
svr3
```

并且svr3同时承担：

```text
开发
测试
正式
```

同时还运行旧quantStock和其他系统。

因此本文件解决：

```text
同一服务器
如何让新旧项目分开
如何让dev/test/prod分开
```

---

# 2. 总原则

物理服务器可以共用。

以下内容必须隔离：

```text
代码
容器
网络
数据库
用户
配置
端口
数据目录
任务
日志
备份
```

---

# 3. 新旧项目隔离

旧项目：

```text
quantStock
```

新项目：

```text
quantStock1
```

新项目禁止复用旧项目的：

- Compose project name；
- 容器；
- Docker network；
- PostgreSQL数据库；
- PostgreSQL用户；
- Redis；
- volume；
- 端口；
- `.env`；
- 日志目录；
- 任务表。

---

# 4. 服务器目录建议

新项目统一目录：

```text
/mnt/2t_ssd/quantstock1/
```

建议：

```text
/mnt/2t_ssd/quantstock1/
├─ prod/
│  ├─ pgdata/
│  ├─ data/
│  ├─ logs/
│  └─ archive/
├─ test/
│  ├─ pgdata/
│  ├─ data/
│  └─ logs/
└─ dev/
   ├─ pgdata/
   ├─ data/
   └─ logs/
```

代码仓库不与数据库数据目录混放。

服务器代码工作目录建议：

```text
/mnt/1t_back/project/quantstock1
```

具体服务器代码目录部署时再以实际仓库位置确认。

---

# 5. Docker Compose项目名

明确使用：

```text
quantstock1-prod
quantstock1-test
quantstock1-dev
```

不能使用旧项目：

```text
quantstock
```

这样Docker自动生成的：

- network；
- volume；
- container namespace；

不会与旧项目混淆。

---

# 6. 容器命名原则

不强制手写`container_name`。

优先依赖Compose项目隔离。

例如：

```text
quantstock1-prod-api-1
quantstock1-prod-worker-1
quantstock1-prod-scheduler-1
quantstock1-prod-db-1
```

一眼能看出环境。

---

# 7. 第一阶段生产容器

prod只需要：

```text
db
api
scheduler
worker
```

以后需要统一Web入口时再增加：

```text
nginx
```

避免一开始复制旧项目大量容器。

---

# 8. 开发环境

日常开发优先：

```text
笔记本本地代码
+
本地测试
```

需要长时间AI开发时：

```text
svr3 quantstock1-dev
```

dev只能访问：

```text
dev数据库
```

不能默认连prod数据库。

---

# 9. 测试环境

test用于：

- 集成测试；
- 数据迁移验证；
- Tushare接口测试；
- 升级验证；
- 部署验证。

test使用：

```text
小规模样本数据
```

不复制全部历史生产数据。

---

# 10. 正式环境

prod只运行：

- 已提交Git的正式版本；
- 已通过测试的数据库迁移；
- 已确认的配置。

禁止：

```text
直接在prod容器里改代码
```

OpenCode长时间开发任务不能直接修改prod挂载代码。

---

# 11. 数据库隔离

至少：

```text
quantstock1_dev
quantstock1_test
quantstock1_prod
```

并使用不同数据库用户。

例如：

```text
quantstock1_dev_user
quantstock1_test_user
quantstock1_prod_user
```

prod用户凭据不能放进dev默认环境。

---

# 12. 数据量隔离

prod保存：

```text
正式完整数据
```

test保存：

```text
代表性样本
```

dev保存：

```text
最小开发样本
```

不能为了环境一致性复制三份完整分钟数据。

---

# 13. 历史数据迁移隔离

旧quantStock数据库：

```text
只读
```

迁移程序使用独立只读账号。

权限：

```text
SELECT
```

不允许新迁移程序：

```text
INSERT
UPDATE
DELETE
DDL
```

旧数据库。

---

# 14. 旧数据库网络关系

迁移期间允许：

```text
quantstock1 migration process
        ↓ read-only
legacy quantStock PostgreSQL
```

迁移完成后：

```text
正常业务链不依赖旧数据库
```

---

# 15. 端口隔离

当前旧系统已占用：

- 5434；
- 6380；
- 8000；
- 8080；

以及服务器其他服务端口。

新项目部署时不得复用这些宿主机端口。

具体端口在部署前通过：

```text
ss -lntp
```

重新确认后确定。

数据库生产环境原则上不必公开到`0.0.0.0`。

能走Docker内部网络的服务：

```text
不暴露宿主机端口
```

---

# 16. 数据库暴露原则

生产数据库：

```text
仅Compose内部网络访问
```

除非运维确有需要。

不建议：

```text
0.0.0.0:新端口 -> PostgreSQL
```

测试或调试若临时暴露：

- 只绑定127.0.0.1；
- 使用SSH隧道访问。

---

# 17. API暴露

第一阶段API可以：

```text
127.0.0.1:内部端口
```

由宿主机已有Nginx或新项目Nginx统一转发。

正式对外方式在部署设计阶段确定。

---

# 18. 配置文件

建议：

```text
.env.dev
.env.test
.env.prod
```

但：

```text
真实.env文件不提交Git
```

仓库只保留：

```text
.env.example
```

说明所有配置项。

---

# 19. 密钥

包括：

- Tushare Token；
- 数据库密码；
- QMT凭据；
- AI API Key；

全部作为环境密钥管理。

禁止：

- 写死在源码；
- 写入Markdown；
- 提交Git；
- 打印到日志。

---

# 20. Git版本边界

prod必须能够对应到：

```text
Git commit
```

部署记录至少保存：

```text
commit SHA
deployment time
database migration version
environment
```

不能出现：

```text
服务器代码改过
但Git里没有
```

---

# 21. OpenCode开发边界

svr3上的OpenCode只操作：

```text
quantstock1-dev工作区
```

完成后：

```text
测试
↓
Git提交
↓
用户同步/审核
↓
部署prod
```

不得让AI直接修改prod运行目录作为正常开发方式。

---

# 22. 数据库迁移

Alembic迁移流程：

```text
dev验证
↓
test验证
↓
备份
↓
prod执行
```

prod禁止手工随意改表后不记录迁移。

---

# 23. 发布流程

单人项目采用最小流程：

```text
开发
↓
自动测试
↓
test环境
↓
确认
↓
Git commit
↓
prod build
↓
数据库迁移
↓
prod启动
↓
健康检查
```

不需要一开始建设复杂CI/CD平台。

---

# 24. 回滚

每次prod发布至少具备：

- 上一个Git版本；
- 上一个镜像；
- 数据库迁移回滚/恢复方案；
- 发布前备份；
- 配置版本。

程序回滚和数据回滚是两件事，不能混为一谈。

---

# 25. 资源隔离

svr3是共享服务器。

新项目第一阶段要限制：

- Worker并发；
- 历史迁移并发；
- PostgreSQL内存；
- Docker日志；
- 临时文件；
- 全量采集时间段。

避免影响：

- 旧quantStock；
- Seafile；
- MySQL；
- 其他服务；
- OpenCode开发任务。

---

# 26. 开发任务与生产任务错峰

大规模：

- 历史迁移；
- 历史回填；
- 压缩；
- 重建索引；

优先在正式日常采集低峰期执行。

日常增量优先级高于历史补全。

---

# 27. 日志隔离

至少区分：

```text
dev
test
prod
```

prod日志必须能识别：

```text
service
run_id
trace_id
environment
```

旧quantStock日志不进入新项目日志系统。

---

# 28. 备份隔离

新项目备份目录独立。

建议：

```text
/mnt/1t_back/quantstock1/
```

但当前备份盘容量已经不足以长期完整承载大规模数据库。

因此第一阶段先保存：

- 配置；
- 元数据；
- 关键业务表；
- 数据库结构；
- 迁移记录；

大容量历史市场数据采用后续冷热/归档方案。

---

# 29. prod数据不能直接作为测试沙箱

禁止：

```text
test代码
直接写prod数据库
```

允许的调试方式：

```text
从prod导出有限样本
↓
脱离prod
↓
导入test
```

---

# 30. 三环境并不等于三套完整硬件

当前：

```text
同一svr3
+
逻辑三环境
```

即可。

以后只有出现明确要求才增加物理服务器，例如：

- prod稳定性受到开发影响；
- CPU长期不足；
- 磁盘容量不足；
- 自动交易要求更高可靠性。

---

# 31. 第一阶段环境拓扑

```text
svr3
│
├─ legacy quantStock
│   └─ 旧容器 / 旧数据库 / 历史数据
│
├─ quantstock1-prod
│   ├─ db
│   ├─ api
│   ├─ scheduler
│   └─ worker
│
├─ quantstock1-test
│   ├─ db（样本）
│   ├─ api
│   ├─ scheduler
│   └─ worker
│
└─ quantstock1-dev
    ├─ db（小样本）
    ├─ api
    ├─ scheduler
    └─ worker
```

实际运行时dev/test不需要24小时全部启动。

需要时启动即可。

---

# 32. P2.3部署结论

确定：

1. 旧quantStock继续独立存在；
2. 新quantStock1完全独立部署；
3. svr3暂时继续承载dev/test/prod；
4. 三环境逻辑隔离；
5. test/dev只使用小样本，不复制大规模正式分钟数据；
6. prod只有正式Git版本；
7. OpenCode不直接修改prod；
8. 历史数据只能通过只读迁移链进入新项目；
9. 新项目第一阶段仅四个核心容器；
10. 扩展基础设施必须由真实需求驱动。
