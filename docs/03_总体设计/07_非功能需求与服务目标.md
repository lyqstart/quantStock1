# 非功能需求与服务目标

> 路线图阶段：P2.4 非功能要求  
> 项目：A股量化研究与信号决策平台（quantStock1）  
> 日期：2026-07-27  
> 状态：已确认

---

# 1. 目标

本文件定义quantStock1必须长期遵守的非功能要求。

这些要求不描述“系统有什么功能”，而描述：

```text
系统必须以什么质量运行
```

包括：

- 数据准确性；
- 一致性；
- 任务可靠性；
- 故障恢复；
- 性能；
- 安全；
- 审计；
- 可观测性；
- 备份恢复；
- 可维护性；
- 扩展性；
- 环境隔离。

---

# 2. 总体优先级

项目非功能优先级确定为：

```text
数据正确
>
可追溯
>
可恢复
>
稳定
>
可维护
>
性能
>
扩展规模
```

原因：

平台最终用于量化研究和交易决策。

错误但快速的数据比慢一点但正确的数据风险更大。

---

# 3. 数据准确性

正式进入CLEAN的数据必须满足：

```text
来源明确
主键明确
时间明确
版本明确
质量状态明确
```

禁止：

- 无来源数据进入正式研究；
- 接口返回达到行数上限时直接判定完整；
- 重复记录静默保留；
- 财务修订覆盖历史版本；
- 时间字段语义不明确的数据进入正式回测；
- 质量失败数据直接被策略使用。

---

# 4. 数据一致性

同一DataItem在不同模块中的含义必须一致。

例如：

```text
股票代码
交易日
分钟时间
复权口径
财务报告期
公告时间
可用时间
```

不能在：

- 采集；
- 清洗；
- DataContext；
- 回测；
- 策略；

中各自定义不同口径。

标准口径属于平台级规则。

---

# 5. 防未来数据要求

所有参与历史研究和回测的数据必须支持：

```text
available_at
```

或等价的历史可用时间语义。

历史时间点T：

```text
只能读取当时已经可见的数据
```

不能使用：

- 后续财务修订；
- 后续指数成分；
- 后续行业分类；
- 后续股票状态；
- 后续公告；
- 后续清洗结果中新增的未来事实；

污染历史回测。

---

# 6. 数据追溯要求

正式数据至少能够追溯：

```text
DataSource
↓
SourceBinding
↓
CollectRun
↓
RawBatch / LegacyMigrationBatch
↓
CleanBatch
↓
DataSnapshot
```

后续研究对象继续向下追溯：

```text
Feature
Analysis
Strategy
Backtest
TradePlan
Risk
Signal
UserDecision
```

不能出现只有结果、找不到来源的正式数据。

---

# 7. 任务可靠性

所有长时间任务必须：

```text
有状态
可重试
可断点
可幂等
可取消
可恢复
```

任务状态不能只存在于Python进程内存。

进程退出后：

```text
任务事实仍然存在
```

---

# 8. 幂等要求

同一个：

```text
数据项
+
对象范围
+
时间范围
+
版本
```

重复执行时，不能产生不可控重复数据。

重复执行允许：

- 更新确认后的同一业务事实；
- 新增正式修订版本；
- 留下新的执行记录；

但不能无限插入完全相同的数据正文。

---

# 9. 故障隔离

单个接口、单个DataItem、单个任务失败：

```text
不能让无关数据任务全部停止
```

例如：

```text
财务接口失败
```

不应导致：

```text
日线
分钟
交易日历
```

全部停止。

故障范围必须可定位。

---

# 10. 重试要求

外部临时错误：

- 网络异常；
- Tushare临时失败；
- 请求超时；
- 服务短时不可用；

允许自动重试。

业务错误：

- 无权限；
- 参数错误；
- Schema变化；
- 数据质量失败；

不能无限自动重试。

必须进入明确异常状态。

---

# 11. 断点恢复

以下大任务必须支持断点：

- 历史初始化；
- 分钟历史采集；
- 旧quantStock历史迁移；
- 大范围重新清洗；
- 大范围补采。

系统重启后不应：

```text
从第一条重新开始
```

除非用户明确要求重跑。

---

# 12. Scheduler可靠性

Scheduler只负责：

```text
按规则创建任务
```

必须避免同一计划周期重复创建相同正式任务。

系统重启后：

- 已创建任务不能丢；
- 未完成任务可继续；
- 已完成任务不能因为重启重复执行。

---

# 13. Worker可靠性

Worker处理任务时必须定期记录：

```text
heartbeat
checkpoint
progress
```

如果Worker异常退出，系统需要能够判断：

```text
任务是否失联
```

而不是永久停留在：

```text
running
```

---

# 14. 第一阶段服务可用性目标

当前系统：

- 单人使用；
- 单服务器；
- 无高可用集群；
- 无第二生产服务器。

因此V1第一阶段不设：

```text
99.99%高可用
```

等不符合现有资源的目标。

实际目标：

> 日常数据任务在下一依赖任务开始前完成；临时故障发生后可以自动或人工恢复，不造成数据不可解释的永久缺口。

---

# 15. 日常数据更新目标

正常交易日：

```text
数据源发布
↓
自动创建增量任务
↓
采集
↓
清洗
↓
质量校验
↓
正式可用
```

应在下一交易日正式研究任务开始前完成。

具体不同接口的完成时间：

```text
由数据源实际可用时间决定
```

不统一规定一个错误的固定时刻。

---

# 16. 查询性能目标

P2阶段不凭空设定没有实测依据的毫秒级SLA。

第一阶段目标：

```text
常用单股/短区间查询
应支持交互式使用

全市场/长历史/分钟级大查询
允许批处理
```

具体性能指标在P4/P5实现后通过真实数据基准测试确定。

---

# 17. 批处理优先

以下场景不要求实时返回：

- 全市场多年分钟扫描；
- 全历史重洗；
- 大范围补采；
- 大范围数据迁移；
- 全量回测。

统一作为：

```text
后台任务
```

避免为了“实时”把架构复杂化。

---

# 18. 容量要求

当前旧quantStock数据库已经约776GB，2TB NVMe空间有限。

新项目必须具备：

- 数据库容量监控；
- 磁盘容量监控；
- 大任务启动前容量检查；
- 历史数据压缩；
- 大容量数据生命周期管理；
- 冷归档能力。

不能允许数据库无边界增长直到磁盘写满。

---

# 19. 容量管理线

项目初始运维阈值：

```text
70%：关注
75%：预警
80%：限制非必要大规模历史任务
85%：进入容量保护状态
```

这些是项目管理阈值，不是Linux或PostgreSQL硬限制。

阈值以后可根据实际运行调整。

---

# 20. 数据库性能原则

PostgreSQL / TimescaleDB优化优先顺序：

```text
正确数据模型
↓
正确主键
↓
合理分区/Hypertable
↓
实际查询所需索引
↓
压缩
↓
SQL优化
```

不采用：

```text
发现慢查询就不断加索引
```

的方式。

---

# 21. 安全边界

新quantStock1必须与旧quantStock隔离。

必须独立：

- 数据库；
- 数据库用户；
- 容器；
- Docker网络；
- 配置；
- 任务状态；
- 日志；
- 数据目录。

旧系统不能成为新系统生产依赖。

---

# 22. 最小权限

不同运行角色只获得所需权限。

例如：

```text
Legacy Migration
=
旧库只读
```

不能拥有旧quantStock数据库修改权限。

开发环境不能默认获得生产数据库写权限。

---

# 23. Token和密钥

以下信息禁止进入Git：

- Tushare Token；
- 数据库密码；
- AI API Key；
- QMT凭据；
- 其他第三方密钥。

禁止：

- 写死源码；
- 写入正式Markdown；
- 输出到普通日志。

---

# 24. 用户权限

当前只有一个用户，但底层仍保留：

```text
user_id
owner_id
created_by
```

AI权限必须满足：

```text
AI权限 ⊆ 当前用户权限
```

AI不能获得额外后台权限。

---

# 25. 高风险操作

以下操作必须有明确确认和审计：

- 删除正式数据；
- 批量重新清洗；
- 批量覆盖；
- 修改生产数据源配置；
- 数据库Schema高风险迁移；
- 旧数据库迁移；
- 未来QMT真实交易。

---

# 26. 审计要求

关键状态变化统一保存：

```text
谁
何时
对什么对象
从什么状态
变成什么状态
为什么
结果如何
```

关键审计不能只存在文本日志。

---

# 27. 日志要求

日志至少包括：

```text
timestamp
environment
service
level
run_id
trace_id
message
error_code
```

禁止日志输出：

- 密码；
- Token；
- 完整敏感配置。

---

# 28. 可观测性

第一阶段必须能看到：

## 服务状态

```text
API
Scheduler
Worker
Database
```

## 任务状态

```text
pending
running
failed
succeeded
partial
```

## 数据状态

```text
最新数据日期
缺口
质量异常
待补采
```

## 资源状态

```text
CPU
内存
磁盘
数据库容量
```

---

# 29. 告警原则

第一阶段不建设复杂告警平台。

至少对以下事件形成可见告警：

- 日常关键任务未完成；
- 连续采集失败；
- 数据质量失败；
- 数据明显缺口；
- Worker失联；
- Scheduler失联；
- 数据库不可用；
- 磁盘达到容量预警线。

---

# 30. 备份分级

数据按价值分级备份。

## 一级：不可轻易重建

包括：

- meta；
- audit；
- migration；
- 用户配置；
- 策略定义；
- 用户决策；
- 未来订单和成交。

必须重点备份。

## 二级：恢复成本高

包括：

- 历史分钟；
- 财务历史版本；
- 特殊历史事件。

需要数据库备份或可靠冷归档。

## 三级：可重建

包括：

- 派生分钟周期；
- 缓存；
- 可重新计算特征；
- 临时中间数据。

不要求完整多副本。

---

# 31. 初始恢复目标

由于当前只有一台服务器，不宣称高可用。

项目初始设计目标：

## 核心元数据和用户资产

```text
RPO：不超过24小时
RTO：不超过一个工作日
```

## 可从外部重新获取的市场数据

恢复方式可以是：

```text
备份恢复
或
重新采集
```

不要求与核心元数据采用相同恢复方式。

这些是项目设计目标，部署阶段必须实际演练后才能确认达标。

---

# 32. 备份必须验证

存在备份文件：

```text
≠
可以恢复
```

部署阶段必须实际执行：

```text
备份
↓
恢复到隔离环境
↓
校验
```

未验证的备份不能作为完成证据。

---

# 33. 迁移可靠性

旧quantStock历史数据迁移必须：

- 只读来源；
- 分批；
- 有校验；
- 有记录数对账；
- 有Hash或等价内容校验；
- 失败可重新执行；
- 成功批次不可重复污染目标数据。

不允许整库盲目复制。

---

# 34. 可维护性

第一阶段必须坚持：

```text
一个仓库
模块化单体
API
Scheduler
Worker
PostgreSQL/TimescaleDB
```

没有实际证据前不新增：

- Kafka；
- RabbitMQ；
- Kubernetes；
- 微服务群；
- 分布式数据库；
- 多种调度框架。

---

# 35. 代码可维护性

公共规则只能存在一个正式实现来源。

例如：

- 时间规则；
- 交易日历；
- 数据状态；
- 财务可用时间；
- 主键生成；
- 重试分类；
- 数据质量状态；

禁止每个模块复制一套逻辑。

---

# 36. 配置可维护性

配置必须区分：

```text
程序默认配置
环境配置
密钥
业务配置
```

环境差异不能通过：

```text
改源码
```

解决。

---

# 37. 数据Schema可维护性

数据库结构变化使用：

```text
Alembic
```

或正式数据库迁移机制。

禁止生产环境长期通过手工SQL改表而仓库没有记录。

---

# 38. 可扩展性原则

扩展顺序：

```text
先优化当前单体
↓
同代码增加Worker
↓
按真实瓶颈拆运行角色
↓
需要时增加Redis/队列
↓
需要时增加独立计算节点
```

不能直接跳到复杂分布式架构。

---

# 39. 多数据源扩展

新增数据源时：

```text
新增Adapter
+
新增SourceBinding
```

不修改：

```text
上层策略业务逻辑
```

CLEAN业务模型保持稳定。

---

# 40. 多用户扩展

当前单用户。

但所有正式业务对象必须保留：

```text
owner / creator
```

以后增加多用户时：

```text
不重写业务对象主键
```

---

# 41. QMT扩展边界

QMT未来只属于：

```text
Execution Layer
```

不能进入：

- 数据采集；
- CLEAN；
- Feature；
- Strategy计算核心。

未来自动交易失败不能破坏研究数据层。

---

# 42. AI扩展边界

AI通过：

```text
正式应用能力接口
```

工作。

不能：

- 直接任意操作数据库；
- 绕过状态机；
- 绕过风控；
- 获取用户没有的权限；
- 直接成为正式业务事实来源。

---

# 43. 开发、测试、生产隔离

虽然当前共用svr3物理服务器：

```text
dev
test
prod
```

必须逻辑隔离。

至少独立：

- 数据库；
- 配置；
- Compose Project；
- 运行状态；
- 日志。

test/dev只使用小样本数据。

不复制三套完整分钟历史数据。

---

# 44. 生产变更原则

生产变更必须来自：

```text
Git正式版本
```

禁止正常开发流程采用：

```text
直接进入prod容器修改代码
```

OpenCode只在开发工作区工作。

---

# 45. 第一阶段验收需要验证的非功能项

P3/P4实施后至少实际验证：

1. 重复任务幂等；
2. Worker异常退出恢复；
3. Scheduler重启恢复；
4. Tushare临时失败重试；
5. 无权限接口正确停止重试；
6. 接口达到返回上限能识别截断风险；
7. 数据缺口能发现并补采；
8. 财务历史版本不会覆盖；
9. 旧数据迁移可以对账；
10. 磁盘容量预警有效；
11. 开发环境不能误写正式库；
12. 备份可以实际恢复。

---

# 46. 当前明确不承诺的指标

P2阶段没有实际压力测试，因此不虚构：

- 每秒写入多少万行；
- API响应固定低于多少毫秒；
- 全市场分钟回测固定多少秒；
- 99.99%系统可用性；
- 历史全量采集固定多少小时完成。

这些指标只能在真实实现和真实数据基础上测量。

---

# 47. P2.4结论

quantStock1的非功能基线确定为：

```text
正确
可追溯
可恢复
可维护
再追求性能
```

第一阶段必须保证：

- 数据错误不能静默进入正式研究；
- 任务失败后可以定位和恢复；
- 重复执行保持幂等；
- 历史回测有明确时间边界；
- 新旧项目严格隔离；
- dev/test/prod逻辑隔离；
- 关键状态可观测；
- 磁盘容量受控；
- 关键数据有可验证备份；
- 架构复杂度与单人维护能力匹配。

P2阶段至此具备进入后续数据源与采集平台设计的条件。
