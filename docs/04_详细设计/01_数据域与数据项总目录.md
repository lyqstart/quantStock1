# 1. 文档目的

本文件建立 quantStock1 的统一数据目录。

以后任何数据采集、清洗、存储、查询、特征、策略和回测，都必须先对应到一个正式 DataItem。

本文件回答：

1. 平台最终需要管理哪些数据域；
2. 当前 Tushare 权限能提供哪些数据；
3. 哪些数据第一批接入；
4. 哪些数据后续逐步接入；
5. 哪些接口当前没有正式权限；
6. AKShare 和旧 quantStock 在目录中的定位；
7. 后续字段映射、采集任务和清洗规则以什么稳定身份关联。

---

# 2. 核心原则

## 2.1 DataItem 是平台自己的数据身份

平台不能把：

```text
Tushare API 名称
```

直接作为长期业务身份。

例如：

```text
DataItem：stock_daily
业务名称：A股日线行情
主来源：Tushare
来源接口：daily
```

以后即使增加 AKShare：

```text
DataItem 仍然是 stock_daily
```

上层模块不需要跟着改。

---

## 2.2 数据目录与数据源解耦

结构：

```text
DataDomain
    ↓
DataItem
    ↓
SourceBinding
    ├─ Tushare
    ├─ AKShare
    └─ legacy_quantstock
```

DataItem 描述：

```text
平台需要什么数据
```

SourceBinding 描述：

```text
从哪里获得
```

---

## 2.3 当前主数据源

当前正式主数据源：

```text
Tushare
```

账户条件：

```text
2120积分
+
A股历史分钟独立权限
+
集合竞价独立权限
```

Token 基础有效性已经历史实际验证。

# 3. 其他来源定位

## 3.1 AKShare

当前定位：

```text
补充
验证
备用
```

第一阶段不要求把 AKShare 所有接口全部接入。

只有出现以下情况时才正式建立 SourceBinding：

- Tushare 当前权限无法覆盖；
- 需要多源交叉校验；
- Tushare 某数据项持续不可用；
- AKShare 能提供有明确研究价值的补充数据。

---

## 3.2 legacy_quantstock

旧 quantStock 定位：

```text
遗留历史数据来源
```

只能通过：

```text
LegacyMigrationBatch
```

受控迁移。

不能成为日常在线采集源。

# 5. 实施优先级

统一采用五级实施顺序：

```text
A：第一批基础闭环
B：财务与公司行为
C：资金和交易行为
D：指数和行业
E：高数据量专项
```

含义：

> A～E 只表示实施顺序，不表示后面的数据不采。

当前正式权限范围内、与 A 股研究相关的数据最终都进入采集规划。

# 10. 分钟数据长期存储原则

采集目录保留五种频率能力。

但内部长期存储默认优先：

```text
1分钟
```

5/15/30/60分钟在验证与1分钟聚合结果一致后：

```text
不默认长期保存五套完整历史副本
```

具体存储策略在 P4 数据治理与存储阶段确认。

# 26. 遗留 quantStock 数据域

旧项目中已经存在大量：

- 分钟；
- 日线；
- 每日指标；
- 复权因子；
- 财务；
- 事件；

```text

```

```text
stock_daily
```

区别只体现在 SourceBinding：

```text
source = legacy_quantstock
binding_type = migration
```

# 37. 本阶段结论

P3数据目录正式确定：

1. Tushare为主数据源；
2. AKShare为补充、验证、备用来源；
3. legacy_quantstock只用于受控历史迁移；
4. 数据目录以平台DataItem为稳定身份，不以外部API为业务身份；
5. 当前正式权限内的A股相关数据全部进入最终采集规划；
6. A～E只代表实施顺序；
7. 第一批先跑通七个基础DataItem，再用分钟和财务样本验证特殊场景；
8. 当前无权限接口保留能力目录但不创建正式任务；
9. 分钟五种频率保留采集能力，但长期存储策略后续单独确认；
10. 所有DataItem和SourceBinding必须可配置、可探测、可追踪；
11. 后续进入数据源接入规范和Tushare采集详细设计；
12. 全部正式启用接口的逐字段映射必须在详细设计阶段完成。
