# 数据源接入规范

> 路线图阶段：P3 数据源与采集平台  
> 项目：A股量化研究与信号决策平台（quantStock1）  
> 文档性质：详细设计——数据源接入基线  
> 日期：2026-07-27  
> 状态：已确认

---

# 1. 文档目的

本文件定义 quantStock1 接入外部和遗留数据源的统一规则。

当前数据源：

```text
Tushare
AKShare
legacy_quantstock
```

本文件解决：

1. 数据源如何注册；
2. DataItem 如何绑定来源；
3. Token 和其他凭据如何管理；
4. 接口权限如何探测；
5. 限频、单次返回上限如何统一管理；
6. 主数据源和备用数据源如何切换；
7. 数据源异常如何处理；
8. 旧 quantStock 如何只读迁移；
9. 为什么上层业务不能直接调用外部 SDK；
10. 新增数据源时如何避免修改整个系统。

---

# 2. 总体接入模型

统一采用：

```text
DataSource
    ↓
SourceBinding
    ↓
SourceAdapter
    ↓
Provider API / Legacy DB
```

DataItem 与数据源关系：

```text
DataItem
    ↓
一个或多个 SourceBinding
    ↓
具体来源
```

例如：

```text
DataItem：stock_daily
    ├─ Tushare / daily       主来源
    ├─ AKShare / 对应接口     备用或验证
    └─ legacy_quantstock     历史迁移来源
```

---

# 3. 核心边界

## 3.1 上层业务只认识 DataItem

以下模块：

- 清洗；
- 数据质量；
- DataContext；
- Feature；
- Strategy；
- Backtest；

不能依赖：

```text
Tushare.daily
AKShare具体函数
旧quantStock表名
```

它们只依赖平台标准 DataItem。

---

## 3.2 外部调用只能经过 Adapter

禁止：

```text
业务代码
↓
直接 import tushare
↓
直接调用 pro.daily()
```

正式路径：

```text
Collect Worker
↓
SourceBinding
↓
TushareAdapter
↓
Tushare SDK
```

AKShare同理。

# 4. DataSource 对象

DataSource 表示一个来源平台或来源系统。

当前：

| source_code | 名称 | 类型 | 当前定位 |
|---|---|---|---|
| `tushare` | Tushare | API | 主数据源 |
| `akshare` | AKShare | API/网页数据聚合 | 补充、验证、备用 |
| `legacy_quantstock` | 旧 quantStock | PostgreSQL/TimescaleDB | 只读历史迁移 |

全部进入 SourceBinding 或其版本化配置。

业务程序统一读取配置。

# 8. Tushare 权限模型

Tushare当前存在两种主要权限模式：

```text
积分型接口
+
独立购买权限接口
```

当前账户：

```text
2120积分
+
历史分钟权限
+
集合竞价权限
```

Token基础有效性已经历史实际验证。

因此系统不再设置：

```text
“Token是否存在”
```

作为唯一权限判断。

必须判断：

```text
Token有效
≠
所有接口都有权限
```

# 9. Tushare Credential 管理

Tushare Token：

```text
禁止进入Git
禁止进入Markdown
禁止写死源码
禁止打印普通日志
```

运行时通过：

```text
环境变量
或后续统一Secret机制
```

提供。

代码只读取：

```text
credential_ref
```

不把明文 Token 保存在 DataSource 表。

# 12. 接口级能力探测

Token已经验证，不代表每个接口都永久可用。

系统必须建立：

```text
CapabilityProbe
```

用于确认：

```text
当前账户
+
当前时间
+
当前接口
=
实际可调用状态
```

---

# 13. CapabilityProbe 触发时机

至少在以下情况执行：

## 首次启用 DataItem

必须探测。

## 系统部署或大版本升级

对已启用关键接口做抽样探测。

## 接口连续出现权限错误

立即更新状态。

## 用户积分或独立权限变化

重新探测相关接口。

## Tushare规则发生变化

重新探测受影响接口。

---

# 14. CapabilityProbe 不做什么

探测不是全量采集。

只使用：

```text
最小合法请求
```

确认：

- 接口存在；
- Token有权限；
- 返回结构正常；
- 当前字段与预期兼容；
- 当前限制没有明显变化。

避免能力探测本身消耗大量调用额度。

---

# 15. 能力探测状态

统一：

```text
unknown
available
permission_denied
schema_changed
temporarily_unavailable
rate_limited
provider_error
disabled
```

SourceBinding必须保存最近探测结果。

---

# 16. DataItem 状态与接口状态分离

例如：

```text
DataItem = stock_daily
status = enabled
```

但：

```text
Tushare SourceBinding
status = temporarily_unavailable
```

此时 DataItem 本身仍然存在。

如果还有有效备用来源，可以按规则切换。

---

# 17. Tushare RateLimiter

所有 Tushare 调用必须经过统一：

```text
RateLimiter
```

不能每个采集函数自己：

```text
sleep()
```

---

# 18. RateLimiter 管理维度

至少管理：

```text
source
api_name
permission_level
minute_window
daily_window
```

因为不同接口可能存在不同频率。

---

# 19. 限流配置来源

优先顺序：

```text
运行时接口级实测/当前配置
↓
当前官方具体接口文档
↓
当前官方总权限表
↓
历史参考资料
```

如果存在冲突：

```text
具体当前接口页
>
旧版权限汇总
```

不能把旧文档硬编码成永久事实。

---

# 20. 限流安全余量

系统不主动跑到理论极限。

例如配置：

```text
max_calls_per_minute = 200
```

运行调度可以设置：

```text
effective_limit < 200
```

留出：

- 重试；
- 人工调用；
- 能力探测；
- 其他任务；

的余量。

具体比例在性能测试阶段确定，不在本文件写死。

---

# 21. 单次最大返回行数

每个接口必须登记：

```text
max_rows_per_request
```

采集器必须知道：

```text
返回行数 == max_rows_per_request
```

是风险信号。

不能直接判断：

```text
本次范围已经完整
```

---

# 22. 上限命中处理

如果返回行数达到上限：

```text
当前范围
↓
进一步拆分
↓
重新请求
↓
直到子范围不再触顶
```

或者接口有可靠分页机制时使用分页。

禁止：

```text
直接接受可能被截断的数据
```

---

# 23. SplitPolicy

每个 SourceBinding 必须指定主要拆分维度。

可能包括：

```text
trade_date
ts_code
start_date/end_date
report_period
announcement_date
exchange
market
frequency
```

例如：

```text
daily
优先按 trade_date 全市场采集

stk_mins
优先按 ts_code + 时间窗口采集
```

---

# 24. RequestPolicy

请求策略配置至少包括：

```text
split_policy
page_policy
timeout
retry_policy
rate_limit_policy
max_range
fields
request_defaults
```

采集主流程不为每个接口写完全不同的控制逻辑。

---

# 25. Provider Error 标准化

外部来源错误统一转换为平台错误类型。

至少：

```text
AUTH_ERROR
PERMISSION_DENIED
RATE_LIMITED
TIMEOUT
NETWORK_ERROR
INVALID_REQUEST
SCHEMA_CHANGED
SOURCE_EMPTY
PROVIDER_ERROR
```

上层任务逻辑只处理平台错误。

---

# 26. 错误是否重试

## 可自动重试

```text
TIMEOUT
NETWORK_ERROR
临时 PROVIDER_ERROR
部分 RATE_LIMITED
```

## 不自动无限重试

```text
AUTH_ERROR
PERMISSION_DENIED
INVALID_REQUEST
SCHEMA_CHANGED
```

这些必须转入人工处理或配置修正。

---

# 27. RetryPolicy

重试配置至少：

```text
max_attempts
initial_delay
backoff_type
max_delay
retryable_errors
```

统一由平台控制。

禁止不同接口随意写：

```text
for i in range(100)
```

---

# 28. 数据源健康状态

DataSource级健康状态：

```text
healthy
degraded
unavailable
disabled
```

健康状态根据：

- 最近能力探测；
- 最近正式请求；
- 连续失败；
- 错误类型；

综合计算。

---

# 29. SourceBinding 健康状态更重要

不能因为：

```text
Tushare某一个接口失败
```

就把整个 Tushare 标记为完全不可用。

健康度至少分：

```text
DataSource
+
SourceBinding
```

两个层级。

---

# 30. 主数据源规则

当前主源：

```text
Tushare
```

对于已有正式 Tushare 来源的数据项：

```text
primary_source = tushare
```

AKShare不能因为一次Tushare失败就自动覆盖正式历史。

---

# 31. 备用源不能静默切换

严禁：

```text
Tushare失败
↓
自动用AKShare
↓
写进同一CLEAN
↓
不记录来源差异
```

因为两个来源可能存在：

- 时间定义差异；
- 复权差异；
- 单位差异；
- 字段计算差异；
- 历史修订差异。

---

# 32. 备用源切换条件

只有满足：

1. DataItem 已有备用 SourceBinding；
2. 字段映射已经定义；
3. 数据语义已经验证兼容；
4. 冲突规则已定义；
5. 当前主源明确不可用；

才能使用备用源。

---

# 33. 备用源使用仍进入 RAW

路径：

```text
AKShare
↓
AKShareAdapter
↓
RAW
↓
Quality
↓
CLEAN
```

不能直接替换 CLEAN。

来源必须保留：

```text
source = akshare
```

---

# 34. 多源冲突

同一业务事实出现：

```text
Tushare值 != AKShare值
```

不能由程序随意选择。

建立：

```text
SourceConflict
```

至少记录：

```text
data_item_id
business_key
source_a
value_a/hash_a
source_b
value_b/hash_b
detected_at
resolution_status
resolution_rule
```

---

# 35. SourcePriority

DataItem定义来源优先级。

例如：

```text
stock_daily
1 = tushare
2 = akshare
3 = legacy_quantstock（仅历史迁移）
```

优先级不代表：

```text
低优先级数据一定错误
```

只决定正常情况下使用哪个来源形成正式数据。

---

# 36. AKShare 接入原则

AKShare属于：

```text
开源数据接口聚合能力
```

平台将其视为普通外部数据源。

不能因为免费就降低数据治理要求。

---

# 37. AKShare Adapter

正式接入某个AKShare数据项时，必须建立：

```text
AKShare SourceBinding
```

明确：

- 函数；
- 参数；
- 数据来源网站；
- 字段；
- 单位；
- 更新时间；
- 稳定性；
- 历史范围；
- 质量规则。

---

# 38. AKShare 接口变更处理

如果网站或AKShare版本导致：

```text
字段变化
返回结构变化
接口失效
```

状态应进入：

```text
schema_changed
或
temporarily_unavailable
```

不能静默产生错误CLEAN数据。

---

# 39. AKShare版本

正式部署必须固定：

```text
AKShare Python包版本
```

不能生产环境每次构建自动安装最新版本。

升级：

```text
dev验证
↓
test验证
↓
SourceBinding兼容验证
↓
prod
```

---

# 40. legacy_quantstock 接入类型

旧 quantStock 不是常规在线 DataSource。

它的：

```text
source_type = legacy_database
```

绑定类型：

```text
binding_type = migration_only
```

禁止：

```text
scheduled_collection = true
```

---

# 41. 旧数据库权限

新项目迁移程序连接旧数据库必须使用：

```text
只读账户
```

仅允许：

```text
SELECT
```

禁止：

```text
INSERT
UPDATE
DELETE
CREATE
ALTER
DROP
```

---

# 42. 旧数据库访问生命周期

只在：

```text
LegacyMigrationBatch
```

执行期间访问旧库。

正式日常业务：

```text
不得依赖旧库可用性
```

旧 quantStock以后关停：

```text
不能影响新 quantStock1
```

---

# 43. 旧数据来源身份

旧数据库里的数据可能原本来自：

```text
Tushare
```

因此必须区分：

```text
origin_source = tushare
ingestion_source = legacy_quantstock
```

含义：

- 原始事实来自Tushare；
- 本次进入新项目是从旧系统迁移。

---

# 44. 数据来源链

迁移数据完整来源：

```text
Tushare
↓
旧 quantStock
↓
LegacyMigrationBatch
↓
新 quantStock1
```

不能简单记录：

```text
source = legacy
```

后就失去最初数据来源。

---

# 45. 数据源调用审计

每次外部正式调用至少记录：

```text
source_id
source_binding_id
collect_run_id
api_name
request_range
request_hash
started_at
finished_at
response_rows
result
error_type
retry_count
```

敏感参数必须脱敏。

---

# 46. 禁止记录Token

无论：

- 请求日志；
- 异常堆栈；
- AuditEvent；
- Debug日志；

都不能输出真实Token。

---

# 47. 字段选择

如果Tushare接口支持：

```text
fields
```

正式 SourceBinding 应明确需要的字段。

但第一阶段建立RAW时：

> 不应为了节省几个字段而丢失未来有研究价值的正式返回字段。

最终字段集合由逐字段映射设计确定。

---

# 48. SchemaFingerprint

SourceBinding应保存外部接口当前结构指纹。

例如根据：

```text
字段名
字段顺序（如果有意义）
类型
```

生成：

```text
schema_fingerprint
```

运行时发现结构明显变化：

```text
暂停该Binding进入CLEAN
```

等待确认。

---

# 49. FieldMappingVersion

外部字段到平台标准字段映射必须版本化：

```text
field_mapping_version
```

Tushare字段发生变化时：

```text
新增映射版本
```

不直接修改历史定义后让旧批次失去解释。

---

# 50. UpdateAvailabilityRule

每个DataItem必须明确：

```text
什么时候理论上应该有新数据
```

例如：

- 收盘后；
- 周末；
- 月末；
- 财报公告后；
- 事件发生后。

不能所有接口统一：

```text
每天15:30采集
```

---

# 51. 调度不直接绑定API

Scheduler根据：

```text
DataItem
+
UpdatePolicy
```

创建任务。

任务再通过：

```text
SourceBinding
```

找到具体数据源。

这样以后切换来源时：

```text
不改Scheduler业务逻辑
```

---

# 52. 运行时Binding选择

正常流程：

```text
DataItem
↓
找到enabled SourceBinding
↓
按priority排序
↓
检查能力/健康状态
↓
选择合法来源
```

但备用切换必须遵守前述兼容性规则。

---

# 53. Interface Probe 与正式运行分离

接口探测：

```text
probe_run
```

正式采集：

```text
collect_run
```

两者记录分开。

不能用一次正式大采集来判断：

```text
“接口有没有权限”
```

---

# 54. 数据源启停

停用一个SourceBinding：

```text
enabled = false
```

应做到：

- 不再创建新采集任务；
- 已有历史数据不删除；
- 已完成追溯不破坏；
- 可以以后重新启用。

---

# 55. DataSource退役

DataSource进入：

```text
retired
```

后：

- 不再允许新的在线采集；
- 历史Binding保留；
- 历史Raw保留来源标识；
- 历史Clean仍可追溯。

---

# 56. 接口删除或废弃

如果Tushare以后废弃某API：

```text
SourceBinding -> deprecated/disabled
```

DataItem仍然存在。

再建立：

```text
新的SourceBinding
```

上层业务不改变DataItem身份。

---

# 57. 配置变更审计

以下变化必须有审计：

- SourceBinding启停；
- priority变化；
- 限频变化；
- 最大行数变化；
- 字段映射版本变化；
- API名称变化；
- 权限状态变化；
- 主备用关系变化。

---

# 58. 生产配置边界

运行时可调整的业务配置放数据库。

例如：

```text
enabled
priority
effective_rate_limit
```

密钥：

```text
不进入数据库明文字段
```

代码级稳定配置：

```text
由Git版本管理
```

---

# 59. 第一批Tushare Binding

P3第一批至少建立：

```text
stock_basic
trade_calendar
stock_daily
stock_adj_factor
stock_daily_basic
stock_suspend
stock_limit_price
```

对应SourceBinding。

再建立测试性：

```text
stock_minute 1m

```

验证特殊采集模式。

---

# 60. 第一批不做自动主备切换

为了降低复杂度，第一批：

```text
Tushare = 正式主源
```

AKShare：


未来新增一个新Provider：

```text

2. 实现Adapter
3. 为目标DataItem创建SourceBinding
4. 定义字段映射
5. 定义请求策略
6. 定义限频
7. 定义质量规则
8. 能力探测
9. test验证
10. 正式启用
```

不修改已经稳定的上层业务对象。

# 65. P3接入规范验收条件

数据源接入能力完成时必须验证：

1. Token不会进入Git和日志；
2. Tushare只通过统一Adapter调用；
3. 接口权限可以独立探测；
4. SourceBinding能保存接口限制；
5. 达到单次返回上限时会继续拆分；
6. RATE_LIMITED能正确退避；
7. PERMISSION_DENIED不会无限重试；
8. 单个接口失败不会让整个数据源失效；
9. Binding可以独立启停；
10. AKShare数据保留真实来源；
11. 备用来源不会静默覆盖主源；
12. 旧quantStock只读；
13. 旧系统关闭不会影响新项目；
14. 外部Schema变化可以被发现；
15. 字段映射有版本；
16. 所有调用可追溯到CollectRun。

# 66. 官方依据

Tushare当前官方说明确认：

- 权限包括积分型接口和独立购买权限接口；
- Python SDK通过Token初始化；
- 不同接口具有独立的积分、频次和单次返回限制；
- 例如`stock_basic`当前为2000积分起、单次最多6000行、每分钟50次；
- `daily_basic`当前为2000积分起、单次最多6000行，并有独立更新时间和调用规则。


# 67. 最终结论

quantStock1数据源接入标准确定为：

```text
DataItem
↓
SourceBinding
↓
统一Adapter
↓
外部数据源
```

关键决策：

1. Tushare是第一阶段正式主源；
2. AKShare是补充、验证和备用源；
3. 旧quantStock只能作为只读迁移源；
4. 上层业务不能直接调用Tushare/AKShare；
5. Token等凭据不进入代码、Git、Markdown和普通日志；
6. 每个接口独立管理权限、频率、单次上限和拆分策略；
7. Token有效不代表所有接口可用；
8. 必须建立接口级CapabilityProbe；
9. 返回数量触及上限必须继续拆分或分页；
10. 外部错误统一转换为平台错误；
11. 主备用源不能静默切换；
12. 多源冲突必须留下正式记录；
13. 外部字段映射必须版本化；
14. Scheduler只依赖DataItem和更新策略，不直接绑定API；
15. 新增数据源不修改上层研究架构；
16. 第一批暂不建设复杂自动多源故障切换。
