# 补采重试幂等与限频设计

> 路线图阶段：P3 数据源与采集平台  
> 项目：A股量化研究与信号决策平台（quantStock1）  
> 文档性质：详细设计——补采、重试、幂等与限频  
> 日期：2026-07-27  
> 状态：已确认

---

# 1. 设计目标

本文件定义采集平台在以下场景下如何保持可靠：

```text
采集失败
数据缺口
来源延迟
接口限频
重复调度
Worker崩溃
人工补采
重复补采
同一数据多次返回
```

核心目标：

1. 临时故障能够自动恢复；
2. 永久错误不能无限重试；
3. 缺口能够准确补齐；
4. 重复任务不会产生重复业务数据；
5. 同一业务目标只能有一个有效正常任务；
6. 已失败历史不能被改写；
7. Tushare调用统一限频；
8. 多Worker以后仍可扩展到全局限频。

---

# 2. 四个概念必须分开

## 2.1 RETRY

针对：

```text
同一个采集目标
由于临时错误再次执行
```

例如：

```text
网络超时
Tushare临时错误
限流
```

---

## 2.2 BACKFILL

针对：

```text
用户主动指定历史范围重新补数据
```

例如：

```text
补2020-01-01～2020-03-31的daily
```

---

## 2.3 REPAIR

针对：

```text
系统质量检查发现明确DataGap
```

自动或人工触发修复。

---

## 2.4 RERUN

针对：

```text
已经成功过
但用户认为结果可疑
要求重新采集验证
```

RERUN不是RETRY。

---

# 3. 执行事实不可覆盖

例如：

```text
Run-001
状态 = failed
```

重试后：

```text
Run-002
状态 = succeeded
```

系统最终可以认为业务目标完成。

但必须永久保留：

```text
Run-001失败
Run-002成功
```

禁止：

```text
把Run-001状态直接改成succeeded
```

否则失去真实故障历史。

---

# 4. 任务目标与执行实例分离

统一：

```text
CollectTask
=
业务目标

CollectRun
=
一次真实执行
```

例如：

```text
CollectTask：
stock_daily / 2026-07-24

Run-001：
第一次执行，超时失败

Run-002：
重试执行，成功
```

---

# 5. RequestSlice同样保留执行历史

一个Slice可以有：

```text
SliceExecution-001
SliceExecution-002
...
```

或者在Slice内部记录attempt历史。

具体物理表结构后续实现确定。

原则必须满足：

```text
每次真实外部调用可追溯
```

---

# 6. 错误分类

所有外部和内部错误统一转换为平台错误类型。

第一阶段至少：

```text
AUTH_ERROR
PERMISSION_DENIED
RATE_LIMITED
TIMEOUT
NETWORK_ERROR
INVALID_REQUEST
SCHEMA_CHANGED
PROVIDER_ERROR
SOURCE_EMPTY
SOURCE_LATE
WRITE_FAILED
DATABASE_ERROR
POSSIBLE_TRUNCATION
QUALITY_BLOCKED
CAPACITY_BLOCKED
WORKER_LOST
CANCELLED
UNKNOWN_ERROR
```

---

# 7. 错误分类目的

错误分类直接决定：

```text
是否重试
什么时候重试
是否暂停Binding
是否需要人工处理
是否需要拆分Slice
```

不能所有错误统一：

```text
sleep 5秒再重试
```

---

# 8. 自动重试错误

默认允许自动重试：

```text
NETWORK_ERROR
TIMEOUT
临时PROVIDER_ERROR
RATE_LIMITED
DATABASE_ERROR（确定为临时故障时）
WORKER_LOST
```

---

# 9. 不应自动无限重试

以下默认不能自动无限重试：

```text
AUTH_ERROR
PERMISSION_DENIED
INVALID_REQUEST
SCHEMA_CHANGED
CAPACITY_BLOCKED
CANCELLED
```

处理：

```text
停止当前自动重试
↓
更新可见状态
↓
等待配置修正 / 人工处理
```

---

# 10. POSSIBLE_TRUNCATION不是普通失败

如果：

```text
response_rows == max_rows_per_request
```

进入：

```text
POSSIBLE_TRUNCATION
```

标准处理：

```text
拆分当前Slice
↓
生成子Slice
↓
重新请求
```

不是简单重复完全相同请求。

---

# 11. SOURCE_EMPTY处理

空结果需要分类。

## EXPECTED_EMPTY

正常。

例如：

```text
股票上市前
非交易日
某股票当天停牌且接口本就不返回
```

## SUSPICIOUS_EMPTY

异常。

例如：

```text
正常交易日全市场daily = 0行
```

## UNKNOWN_EMPTY

当前无法判断。

需要：

```text
质量检查
或
短延迟重试
```

---

# 12. SOURCE_LATE

数据已经到理论更新时间，但来源暂时还未发布。

处理：

```text
waiting_source
↓
延迟检查
↓
再次请求
```

SOURCE_LATE不是：

```text
接口故障
```

---

# 13. RetryPolicy

每个SourceBinding可以配置：

```text
max_attempts
initial_delay
backoff_type
backoff_factor
max_delay
retryable_errors
jitter
```

配置属于运行策略，不硬编码到各接口。

---

# 14. 默认退避模型

第一阶段推荐：

```text
指数退避
+
随机抖动
```

逻辑：

```text
第一次失败
↓
等待较短时间

连续失败
↓
逐步延长等待

达到max_delay
↓
不再无限增长
```

随机抖动用于避免以后多个Worker同时再次请求。

---

# 15. 不写死重试次数

框架不规定：

```text
所有接口都重试3次
```

不同DataItem可以使用不同RetryPolicy。

例如：

```text
日常关键daily
```

与：

```text
低优先级历史股东数据
```

可以不同。

---

# 16. RateLimit错误处理

收到明确限频：

```text
RATE_LIMITED
```

处理：

```text
暂停该SourceBinding新的请求
↓
记录限频事件
↓
按退避策略等待
↓
降低有效请求速率
↓
恢复
```

禁止：

```text
立即高速循环重试
```

---

# 17. documented_limit

SourceBinding保存：

```text
documented_limit
```

表示：

```text
当前官方文档或确认资料中的上限
```

---

# 18. effective_limit

运行时真正使用：

```text
effective_limit
```

必须满足：

```text
effective_limit <= documented_limit
```

系统不主动跑满理论最大值。

---

# 19. 为什么不跑满官方限制

需要为：

- 重试；
- CapabilityProbe；
- 人工任务；
- 规则变化；
- 网络抖动；

保留安全余量。

具体安全余量由实测决定，不在本文件固定百分比。

---

# 20. 限频维度

第一阶段RateLimiter至少按：

```text
source_id
+
source_binding/api
```

管理。

不能只使用：

```text
Tushare全局一个sleep
```

因为不同接口限制不同。

---

# 21. 未来多Worker限频

第一阶段：

```text
单Worker优先
```

可使用进程内限频+数据库状态。

以后出现多个Worker后：

```text
必须升级成全局限频
```

确保：

```text
多个Worker总调用量
<=
账户限制
```

不能每个Worker各自认为自己拥有完整额度。

---

# 22. 第一阶段不因此引入Redis

全局限频未来可以：

```text
PostgreSQL
或
Redis
```

实现。

第一阶段不因为一个未来需求就提前把Redis变成核心依赖。

---

# 23. Token Bucket / Sliding Window

RateLimiter内部实现可以选：

```text
Token Bucket
或
Sliding Window
```

具体算法由实现阶段决定。

业务层只依赖统一接口：

```text
acquire(binding, cost=1)
```

---

# 24. 每日调用额度

如果某接口存在每日额度：

系统必须同时维护：

```text
minute_limit
day_limit
```

不能只满足每分钟频率，却在当天提前耗尽总额度。

---

# 25. 调用额度优先级

当资源有限时：

```text
P0 日常关键增量
>
P1 Repair
>
P2 Retry
>
P3 初始化
>
P4 低优先级历史扩展
```

不能让历史全量耗尽当天额度，导致最新日线无法采集。

---

# 26. RateLimiter与Scheduler职责分离

Scheduler：

```text
决定任务是否应该存在
```

RateLimiter：

```text
决定此刻能不能调用外部接口
```

Scheduler不能为了限频自己维护大量sleep逻辑。

---

# 27. 补采触发来源

BACKFILL可以来自：

```text
用户
运维API
管理员操作
```

REPAIR可以来自：

```text
DataGap
质量扫描
自动对账
```

---

# 28. BACKFILL请求参数

至少包括：

```text
data_item
object_scope
start_time
end_time
frequency（需要时）
source_binding（可选）
reason
requested_by
```

---

# 29. BACKFILL不能绕过正常采集框架

正式路径仍然：

```text
BACKFILL Task
↓
Planner
↓
RequestSlice
↓
Adapter
↓
RateLimiter
↓
RAW
```

禁止单独写脚本：

```text
临时从Tushare下载
直接INSERT数据库
```

否则失去追溯。

---

# 30. REPAIR必须绑定DataGap

自动Repair：

```text
DataGap
↓
RepairTask
```

RepairTask必须保存：

```text
gap_id
```

修复完成后：

```text
重新质量检查
↓
确认缺口关闭
```

不能采到数据就直接把Gap标记解决。

---

# 31. Gap关闭条件

只有：

```text
补采成功
+
CLEAN成功
+
对应质量规则重新通过
```

才：

```text
DataGap = resolved
```

---

# 32. Repair失败

Repair失败：

```text
DataGap仍保持open
```

并记录：

```text
repair_run_id
last_error
retry_count
```

---

# 33. 幂等的目标

幂等不是：

```text
重复请求绝对不会发生
```

而是：

> 同一个业务事实被重复请求、重试或补采时，不会产生不可控重复结果。

---

# 34. 三层幂等

平台采用：

```text
任务幂等
请求幂等
数据幂等
```

三个层次。

---

# 35. 任务幂等

同一个正常调度目标：

```text
DataItem
+
SourceBinding
+
run_type
+
object_scope
+
time_scope
+
frequency
```

生成稳定：

```text
task_idempotency_key
```

数据库建立唯一约束。

---

# 36. 为什么必须数据库唯一约束

禁止只依赖：

```text
SELECT有没有
↓
没有就INSERT
```

因为两个Scheduler并发时可能：

```text
同时查到没有
↓
同时创建
```

正确方式：

```text
数据库唯一约束
+
INSERT冲突处理
```

---

# 37. 不同run_type不应互相阻止

例如：

```text
INCREMENTAL / 2026-07-27
```

已经成功。

用户仍可以：

```text
RERUN / 2026-07-27
```

因为RERUN是新的业务意图。

所以：

```text
run_type
```

属于幂等键的一部分。

---

# 38. 请求幂等

外部请求生成：

```text
request_hash
```

来源：

```text
source_binding
api_name
规范化request_params
field_mapping_version
```

用于识别：

```text
完全相同请求是否已经发生
```

但历史审计仍保留每次真实调用。

---

# 39. 数据幂等

RAW：

```text
content_hash
```

用于识别完全相同正文。

CLEAN：

```text
业务唯一键
+
版本语义
```

控制正式数据。

---

# 40. 日级CLEAN幂等

例如：

```text
stock_daily
(ts_code, trade_date)
```

重复获取完全相同数据：

```text
不产生第二条正式记录
```

如果来源数据发生变化：

```text
形成变更审计
```

再按DataItem规则决定更新CLEAN。

---

# 41. 财务CLEAN幂等

财务不能：

```text
(ts_code, report_period)
```

直接覆盖。

正式身份需要：

```text
版本ID
+
公告/修订语义
+
content_hash
```

相同版本重复到达不新增正文。

新修订则新增版本。

---

# 42. 事件数据幂等

事件数据：

```text
业务自然键
+
content_hash
```

确定。

业务键由DataItem单独定义。

不能统一使用：

```text
ts_code + trade_date
```

---

# 43. 分钟数据幂等

CLEAN唯一：

```text
ts_code
+
frequency
+
trade_time
```

重复采集同一bar：

- 完全一致：不重复；
- 内容发生变化：记录来源变化，再按修订策略处理。

---

# 44. RAW是否保存完全重复正文

默认：

```text
完全相同content_hash
```

不重复写数据正文。

但：

```text
CollectRun
RawBatch
request调用事实
```

仍保留。

这样既能审计，又避免大量重复存储。

---

# 45. 重试与幂等

RETRY可能再次获得：

```text
上次其实已经写成功
但客户端没收到成功响应
```

因此写入必须支持：

```text
重复提交不会产生重复业务数据
```

这是幂等最重要的实际场景之一。

---

# 46. 数据库事务

推荐顺序：

```text
外部请求成功
↓
建立RawBatch
↓
RAW幂等写入
↓
提交事务
↓
更新Slice成功
```

如果事务失败：

```text
Slice不能成功
```

重试时依赖RAW幂等安全再次写入。

---

# 47. Exactly Once不作为外部调用目标

Tushare请求无法做到严格：

```text
exactly once
```

因为网络中断时可能不知道服务端是否已经处理。

平台采用：

```text
at-least-once外部调用
+
内部幂等写入
```

实现可靠最终结果。

---

# 48. Worker Lease

Worker领取任务后记录：

```text
leased_by
leased_at
lease_expires_at
heartbeat_at
```

只有持有有效Lease的Worker可以更新当前执行状态。

---

# 49. Lease续期

长任务：

```text
定期heartbeat
↓
延长lease
```

如果heartbeat消失：

```text
lease过期
```

任务进入恢复流程。

---

# 50. Worker Lost

检测：

```text
running
+
lease_expires_at < now
```

标记：

```text
WORKER_LOST
```

随后：

```text
产生恢复执行
或
Slice重新pending
```

不能永久卡在running。

---

# 51. 重试所有权

一个Slice同一时刻只能有：

```text
一个有效执行者
```

依赖数据库原子领取。

推荐：

```text
SELECT ... FOR UPDATE SKIP LOCKED
```

或等价数据库机制。

---

# 52. Retry Storm防护

外部来源整体故障时，不能几千任务同时：

```text
失败
↓
立即重试
```

必须有：

```text
Binding级熔断
```

---

# 53. Binding级熔断

如果同一SourceBinding在短时间连续出现：

```text
相同Provider级错误
```

进入：

```text
open
```

状态。

此时：

```text
暂停新的真实外部调用
```

任务保持等待。

---

# 54. Circuit Breaker状态

```text
closed
↓
open
↓
half_open
↓
closed
```

含义：

```text
closed = 正常调用
open = 暂停调用
half_open = 少量探测恢复
```

---

# 55. 什么错误不触发Provider熔断

例如：

```text
单股票参数问题
单个数据项Schema问题
单次业务空结果
```

不能把整个Tushare熔断。

熔断范围优先：

```text
SourceBinding
```

不是整个DataSource。

---

# 56. 权限错误处理

出现：

```text
PERMISSION_DENIED
```

处理：

```text
当前Run失败
↓
SourceBinding标记permission_denied
↓
暂停新任务实际调用
↓
等待CapabilityProbe/配置变化
```

不能每天继续制造同样的失败。

---

# 57. Token认证失败

```text
AUTH_ERROR
```

属于DataSource级高优先级故障。

处理：

```text
暂停Tushare正式调用
↓
告警
↓
等待凭据修复
```

不在日志打印Token。

---

# 58. Schema变化处理

```text
SCHEMA_CHANGED
```

处理：

```text
暂停该Binding进入CLEAN链
↓
保留原始响应证据（安全方式）
↓
更新字段映射
↓
测试
↓
恢复
```

不能把列错位的数据继续写成正常数据。

---

# 59. 数据库错误

数据库临时断开：

```text
DATABASE_ERROR
```

可以重试。

但：

```text
磁盘满
```

应转换成：

```text
CAPACITY_BLOCKED
```

不能无限重试写盘。

---

# 60. 容量保护

达到容量保护线时：

```text
暂停P3/P4历史大任务
```

优先保留：

```text
P0日常关键增量
```

如果继续写入也有风险，则系统必须：

```text
整体进入保护状态
```

不能把磁盘写满。

---

# 61. 重试优先级

推荐：

```text
P0 日常关键任务临时重试
P1 关键Gap Repair
P2 普通Retry
P3 人工Backfill
P4 历史初始化重试
```

但人工可在受控情况下调整。

---

# 62. BACKFILL优先级

用户主动补采默认不能压过：

```text
当日正式增量
```

除非用户明确提升优先级。

---

# 63. 补采范围拆分

BACKFILL仍按正常SplitPolicy：

```text
日级 -> 交易日
分钟 -> 股票+时间窗
财务 -> 股票/报告期
事件 -> 时间窗口
```

不因为是人工任务就跳过截断保护。

---

# 64. 补采来源选择

默认使用：

```text
DataItem当前主SourceBinding
```

如果用户指定备用来源：

必须记录：

```text
requested_source
reason
```

并仍经过正式Adapter和RAW。

---

# 65. 多源补采

如果Tushare缺口改由AKShare补：

```text
source = akshare
```

必须真实保留。

不能伪装成Tushare数据。

---

# 66. 旧quantStock补历史

如果DataGap范围在旧quantStock中存在：

可以创建：

```text
MIGRATION/REPAIR
```

而不是重新调用Tushare。

但必须先通过迁移质量规则。

---

# 67. 手工操作审计

# 93. 最终结论

补采、重试、幂等和限频统一设计为：

```text
错误分类
↓
RetryPolicy
↓
RateLimiter
↓
Task/Run分离
↓
数据库幂等约束
↓
RAW/CLEAN数据幂等
↓
Gap Repair闭环
```

关键决策：

1. RETRY、BACKFILL、REPAIR、RERUN严格分开；
2. 失败执行永不改写为成功；
3. 临时错误自动重试，永久错误停止自动重试；
4. 触及行数上限走Split，不走原请求重试；
5. 所有Tushare调用统一RateLimiter；
6. 有documented_limit和effective_limit两层；
7. 日常关键任务优先获得调用额度；
8. 不为限频提前引入Redis核心依赖；
9. 任务幂等依赖数据库唯一约束；
10. 外部调用按at-least-once设计，内部写入必须幂等；
11. 财务修订不是重复数据；
12. Gap只有重新质量通过后才算修复；
13. Worker Lease保证失联任务可恢复；
14. Binding级熔断防止Retry Storm；
15. 权限错误会暂停Binding，不会每天无限失败；
16. 所有人工补采和强制重跑必须审计。
