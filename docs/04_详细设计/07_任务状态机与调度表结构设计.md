# 任务状态机与调度表结构设计

> 路线图阶段：P3 数据源与采集平台  
> 项目：A股量化研究与信号决策平台（quantStock1）  
> 文档性质：详细设计——任务、调度与断点恢复  
> 日期：2026-07-27  
> 状态：已确认

---

# 1. 设计目标

本文件把前面已经确认的：

```text
历史初始化
日常增量
补采
Repair
Retry
断点续传
幂等
限频
Worker Lease
```

落实为一套可直接开发的 PostgreSQL 任务模型。

第一阶段不采用 Celery。

任务事实、执行状态和断点全部保存到 PostgreSQL。

核心架构：

```text
Scheduler
    ↓
CollectTask
    ↓
CollectRun
    ↓
RequestSlice
    ↓
Worker原子领取
    ↓
执行
    ↓
RawBatch
```

---

# 2. 设计原则

## 2.1 业务目标与真实执行分离

```text
Task = 要完成什么
Run  = 某一次真实执行
```

不能混成一张表。

例如：

```text
Task：
采集2026-07-24全市场daily

Run-001：
第一次执行，网络失败

Run-002：
Retry后成功
```

Task最终可以完成。

Run-001仍永久保留为失败事实。

---

## 2.2 大任务与外部请求分离

```text
Task
↓
Slice
↓
外部API请求
```

一个Task可以包含很多Slice。

例如分钟历史：

```text
Task：
000001.SZ 2020-2025 1min

Slice：
2020-01-01～2020-01-31
2020-02-01～2020-02-29
...
```

---

## 2.3 所有关键状态落库

禁止唯一状态存在于：

- Python内存；
- Worker本地文件；
- Docker临时目录；
- 日志文本。

数据库是任务事实的唯一正式来源。

```text

↓

├─→ SUCCEEDED
├─→ PARTIAL
├─→ FAILED
```

```text

```

---

# 11. Task合法状态流转

允许：

```text
PENDING -> RUNNING
PENDING -> CANCELLED

RUNNING -> SUCCEEDED
RUNNING -> PARTIAL
RUNNING -> FAILED
RUNNING -> PAUSED
RUNNING -> CANCELLED
RUNNING -> WAITING_SOURCE
RUNNING -> WAITING_RATE_LIMIT
RUNNING -> WAITING_DEPENDENCY
RUNNING -> CAPACITY_BLOCKED

WAITING_SOURCE -> PENDING
WAITING_SOURCE -> FAILED
WAITING_SOURCE -> CANCELLED

WAITING_RATE_LIMIT -> PENDING
WAITING_RATE_LIMIT -> CANCELLED

WAITING_DEPENDENCY -> PENDING
WAITING_DEPENDENCY -> FAILED
WAITING_DEPENDENCY -> CANCELLED

CAPACITY_BLOCKED -> PENDING
CAPACITY_BLOCKED -> CANCELLED

PAUSED -> PENDING
PAUSED -> CANCELLED

PARTIAL -> PENDING
PARTIAL -> FAILED
PARTIAL -> CANCELLED
```

---

# 12. 不允许的状态流转

例如：

```text
FAILED -> SUCCEEDED
CANCELLED -> RUNNING
SUCCEEDED -> RUNNING
```

都不允许直接修改。

需要重新执行：

```text
建立新的Run
或新的RERUN Task
```

保留历史事实。


# 22. SPLIT状态

当：

```text
POSSIBLE_TRUNCATION
```

或当前窗口太大时：

```text
父Slice -> SPLIT
↓
生成多个子Slice
```

父Slice以后不再实际执行。

完成条件由全部叶子子Slice决定。

```text

```

维护。

必须设置：

```text

```

防止错误接口无限递归拆分。

# 28. Checkpoint与Slice关系

如果任务已经完全Slice化：

```text

```

本身就是主要Checkpoint。

`task_checkpoint`主要保存：

- Lazy Planning游标；
- 当前生成到哪个股票；
- 当前生成到哪个日期；
- 迁移扫描游标；
- 大范围进度汇总。

避免重复保存大量Slice状态。

# 32. Worker heartbeat

Worker定期更新：

```text
heartbeat_at
```

具体周期不在P3写死。

必须满足：

```text
明显短于Lease超时
```

例如未来：

```text
heartbeat 10秒
lease 60秒
```

只是实现期可选值，不是当前正式固定参数。

---

# 33. Worker优雅退出

部署或维护时：

```text
ONLINE
↓
DRAINING
```

DRAINING状态：

```text
不领取新Slice
当前Slice安全结束
↓
OFFLINE
```

减少人为发布造成的假LOST。

---

# 34. Worker原子领取

推荐PostgreSQL模式：

```sql
SELECT slice_id
FROM ops.request_slice
WHERE status = 'PENDING'
  AND (next_retry_at IS NULL OR next_retry_at <= now())
ORDER BY priority ASC, slice_order ASC
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

在同一短事务内：

```text
更新为RUNNING
写入leased_by
写入lease_expires_at
创建Attempt/Run关联
提交
```

---

# 35. 为什么使用SKIP LOCKED

多个Worker同时领取时：

```text
不会拿到同一个Slice
```

同时不需要额外引入RabbitMQ/Celery。

PostgreSQL本身已经是系统核心依赖。

---

# 36. 领取事务必须短

禁止：

```text
SELECT FOR UPDATE
↓
保持数据库事务打开
↓
去Tushare请求几十秒
```

正确：

```text
短事务领取
↓
提交
↓
外部请求
↓
新事务写结果
```

Lease负责执行期间所有权。

---

# 37. Lease字段

Slice使用：

```text
leased_by
leased_at
lease_expires_at
heartbeat_at
```

---

# 38. Lease续期

Worker执行较长Slice时：

```text
定期续期
```

但每次续期都必须确认：

```text
leased_by == 当前worker
status == RUNNING
```

避免过期Worker回来后覆盖新Worker状态。

---

# 39. Fence防旧Worker回写

重要规则：

> Lease过期后，旧Worker不能继续把结果写成成功。

实现建议增加：

```text
lease_token
```

每次领取生成新的随机token。

Worker提交结果时必须带：

```text
slice_id + lease_token
```

数据库条件更新：

```text
WHERE slice_id = ?
AND lease_token = ?
AND status = 'RUNNING'
```

如果0行更新：

```text
说明Lease已经失效
```

旧Worker结果不得改变正式状态。

---

# 40. request_slice增加lease_token

因此正式建议字段增加：

```text
lease_token UUID NULL
```

这是防止：

```text
失联Worker复活后误覆盖
```

的重要保护。

# 43. 第一阶段Scheduler互斥

最简单方式：

```text
PostgreSQL advisory lock
```

例如：

```text
quantstock1_scheduler_prod
```

只有获得锁的实例：

```text
成为LEADER
```

其余退出或进入STANDBY。

不用因此增加新的协调组件。

---

# 44. 为什么Scheduler仍需要任务唯一约束

即使有Leader锁，也必须保留：

```text
task idempotency UNIQUE
```

因为：

- 崩溃切换；
- 手工误启动；
- 以后多Scheduler；
- 重复扫描；

都可能重复尝试建任务。

最终防线必须在数据库。

---

# 45. Scheduler主循环

逻辑：

```text
获取Leader锁
↓
更新heartbeat
↓
读取enabled task_definition
↓
计算expected watermark
↓
比较current watermark
↓
创建缺失Task（幂等）
↓
维护等待任务
↓
识别LOST Worker/Lease
↓
触发Lazy Planning
↓
容量/健康检查
↓
记录last_scan_at
```

---

# 46. Scheduler不执行外部请求

禁止：

```text

↓

```

唯一例外：

```text

```

正式CapabilityProbe也应该作为Task交给Worker。

# 49. Watermark不能代替DataGap

例如：


```text

```

因此：

```text

DataGap = 中间缺口
```

两者必须同时存在。

# 54. 为什么不做复杂DAG

当前任务主要是数据采集。

引入：

- Airflow式DAG；
- 通用工作流引擎；
- 可视化编排；

会明显增加维护复杂度。

第一阶段只实现真实需要的DataItem依赖。

# 59. RETRY_WAIT

Slice字段：

```text

```

Worker领取查询只选择：

```text
next_retry_at IS NULL
OR next_retry_at <= now()
```

无需在Worker里长期sleep占资源。

---

# 60. 为什么不能Worker sleep几小时

例如来源延迟：

```text
等待2小时
```

不能让Worker进程：

```text
sleep(7200)
```

占据执行槽。

正确：

```text
更新状态
写next_retry_at
释放Worker
```

---

# 61. Task完成计算

Task状态不应由某个Worker随意判断。

建议统一函数/服务根据叶子Slice汇总：

```text
全部叶子SUCCEEDED
→ SUCCEEDED

有失败且还有可继续
→ PARTIAL / RUNNING

全部终止且存在失败
→ FAILED

用户取消
→ CANCELLED
```

---

# 62. SPLIT父Slice不参与成功计数

父Slice：

```text
SPLIT
```

以后只作为结构节点。

Task完成判断只看：

```text
叶子Slice
```

---

# 63. Lazy Planner

分钟等大任务不一次建全部Slice。

Scheduler/Planner维护：

```text
planning_cursor
```

并限制：

```text
pending_slice_target
```

例如只保持未来一批待执行Slice。

---

# 64. Lazy Planner触发

条件：

```text
Task仍有未规划范围
AND
当前PENDING Slice低于目标
AND
容量/SourceBinding正常
```

则生成下一批。

---

# 65. Planning完成

当：

```text
目标范围全部已经生成过Slice
```

记录：

```text
planning_complete = true
```

Task最终成功还要求全部叶子Slice成功。

---

# 66. collect_task建议增加字段

为Lazy Planning增加：

```text
planning_status varchar(16)
planning_cursor jsonb
planning_complete boolean
```

状态：

```text
NOT_STARTED
PLANNING
COMPLETE
FAILED
```

`request_params jsonb`只保存：

```text

```

禁止包含：

```text
Token
密码
```

Token由Adapter环境配置获取。

# 68. 错误消息长度

数据库保存：

```text
error_type
+
简要error_message
```

完整Python traceback进入日志。

不能把几十KB traceback重复塞进每个任务行。

---

# 69. 日志与任务表边界

任务表保存：

```text
结构化业务状态
```

日志保存：

```text
技术诊断细节
```

两者通过：

```text
run_id

```

关联。

# 70. trace_id


```text

↓

```

贯穿。

# 71. task_definition和task的版本

Task必须保留：

```text

```

即使以后task_definition配置被修改：

```text
历史Task仍知道自己执行的是哪一版规则
```

# 72. SourceBinding快照

Task创建时建议记录：

```text

```

不能只依赖SourceBinding当前最新配置。

否则历史Run以后无法解释：

```text
当时为什么用那个窗口/限频
```

# 73. RetryPolicy快照

Run至少保存：

```text
retry_policy_version
```

不需要复制完整配置JSON到每个Run。

版本指向不可变配置即可。

# 74. UpdatePolicy快照

INCREMENTAL Task保存：

```text
update_policy_version
expected_business_time
```

便于以后解释为什么当天创建该任务。

# 75. Scheduler扫描频率

P3不固定：

```text
每30秒
每1分钟
每5分钟
```

实现后根据：

- 数据源更新时间精度；
- 服务器负载；
- 任务规模；

设置。

采集平台不是高频交易撮合系统，不需要毫秒级Scheduler。

# 76. Scheduler时区

所有A股业务调度规则统一：

```text
Asia/Shanghai
```

数据库时间戳建议：

```text
timestamptz
```

内部统一处理时区。

不能让服务器系统时区隐式决定交易日逻辑。

---

# 77. 交易日边界

Scheduler判断：

```text
今天是否交易日
```

必须使用：

```text

```

不是Python weekday()。

---

# 78. 数据更新时间规则

Scheduler只在：

```text
availability_rule
```

规定的最早可用时间之后创建/激活任务。

如果来源仍未准备好：

```text
WAITING_SOURCE
```

---

# 79. 历史Catch-up

Scheduler启动时：

```text
expected watermark
>
current watermark
```

则生成缺失的INCREMENTAL任务。

系统停机数天不需要人工逐日补。

---

# 80. Catch-up与INITIALIZE区别

```text
INITIALIZE
=
首次构建历史资产

CATCH-UP
=
正常增量链因为停机/故障产生的短期滞后
```

Catch-up的run_type仍可以是：

```text
INCREMENTAL
```

通过：

```text
reason = catch_up
```

标记。

---

# 81. 任务优先级数值

建议小数值优先：

```text
0 = P0 日常关键增量
10 = P1 Repair
20 = P2 Retry
30 = P3 初始化
40 = P4 低优先级历史
```

不要依赖字符串排序。

具体值可以调整，但语义统一。

---

# 82. 人工提权

用户可以把某个Backfill提升优先级。

必须记录：

```text
old_priority
new_priority
actor
reason
```

# 83. 取消Task

用户请求取消：

```text
cancel_requested_at
```

Scheduler/Worker看到后：

- 不再生成新Slice；
- PENDING Slice取消；
- 正在请求中的Slice尽量安全结束；
- 不再开始下一个Slice。

---

# 84. 强制Kill不是正常取消方式

不能把：

```text
docker kill worker
```

作为业务取消流程。

那会产生LOST恢复，而不是CANCELLED。

# 85. PAUSE

暂停用于历史大任务。

字段建议：

```text

```

恢复：

```text
PAUSED -> PENDING
```

已完成Slice不变。

---

# 86. Scheduler对PAUSE的处理

PAUSED Task：

```text
不生成新Slice
不恢复失败Slice
```

但已在执行中的请求可安全结束。

# 129. P3任务系统完成标准

满足以下条件才能认为任务系统设计闭环：

1. Task和Run分离；
2. Task和Slice分离；
3. 每次外部请求有Attempt；
4. Scheduler不执行采集；
5. Worker使用数据库原子领取；
6. 多Worker不会领取同一个Slice；
7. Lease过期任务可恢复；
8. 旧Worker不能越权回写；
9. Scheduler有Leader互斥；
10. Task仍有数据库唯一幂等约束；
11. Lazy Planning避免任务爆炸；
12. Split可以形成子Slice树；
13. Retry_wait不占Worker；
14. Watermark和DataGap分离；
15. dev/test/prod任务状态隔离；
16. 不依赖Celery和Redis保存正式任务事实。

---

# 130. 最终结论

quantStock1第一阶段任务系统正式确定为：

```text
PostgreSQL任务事实库
+
单Scheduler
+
统一Worker
+
SKIP LOCKED原子领取
+
Lease / lease_token
+
Lazy Planning
+
Watermark
+
DataGap
```

核心数据模型：

```text
TaskDefinition
↓
CollectTask
↓
CollectRun
↓
RequestSlice
↓
SliceAttempt
```

关键决策：

1. 不采用Celery作为第一阶段任务框架；
2. PostgreSQL保存唯一正式任务状态；
3. Scheduler只负责创建和维护任务；
4. Worker只负责执行；
5. Task、Run、Slice、Attempt四层职责分开；
6. `FOR UPDATE SKIP LOCKED`用于多Worker原子领取；
7. Lease负责崩溃恢复；
8. lease_token防止过期Worker错误回写；
9. Scheduler使用PostgreSQL advisory lock保证单Leader；
10. 数据库唯一约束是任务幂等最后防线；
11. Lazy Planning避免分钟历史产生海量待办记录；
12. RETRY_WAIT使用next_retry_at，不让Worker长时间sleep；
13. Watermark只表示向前进度，DataGap负责中间缺口；
14. 旧quantStock任务状态不复用；
15. MIGRATION也复用同一可靠任务框架。
