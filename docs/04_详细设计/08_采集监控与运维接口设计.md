# 采集监控与运维接口设计

> 路线图阶段：P3 数据源与采集平台  
> 项目：A股量化研究与信号决策平台（quantStock1）  
> 文档性质：详细设计——采集监控、运维与人工控制  
> 日期：2026-07-27  
> 状态：已确认

---

# 1. 设计目标

本文件定义采集平台如何回答以下问题：

```text
系统现在是否正常？
今天的数据采完了吗？
哪个DataItem落后？
哪里有缺口？
哪个任务失败？
失败原因是什么？
Worker和Scheduler是否在线？
Tushare接口是否可用？
磁盘是否快满？
我能否安全地补采、重试、暂停、恢复或取消？
```

目标不是建设复杂监控平台。

第一阶段只建立：

```text
结构化运行状态
+
查询接口
+
受控运维接口
+
基础告警
+
审计
```

---

# 2. 总体原则

监控能力分为四层：

```text
系统层
↓
数据源层
↓
任务层
↓
数据资产层
```

并增加：

```text
资源容量层
```

每一层都必须能独立判断健康状态。

---

# 3. 监控与日志的区别

监控回答：

```text
现在是什么状态？
是否需要处理？
```

日志回答：

```text
技术上发生了什么？
```

例如：

```text
监控：
stock_daily 落后1个交易日

日志：
某次Tushare请求TIMEOUT
```

不能要求用户每天翻日志判断系统是否正常。

---

# 4. 第一阶段核心运维页面

以后前端至少需要五个页面：

```text
1. 运行总览
2. 数据资产状态
3. 任务与失败
4. 数据源状态
5. 系统资源
```

第一阶段即使暂时没有完整前端，也必须先提供相同能力的API。


---

# 6. 总体健康状态

统一：

```text
HEALTHY
DEGRADED
UNHEALTHY
MAINTENANCE
```

---

# 7. HEALTHY

表示：

- API正常；
- Scheduler正常；
- 至少一个Worker正常；
- 数据库正常；
- 关键SourceBinding正常；
- 关键DataItem达到预期水位；
- 没有阻断性容量问题。

---

# 8. DEGRADED

例如：

- 某个非关键接口失败；
- 某个非关键DataItem落后；
- 有少量待修复Gap；
- 一个Worker失联但仍有可用Worker；
- 数据盘达到预警线但未进入保护状态。

系统仍可工作。

---

# 9. UNHEALTHY

例如：

- PostgreSQL不可用；
- Scheduler长期失联；
- 所有Worker不可用；
- Tushare主Token认证失败；
- 关键DataItem持续无法更新；
- 磁盘进入容量保护并影响正式增量。

---

# 10. MAINTENANCE

表示：

```text
用户明确进入维护状态
```

例如：

- 数据库迁移；
- 大规模迁移；
- 存储维护；
- 正式发布。

不是异常。

# 12. DataItem健康状态

统一：

```text

```

---

# 13. CURRENT

表示：

```text
latest_quality_passed_business_time
>=
expected_business_time
```

且没有阻断性Gap。

---

# 14. LAGGING

表示：

```text
应该更新
但尚未推进到预期水位
```

例如：

```text
expected = 2026-07-27
quality_passed = 2026-07-26
```

---

# 15. INCOMPLETE

表示：

```text
最新水位虽然够新
但历史中仍有未解决Gap
```

例如分钟数据：

```text
最新到7月27日
但6月3日缺一段
```

---

# 16. BLOCKED

例如：

- SourceBinding无权限；
- Schema变化；
- 容量保护；
- 数据质量阻断；
- 依赖数据未就绪。

---


```text

```

# 32. 任务进度

不同任务的进度定义不同。

## 已完整规划Task

可以：

```text
成功叶子Slice / 全部叶子Slice
```

## Lazy Planning Task

不能只按当前已生成Slice算百分比。

应根据：

```text
总目标范围
+
planning_cursor
+
已完成范围
```

计算近似进度。

如果无法可靠计算：

```text
显示已完成范围
而不是伪造百分比
```

# 44. 容量阈值

按已经确认的项目规则：

```text

75%：预警

```

这些是项目阈值，不是操作系统硬限制。

---

# 45. 容量保护状态

达到保护条件时：

```text
CAPACITY_PROTECTION
```

系统至少做到：

- 不继续创建低优先级大历史任务；
- 暂停大规模迁移；
- 暂停大范围重洗；
- 保留关键日常任务空间；
- 明确告警。

# 57. Backfill API

请求至少：

```text
data_item
object_scope
time_start
time_end
frequency
source_binding（可选）
reason
```

服务端：

```text
校验
↓
生成Task
↓
返回task_id
```

API本身不执行长时间采集。

---

# 58. Retry API

用途：

```text
对失败Task/Run按原业务目标继续恢复
```

不能随意修改原失败Run。

创建：

```text
新的Run
```

或符合设计的新Retry执行。

---

# 59. Rerun API

用途：

```text
已成功任务重新执行验证
```

必须要求：

```text
reason
```

并产生新的RERUN业务意图。

---

# 60. Pause API

主要用于：

- 历史初始化；
- 大规模Backfill；
- 大规模Migration。

不建议暂停非常短的普通日增量。

---

# 61. Resume API

恢复：

```text
未完成部分
```

已成功Slice不重新执行。

---

# 62. Cancel API

取消后：

- 不新生成Slice；
- PENDING Slice取消；
- 当前正在安全执行的请求结束后停止；
- 已写入RAW不自动删除。

---

# 63. SourceBinding Probe API

触发：

```text
CapabilityProbe
```

返回：

```text
probe_task_id
```

不是接口同步阻塞几十秒等待结果。

---

# 64. Enable/Disable Binding

高影响操作。

Disable后：

- 不创建新任务；
- 已有历史数据不删除；
- 正在执行任务按策略结束/取消；
- 留AuditEvent。

---

# 65. 修改限频

如果以后提供：

```text
effective_limit
```

在线调整接口。

必须独立接口并审计。

第一版也可以只通过配置管理，不必立刻做UI修改。

---

# 66. 高风险操作

以下操作不能一键无确认：

```text
大范围Rerun
大范围Backfill

删除数据
重新清洗全历史

```

第一阶段至少要求：

```text

+
明确范围
```

以后前端增加二次确认。

# 74. 告警去重

同一个问题不能每分钟创建一条新Alert。

```text

```

```text

```

# 148. 最终结论

采集监控与运维能力确定为：

```text
业务状态驱动监控
+
结构化Alert
+
只读监控API
+
受控写操作API
+
AuditEvent
```

核心决策：

1. 用户不需要翻日志才能判断采集是否正常；
2. DataItem健康必须同时看Watermark、Gap和Quality；
3. 采集、清洗、质量水位分别展示；
4. DataSource和SourceBinding分别监控；
5. Task/Run/Slice/Attempt逐层可追踪；
6. Worker和Scheduler都有Heartbeat；
7. `/health`和`/ready`职责分开；
8. `/version`必须能对应Git Commit；
9. Backfill/Retry/Pause/Resume/Cancel全部通过受控API；
10. 运维API不执行长任务，只创建受控业务对象；
11. 所有写操作必须审计；
