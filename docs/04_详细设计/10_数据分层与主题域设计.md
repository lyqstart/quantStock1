# 数据分层与主题域设计

> 路线图阶段：P4 数据治理与分层存储  
> 项目：A股量化研究与信号决策平台（quantStock1）  
> 文档性质：详细设计——数据分层与主题域基线  
> 日期：2026-07-27  
> 状态：已确认

---

# 1. 文档目的

本文件确定 quantStock1 在 P4 阶段的数据分层、Schema 职责、主题域组织方式，以及 RAW 到 CLEAN 的正式边界。

本文件只回答：

1. 数据分成哪些层；
2. 每层存什么、不存什么；
3. 主题域如何组织；
4. RAW 与 CLEAN 如何隔离；
5. 多数据源如何落入统一标准层；
6. 第一批 P4 实施哪些 DataItem；
7. 后续 P4 专题必须遵守哪些边界。

字段、单位、主键、清洗规则、复权规则、质量规则、分区索引和血缘细节分别在后续 P4 专题中确定。


P4 不重新设计 P3 已经完成的采集平台，也不引入新的数据库、中间件或分布式数据平台。

# 3. 总体原则

## 3.1 DataItem 是标准数据的稳定业务身份

长期稳定身份仍然是：

```text
DataItem
```

而不是：

```text
Tushare API
物理表名
数据来源名称
```

例如：

```text
DataItem = stock_daily
```

当前来源可以是：

```text
Tushare daily
```

未来也可以增加：

```text
AKShare
legacy_quantstock migration
```

但上层看到的标准数据身份仍然是：

```text
stock_daily
```

---

## 3.2 RAW 来源相关，CLEAN 来源无关

RAW 允许保留来源特征：

```text
raw.tushare_daily
raw.tushare_adj_factor
...
```

CLEAN 不允许把具体来源写进长期业务身份：

```text
clean.stock_daily
clean.stock_adj_factor
...
```

因此：

```text
RAW = 数据源事实
CLEAN = 平台事实
```

---

## 3.3 RAW 不作为正式研究入口

RAW 的职责是：

```text
保留原始事实
支持追溯
支持重新清洗
支持问题调查
```

RAW 不能成为以下模块的正式数据入口：

```text
Feature
Analysis
Strategy
Backtest
Signal
```

这些模块以后只能通过平台标准数据接口读取 CLEAN 或其上层正式资产。

---

## 3.4 CLEAN 只表达统一后的平台口径

CLEAN 必须完成：

```text
统一主键
统一时间
统一证券标识
统一数据类型
统一单位
统一空值语义
统一状态
统一来源冲突处理
统一质量门禁
```

未通过规定质量门禁的数据不能作为正式 CLEAN 数据向下游发布。

---

## 3.5 不为每个主题域建立独立 Schema

P4 不采用：

```text
stock_schema
finance_schema
index_schema
industry_schema
...
```

主题域由 DataItem 元数据和表命名表达，不通过大量 PostgreSQL Schema 表达。

原因：

```text
当前单库
+
单人维护
+
模块化单体
+
需要最小复杂度
```

---

# 4. 数据分层模型

quantStock1 当前正式数据分层：

```text
定义/控制层
    meta
    ops
    audit
    migration

业务数据层
    raw
    clean

质量治理层
    quality

研究资产层
    research（后续阶段启用）
```

它们不是同一种“数据层”。

---

# 5. meta Schema

`meta` 保存：

```text
系统知道什么
```

包括：

- DataSource；
- DataItem；
- SourceBinding；
- 字段映射版本；
- 清洗规则版本；
- 质量策略版本；
- 更新策略；
- 保留策略；
- 数据契约版本。

不保存大规模市场事实数据。

---

# 6. raw Schema

`raw` 保存：

```text
外部来源实际返回了什么
```

核心规则：

1. 尽量保持来源字段语义；
2. 不做会改变业务含义的修正；
3. 保留来源身份；
4. 保留采集批次；
5. 保留采集时间；
6. 保留源接口和请求上下文引用；
7. 可以重新执行 CLEAN；
8. RAW 中发现错误时不得偷偷覆盖成“正确数据”。

RAW 是可追溯事实层，不是最终可信层。

---

# 7. clean Schema

`clean` 保存：

```text
平台正式统一后的可信数据
```

核心规则：

1. 表名使用 DataItem 业务身份；
2. 不使用 `tushare_`、`akshare_` 等来源前缀；
3. 同一个 DataItem 原则上只有一套正式标准数据；
4. 多来源通过 SourceBinding 和血缘记录区分；
5. 正式下游默认只读取 CLEAN；
6. CLEAN 可以由 RAW 重新生成；
7. CLEAN 的规则变化必须版本化并支持重洗。

第一批示例：

```text
clean.stock_basic
clean.trade_calendar
clean.stock_daily
clean.stock_adj_factor
clean.stock_daily_basic
clean.stock_suspend
clean.stock_limit_price
clean.stock_minute
clean.financial_income
clean.financial_indicator
```

最终物理表名和字段在《标准Schema与编码规范》中确认。

---

# 8. quality Schema

`quality` 不保存另一份完整业务数据副本。

它保存：

- 质量规则定义；
- 规则版本；
- 检查运行结果；
- DataItem 质量状态；
- 数据缺口；
- 重复问题；
- 范围异常；
- 合理性异常；
- 多源冲突；
- 阻断原因；
- 隔离数据引用；
- 人工复核结果。

质量层回答：

```text
这批数据能不能正式使用？
为什么不能使用？
影响什么范围？
如何恢复？
```

---

# 9. ops Schema

`ops` 保存运行事实，不保存正式业务数据。

主要包括：

- CollectTask / CollectRun；
- RequestSlice；
- CleanRun；
- QualityRun；
- Worker 状态；
- Scheduler 状态；
- Watermark；
- Checkpoint；
- 系统运行状态。

P4 清洗和质量任务继续复用 P3 已经建立的 PostgreSQL 任务体系，不新增第二套任务框架。

---

# 10. audit Schema

`audit` 保存：

```text
谁
在什么时候
因为什么
对哪个正式对象
做了什么变化
```

P4 至少审计：

- 手工重洗；
- 人工放行；
- 人工隔离；
- 质量规则启停；
- CLEAN 版本切换；
- 多源冲突人工裁决；
- 数据删除或归档等高风险动作。

---

# 11. migration Schema

`migration` 只管理：

```text
legacy_quantstock
↓
quantStock1
```

的受控历史迁移。

旧 quantStock 数据不能因为迁移进入新项目，就获得独立业务 DataItem 身份。

例如：

```text
旧 daily
↓
标准目标仍是 stock_daily
```

---

# 12. research Schema

P4 不正式建设 Feature / Analysis / Strategy / Backtest 数据模型。

`research` 只保留架构位置。

后续：

```text
P5 DataContext
P6 Feature / Analysis
P7 Strategy
P8 Backtest
```

逐步启用。

因此 P4 不提前创建大量：

```text
feature.*
analysis.*
signal.*
backtest.*
```

Schema。

这些概念属于后续业务资产层，不应在 P4 造成数据库结构膨胀。

---

# 13. 主题域模型

主题域沿用已经确认的数据目录，不重新发明分类。

```text
D01 证券基础
D02 股票行情
D03 分钟行情
D04 集合竞价
D05 财务报表
D06 业绩与披露
D07 股东与公司行为
D08 资金与交易行为
D09 融资融券
D10 沪深港通
D11 指数
D12 行业与市场统计
D13 实时辅助数据
D14 遗留迁移数据
```

主题域用于：

- 数据目录管理；
- 数据质量策略分组；
- 保留策略分组；
- 权限和展示分组；
- 后续 DataContext 查询分类；
- AI 理解数据能力。

主题域不直接决定物理 Schema。

---

# 14. DataItem 与物理存储关系

正式关系：

```text
DataDomain
↓
DataItem
↓
SourceBinding
↓
RAW Table
↓
Clean Rule
↓
CLEAN Table
↓
Quality Gate
↓
正式可用数据
```

一个 DataItem：

```text
可以有多个 SourceBinding
可以有多个 RAW 来源表
原则上只有一个正式 CLEAN 业务口径
```

---

# 15. 多数据源处理边界

例如：

```text
stock_daily
├─ Tushare
├─ AKShare
└─ legacy_quantstock
```

RAW 分别保存真实来源。

进入 CLEAN 时：

```text
不能简单拼接
不能静默覆盖
不能把备用源伪装成主源
```

必须依据后续《清洗规则与状态口径》确定：

- 来源优先级；
- 冲突判定；
- 字段级合并；
- 缺失补充；
- 来源切换；
- 人工确认条件。

最终 CLEAN 仍然只有统一业务语义。

---

# 16. RAW → CLEAN 发布模型

P4 正式主链：

```text
RawBatch
↓
CleanTask
↓
清洗转换
↓
QualityCheck
├─ PASS
│   ↓
│ CLEAN正式发布
│
└─ BLOCK
    ↓
  不进入正式下游
    ↓
  问题记录 / 补采 / 重洗 / 人工复核
```

关键原则：

```text
清洗完成 ≠ 可以使用
```

只有通过规定质量门禁，才成为正式可用 CLEAN 数据。

---

# 17. CLEAN 的更新原则

CLEAN 更新采用：

```text
同一业务身份幂等写入
+
规则版本可追溯
+
来源批次可追溯
```

不能使用：

```text
直接全表覆盖
无法解释旧值从哪里来
规则升级后历史含义混杂
```

具体主键、版本字段和更新策略在后续 P4 文档确认。

---

# 18. 数据血缘原则

每一批 CLEAN 数据必须能够回答：

```text
来自哪个 DataItem
来自哪个 SourceBinding
来自哪些 RawBatch
使用哪一版清洗规则
使用哪一版质量规则
何时生成
当前是否正式可用
```

对于分钟等超大表，不要求把完整来源元数据重复写到每一行。

长期原则：

```text
业务行
↓
CleanBatch / lineage reference
↓
RawBatch
```

避免为了血缘显著放大数十亿行分钟数据。

具体结构在《数据血缘与追溯设计》中确认。

---

# 19. 分钟数据的分层原则

`stock_minute` 是高容量专项数据。

P4 确认长期基础粒度优先：

```text
1分钟
```

在验证聚合结果一致后：

```text
5m
15m
30m
60m
```

不默认长期保存四套完整历史副本。

这些周期优先由：

```text
1m CLEAN
↓
确定性聚合
```

生成。

如果未来出现明确查询性能证据，再决定是否建立物化结果。

分钟数据使用 TimescaleDB 能力，具体分区、压缩和生命周期在 P4.7 确认。

---

# 20. 财务数据的分层原则

财务数据不能只保留“当前最新值”。

CLEAN 必须保留能够表达历史披露变化的信息，包括：

```text
股票
报告期
公告日期
实际公告日期
报告类型
版本/修订身份
```

后续回测必须能够读取：

```text
当时已经公开的数据
```

而不是使用今天看到的最新修订结果替代历史事实。

具体版本键和可用时间在 P4.2、P4.3 和 P5 防未来函数设计中继续确认。

# 21. 第一批 P4 实施范围

P4 第一批不扩展新的采集接口。

只治理 P3 已经真实跑通的数据：

```text
stock_basic
trade_calendar
stock_daily
stock_adj_factor
stock_daily_basic
stock_suspend
stock_limit_price
stock_minute（1m样本）
financial_income

```

目标是先验证：

```text

↓
CLEAN
↓

↓
追溯
```

完整闭环。

完成后再按 DataItem 优先级逐类扩展，不因新增接口重新设计 P4 框架。

# 23. P4.1 确认结论

确认以下正式决策：

1. 继续使用 `meta/raw/clean/quality/ops/audit/migration/research` Schema 基线；
2. 不按主题域创建大量新 Schema；
3. RAW 来源相关，CLEAN 来源无关；
4. CLEAN 表以 DataItem 作为长期业务身份；
5. 上层正式研究禁止直接读取 RAW；
6. CLEAN 发布必须经过质量门禁；
7. quality 记录规则、结果和阻断，不复制整套业务数据；
8. 清洗与质量任务复用 P3 的 Worker + PostgreSQL 任务体系；
9. 多来源在 RAW 保持来源真实性，在 CLEAN 形成统一业务口径；
10. 第一批 P4 只治理 P3 已验证的 10 个 DataItem；
11. 分钟长期基础粒度优先保存 1m，不默认保存五套完整周期副本；
12. 财务 CLEAN 必须保留历史披露和修订语义；
13. CLEAN 必须能够追溯到 RawBatch 和规则版本；
14. P4 不提前建设 Feature/Analysis/Strategy/Backtest 物理模型。

---

# 24. 遗留问题

以下事项不在 P4.1 提前拍板，进入对应专题：

1. CLEAN 表具体主键、字段类型、统一代码格式；
2. 日期、时间、时区和数值单位规范；
3. ST、停牌、退市等状态标准；
4. 前复权、后复权和不复权的正式保存/计算口径；
5. 多来源字段冲突优先级；
6. Quality 状态枚举和下游门禁规则；
7. CleanRun / QualityRun / CleanBatch 的具体表结构；
8. 分钟 hypertable、chunk、压缩和保留周期；
9. RAW 长期保留周期；
10. CLEAN 批次与 RawBatch 的精确血缘结构。

这些问题分别进入 P4.2～P4.8。
