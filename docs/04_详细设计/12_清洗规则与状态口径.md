# 2. 核心原则

P4 正式链路：

```text
RAW
↓
标准化
↓
CLEAN Candidate
↓
质量校验
├─ PASS / WARN
│   ↓
│ CLEAN正式发布
│
└─ BLOCKED
    ↓
  不发布
    ↓
  保留原RAW
    ↓
  问题记录 / 补采 / 重洗 / 人工复核
```

关键原则：

```text
清洗成功
≠
质量通过
≠
正式可用
```

# 3. 清洗与质量的职责边界

## 3.1 清洗负责

清洗只做确定性标准化：

- 字段映射；
- 证券代码标准化；
- 交易所标准化；
- 日期解析；
- 时区解释；
- 数据类型转换；
- 单位转换；
- 空值标准化；
- 稳定枚举映射；
- 业务主键生成；
- 内容哈希；
- 财务版本识别；
- 血缘引用生成。

---

## 3.2 清洗不负责

清洗不能擅自：

- 修正可疑价格；
- 填补缺失行情；
- 前向填充停牌日价格；
- 插值分钟行情；
- 把异常值裁剪到“合理范围”；
- 把未知值改成 0；
- 用股票名称推断 ST 状态；
- 用沪深交易日历猜北交所交易日；
- 用另一个数据源静默覆盖主数据源；
- 把质量异常伪装成清洗成功。

---

## 3.3 质量负责

质量层判断：

```text
数据是否完整
数据是否一致
数据是否合理
数据是否存在缺口
数据是否与其他正式资产冲突
是否允许发布给下游
```

因此：

```text
“能不能转换”
属于清洗

“转换后能不能信”
属于质量
```

# 4. 行级标准化结果

每一条 RAW 记录经过标准化后只有三种结果：

```text
ACCEPT
SKIP
REJECT
```

---

## 4.1 ACCEPT

含义：

```text
属于平台正式范围
+
必要字段能够安全标准化
+
形成 CLEAN Candidate
```

ACCEPT 不代表最终质量通过。

---

## 4.2 SKIP

含义：

```text
来源记录本身有效
但不属于当前平台正式 DataItem 范围
```

SKIP 不算错误，不触发重试。

典型场景：

`stk_limit` 来源接口包含：

```text
A股
B股
基金
```

quantStock1 当前 `stock_limit_price` 正式范围是：

```text
A股
```

因此：

```text
A股       → ACCEPT
B股/基金  → SKIP
```

SKIP 必须计数并能够追溯原因：

```text
OUT_OF_SCOPE_SECURITY
```

不能静默消失。

---

## 4.3 REJECT

含义：

```text
记录属于平台正式范围
但无法安全形成标准记录
```

例如：

- A 股证券代码格式非法；
- 必需日期无法解析；
- 必需业务主键为空；
- 未知交易所无法映射；
- 应为数值却无法解析；
- 单位换算后违反类型约束；
- 财务记录没有任何可用公告日期。

REJECT 必须生成问题记录。

是否阻断整批发布，由质量规则决定。

---

# 5. CLEAN 发布质量状态

正式 CLEAN 行只允许：

```text
PASS
WARN
```

对应：

```text
_quality_status = PASS
_quality_status = WARN
```

---

## 5.1 PASS

满足所有阻断规则。

允许所有正式下游读取。

---

## 5.2 WARN

存在非阻断质量问题，但不影响当前正式使用。

例如：

- 非核心描述字段缺失；
- 来源存在可解释的历史字段缺口；
- 可选盘后字段在接口上线前为 NULL。

WARN 必须能够追溯对应质量问题。

---

## 5.3 BLOCKED

`BLOCKED` 是批次/分区发布状态，不作为正式 CLEAN 行的正常发布状态。

当候选批次被 BLOCKED：

```text
不把新候选数据发布到正式 CLEAN
不覆盖已有可用 CLEAN
RAW 保持不变
质量问题保持可追溯
```

这样可以保证：

```text
新的坏数据
不能破坏已有好数据
```

---

# 6. 清洗运行状态

CleanRun 第一版状态：

```text
PENDING
RUNNING
VALIDATING
SUCCEEDED
BLOCKED
FAILED
CANCELLED
LOST
```

含义：

| 状态 | 含义 |
|---|---|
| `PENDING` | 等待执行 |
| `RUNNING` | 正在标准化 |
| `VALIDATING` | 标准化完成，正在执行质量门禁 |
| `SUCCEEDED` | 质量通过并完成发布 |
| `BLOCKED` | 标准化完成，但质量门禁阻断 |
| `FAILED` | 程序、数据库或规则执行失败 |
| `CANCELLED` | 人工取消 |
| `LOST` | Worker 失联导致本次运行失效 |

---

# 7. BLOCKED 与 FAILED 必须严格区分

## BLOCKED

代表：

```text
程序正常
数据有问题
```

例如：

```text
当日全市场日线明显缺失大量证券
```

---

## FAILED

代表：

```text
程序没有正确完成任务
```

例如：

```text
数据库异常
规则代码异常
类型转换程序异常
```

因此运维处理不同：

```text
BLOCKED
→ 看数据质量 / 补采 / 数据源 / 人工复核

FAILED
→ 看程序 / 数据库 / 运行环境
```

---

# 8. 发布原子性

CLEAN 按“发布单元”原子发布。

不能：

```text
一批5500条
前3000条已覆盖CLEAN
后2500条质量失败
```

正式原则：

```text
候选批次全部完成标准化
↓
质量门禁
↓
允许发布
↓
事务内幂等写入
↓
批次状态SUCCEEDED
```

质量阻断时：

```text
正式CLEAN保持发布前状态
```

# 10. `_available_at` 正式口径

P4.2 中 `_available_at` 正式解释为：

```text
quantStock1 这一版 CLEAN 数据
实际首次允许平台下游读取的时间
```

因此第一版：

```text
_available_at = 本次 CLEAN 批次正式发布完成时间
```

它是：

```text
平台运行可用时间
```

不是：

```text
历史市场理论可知时间
```

---

# 11. 防未来函数时间另行表达

历史回测不能简单使用 `_available_at` 判断历史可知性。

不同数据使用业务时间规则：

```text
行情：
trade_date / trade_time

财务：
available_from_trade_date

证券状态：
对应历史状态数据或明确观察历史
```

因此：

```text
_available_at
用于平台运行追溯

available_from_trade_date等业务字段
用于历史研究防未来函数
```

P5 DataContext 必须同时理解两种时间。

# 12. source 与 SourceBinding

每次清洗只从明确的 SourceBinding 读取 RAW。

第一版：

```text
Tushare = 主来源
```

未来增加：

```text
AKShare
legacy_quantstock
```

时不得：

```text
Tushare缺了
→ 自动拿AKShare填
→ CLEAN仍标成Tushare
```

正式规则：

```text
来源切换
必须显式
必须留血缘
必须经过质量规则
```

---

# 13. 多来源冲突

如果两个来源对同一业务键给出不同值：

```text
不静默覆盖
```

第一版处理：

```text
产生 SOURCE_CONFLICT
↓
按 SourceBinding 正式优先级生成候选
↓
是否发布由质量规则决定
```

只有明确配置“字段级补充”时，才允许从次来源补字段。

# 14. stock_basic 清洗规则

DataItem：

```text
stock_basic
```

RAW：

```text
raw.tushare_stock_basic
```

CLEAN：

```text
clean.security_master
clean.security_master_history
```

---

## 14.1 状态范围

正式采集和清洗保留：

```text
L = 上市
D = 退市
P = 暂停上市
G = 过会未交易
```

不能只保留 L。

否则会产生幸存者偏差。

---

## 14.2 字段映射

```text
ts_code      → security_code
symbol       → symbol
name         → name
area         → area
industry     → industry_name
fullname     → full_name
enname       → english_name
cnspell      → cn_spell
market       → market
exchange     → exchange_code
curr_type    → currency_code
list_status  → list_status
list_date    → list_date
delist_date  → delist_date
is_hs        → hsgt_status
act_name     → actual_controller_name
act_ent_type → actual_controller_entity_type
```

---

## 14.3 交易所

只接受已确认映射：

```text
SSE  → SSE
SZSE → SZSE
BSE  → BSE
```

security_code 后缀必须与 exchange_code 一致：

```text
.SH ↔ SSE
.SZ ↔ SZSE
.BJ ↔ BSE
```

不一致：

```text
REJECT
```

---

## 14.4 当前表与历史表

`security_master`：

```text
保存当前已观察到的最新正式版本
```

`security_master_history`：

```text
保存每次内容变化的系统观察历史
```

内容哈希相同：

```text
不新增历史版本
```

内容变化：

```text
关闭上一 observed_to
新增新版本
```

不能把：

```text
observed_from
```

解释成真实市场生效日期。

# 15. ST 状态口径

第一批 P4 不从股票名称推断 ST。

禁止：

```text
name LIKE '*ST%'
name LIKE 'ST%'
→ is_st=true
```

原因：

```text
股票名称是展示事实
不是正式历史状态契约
```

当前首批 10 个 DataItem 没有独立 ST 历史 DataItem。

因此第一版：

```text
不在 CLEAN 人工制造 is_st 字段
```

后续接入正式 ST 历史接口后，再建立：

```text
stock_st_status
```

DataItem。

## 17.2 成交量

```text

```

```text

```

```text

```

```text

```

不能通过四舍五入掩盖来源异常。

---

## 17.3 成交额

来源：

```text
千元
```

```text

```

---

## 17.4 盘后字段

来源：

```text

ah_amount = 千元
```

CLEAN：

```text
after_hours_volume_share = ah_vol × 100
after_hours_amount_cny   = ah_amount × 1000
```

```text

```

是合法历史状态。

不能：

```text
NULL → 0
```

---

## 17.5 停牌日

日线来源停牌期间不提供行情。

因此：

```text
某股票某交易日没有 stock_daily
```

不能单独判定为数据缺口。

必须结合：

```text
stock_suspend
+
security_master
+
trade_calendar
```

由质量规则判断。

禁止为了“连续”：

```text
复制上一日收盘价制造假K线
```


CLEAN：

```text
clean.financial_indicator
```

关键映射：

```text

ann_date  → ann_date
end_date  → report_period
update_flag → update_flag
```

其余财务指标字段：

```text
保持来源已确认数值语义
```

P4 第一版不进行未经确认的单位换算。

# 25. 财务版本判定

财务记录不能用：

```text
security_code + report_period
```

简单覆盖。

标准化后生成：

```text
content_hash
```

hash 输入：

```text
稳定业务身份字段
+
所有正式业务数值字段
```

不包括：

```text
_clean_batch_id
_created_at
_updated_at
```

---

## 25.1 相同内容

同一证券、报告期、报告类型：

```text
content_hash相同
```

则：

```text
幂等
不新增业务版本
补充最新血缘即可
```

---

## 25.2 内容变化

同一证券、报告期、报告类型：

```text
content_hash变化
```

则：

```text
新增财务版本
不得覆盖旧版本
```

`update_flag` 可以作为来源证据，但：

```text
不能作为唯一版本判断依据
```

## 26.2 financial_indicator


## 26.3 available_from_trade_date

第一版系统策略：

```text

```


# 34. 规则版本

每次 CLEAN 发布必须记录：

```text

_normalization_version
_quality_rule_version
```

```text

= RAW字段 → CLEAN字段关系

= 单位/类型/状态/版本等转换规则
```

# 42. P4.3 正式决策

本文件确认：

1. 清洗只做确定性标准化，质量层决定是否可信；
2. 行级标准化结果只有 `ACCEPT / SKIP / REJECT`；
3. `SKIP` 是合法范围过滤，不等于失败；
4. 正式 CLEAN 只发布 `PASS / WARN`；
5. `BLOCKED` 不覆盖已有 CLEAN；
6. `BLOCKED` 表示数据问题，`FAILED` 表示执行问题；
7. CLEAN 必须按发布单元原子切换；
8. `_available_at` 表示 quantStock1 实际正式发布时间；
9. 历史防未来函数使用业务时间字段，不用 `_available_at` 代替；
10. `stock_basic` 保留 L/D/P/G，不制造单一 active 布尔值；
11. 第一批不从股票名称推断 ST；
12. 停复牌保持事件模型，不制造万能 `is_suspended`；
13. 日线手→股、千元→元，分钟量额不重复换算；
14. 停牌缺日线不能单独判为数据缺口；
15. `stk_limit` 中 B 股和基金按 `SKIP` 处理；
16. 复权因子进入 CLEAN，但 P4.3 不生成复权价格；
17. 财务相同报告期允许多个历史版本；
18. 财务版本由标准化内容 hash 识别，不能只依赖 `update_flag`；
19. 财务 `available_from_trade_date` 使用公告日之后第一个开市日；
20. 清洗不做填充、插值、裁剪、猜测等“智能修复”；
21. 来源历史修订允许更新普通当前事实，但必须保留完整血缘；
22. 规则升级通过 RERUN 重洗，不修改 RAW；
23. P4 继续复用 P3 Worker + PostgreSQL 任务基础设施。
