# 2. 总原则

数据质量治理目标不是：

```text
让所有数据看起来“完整”
```

而是：

```text
明确知道哪些数据可信
哪些数据可疑
哪些数据禁止使用
以及为什么
```

正式原则：

```text
不猜
不补假数据
不静默忽略
不靠人工记忆
不以百分比掩盖明确缺口
```

---

# 3. 三层状态必须分开

P4 正式区分：

```text
清洗状态
质量状态
发布状态
```

不能混成一个 `status`。

---

## 3.1 清洗状态

回答：

```text
程序是否把 RAW 安全转换成标准候选数据？
```

状态：

```text
ACCEPT
SKIP
REJECT
```

---

## 3.2 质量状态

回答：

```text
标准候选数据是否可信？
```

结果：

```text
PASS
WARN
BLOCK
```

---

## 3.3 发布状态

回答：

```text
这批数据是否已经成为正式 CLEAN？
```

状态：

```text
NOT_PUBLISHED
PUBLISHED
SUPERSEDED
```

```text

severity
scope
```

# 5. 质量维度

第一版统一八类质量维度：

```text
SCHEMA
UNIQUENESS
VALIDITY
COMPLETENESS
CONTINUITY
CONSISTENCY
TIMELINESS
LINEAGE
```

---

## 5.1 SCHEMA

检查：

```text
字段
类型
必需列
来源结构变化
```

---

## 5.2 UNIQUENESS

检查：

```text
业务主键是否重复
同一事件是否重复
同一版本是否重复
```

---

## 5.3 VALIDITY

检查：

```text
代码格式
日期
枚举
价格关系
有限数值
正负约束
```

---

## 5.4 COMPLETENESS

检查：

```text
应该存在的数据是否存在
必要字段是否为空
```

---

## 5.5 CONTINUITY

检查：

```text
时间序列是否存在不应出现的缺口
```

主要用于：

```text
日线
分钟
复权因子
```

---

## 5.6 CONSISTENCY

检查：

```text
不同字段
不同表
不同来源
```

是否相互矛盾。

---

## 5.7 TIMELINESS

检查：

```text
数据是否在允许延迟范围内到达
```

只使用：

```text
quantStock1 实际时间证据
```

不能拿来源网站“理论更新时间”伪装成实际到达时间。

---

## 5.8 LINEAGE

检查：

```text
正式 CLEAN 是否能追溯 RawBatch
是否记录规则版本
是否记录 CleanBatch
```

血缘断裂：

```text
正式数据不可接受
```

# 6. 质量严重级别

QualityRule 第一版严重级别：

```text
INFO
WARN
BLOCK
```

---

## 6.1 INFO

仅记录，不影响发布。

例如：

```text
来源新增了当前未使用的可选字段
```

---

## 6.2 WARN

存在明确问题，但不影响核心业务语义。

允许发布：

```text
_quality_status = WARN
```

必须保留 QualityIssue。

---

## 6.3 BLOCK

问题会造成：

```text
错误研究
错误回测
错误策略判断
无法追溯
```

因此：

```text
禁止该发布单元进入正式 CLEAN
```

---

# 7. 不使用统一“质量总分”

P4 第一版不使用：

```text
quality_score = 92
```

来决定是否发布。

原因：

```text
证券代码错了
即使其他99项检查都通过
也不能因为总分高而发布
```

正式门禁：

```text
任一 BLOCK 规则失败
→ 整个发布单元 BLOCKED
```

WARN 不能抵消 BLOCK。

---

# 8. QualityRun

一次 QualityRun 对应一个明确发布单元。

状态：

```text
PENDING
RUNNING
PASSED
WARNED
BLOCKED
FAILED
CANCELLED
LOST
```

含义：

```text
PASSED  = 所有启用规则通过
WARNED  = 无BLOCK失败，但存在WARN
BLOCKED = 至少一个BLOCK规则失败
FAILED  = 检查程序本身执行失败
```

```text
issue_type

message
first_seen_at
last_seen_at

```

# 10. QualityIssue 生命周期

第一版：

```text
OPEN
REPAIRING
RESOLVED
ACCEPTED
```

---

## 10.1 OPEN

问题存在，尚未解决。

---

## 10.2 REPAIRING

已经进入：

```text
补采
重洗
来源修复
```

流程。

---

## 10.3 RESOLVED

重新检查已经证明问题不存在。

不能人工直接把：

```text
OPEN → RESOLVED
```

而没有复检证据。

---

## 10.4 ACCEPTED

仅用于：

```text
已确认真实存在
但业务允许接受
```

例如少量非关键历史描述字段缺失。

BLOCK 问题原则上不能仅靠 ACCEPTED 绕过。

若未来确实需要人工放行：

```text
必须单独设计审计化 override
```

P4 第一版不默认开放“强制发布坏数据”。

---

# 11. DataGap

DataGap 专门表达：

```text
本应存在，但当前缺失的数据范围
```

它不是所有 QualityIssue 的别名。

例如：

```text
某交易日缺少 600000.SH 日线
某股票 10:01 缺一分钟bar
某交易日缺复权因子
```

才创建 DataGap。

---

# 12. DataGap 生命周期

继续沿用 P3 缺口治理语义：

```text
OPEN
REPAIRING
VERIFYING
RESOLVED
```

只有：

```text
补采/修复完成
+
重新清洗
+
质量复检通过
```

才能：

```text
RESOLVED
```

---

# 13. DataGap 不允许“仅因补采成功”关闭

错误流程：

```text
补采HTTP成功
→ Gap RESOLVED
```

正式流程：

```text
补采
↓
RAW到账
↓
CLEAN成功
↓
质量复检
↓
缺口消失
↓
Gap RESOLVED
```

---

# 14. 发布门禁

每个 CLEAN 发布单元执行：

```text
Clean Candidate
↓
QualityRun
↓
规则集合
↓
结果
```

结果：

```text
PASSED
→ 发布

WARNED
→ 发布，标记WARN

BLOCKED
→ 不发布

FAILED
→ 不发布
```

---

# 15. 已有正式 CLEAN 的保护

如果某日已经存在正式好数据：

```text
新一批重采
↓
质量 BLOCKED
```

则：

```text
旧 CLEAN 继续可用
新候选不覆盖旧 CLEAN
```

质量问题必须明确标记：

```text
LATEST_CANDIDATE_BLOCKED
```

避免下游误以为最新来源已经正式生效。

# 18. 交易日历连续覆盖

“连续”不是：

```text
每天都是交易日
```

而是：

```text
请求日期范围中的每个自然日
必须存在一条 calendar 记录
```

包括：

```text
工作日
周末
节假日
```

因为 `trade_calendar` 本身就是判断是否开市的正式依据。

# 20. 日线价格不能用“必须大于0”一刀切

对于正常交易股票：

```text
OHLC > 0
```

是合理要求。

但规则不能简单写成：

```text
所有数值字段 > 0
```

因为：

```text
volume_share
amount_cny
```

在特殊市场状态下可能为 0。

因此价格和成交量必须分别判断。

# 21. 全市场日线完整度

核心原则：

```text
能算应有证券集合
就比较证券集合
而不是比较一个百分比
```

正式：

```text
ExpectedDailySet(trade_date)
-
ActualDailySet(trade_date)
=
MissingSet
```

---

# 22. ExpectedDailySet

第一版由可验证事实生成：

```text
security_master / history
+
list_date
+
delist_date
+
trade_calendar
+
stock_suspend_event
```

基础证券范围：

```text
list_date <= trade_date
AND
(delist_date IS NULL OR delist_date >= trade_date)
```

---

# 23. 新股处理

如果：

```text
list_date > trade_date
```

则：

```text
不属于当日 ExpectedDailySet
```

不能记为缺口。

---

# 24. 退市股票处理

如果：

```text
delist_date < trade_date
```

则：

```text
不属于当日 ExpectedDailySet
```

但退市之前的历史行情仍然必须存在。

---

# 25. 暂停上市与未交易状态

当前 `stock_basic` 的：

```text
P
G
```

不能单独精确表达某个历史日是否应该有日线。

因此第一版质量规则：

```text
不能仅凭当前 list_status=P/G
直接从历史 ExpectedDailySet 删除
```

必须优先使用：

```text
list_date
delist_date
明确停复牌事件
实际历史证据
```

无法确定时生成 WARN：

```text
EXPECTED_SET_UNCERTAIN
```

而不是制造假缺口。

---

# 26. 停牌处理

Tushare 当前官方说明：

```text
daily 在停牌期间不提供数据
```

因此存在正式全日停牌证据时：

```text
该股票从当日 ExpectedDailySet 排除
```

当前 `suspend_d` 中：

```text
S
且 suspend_timing 为空
```

可以作为全日停牌候选证据。

日内停牌：

```text
suspend_timing 非空
```

不能自动排除当日日线。

---

# 27. 日线 MissingSet 的质量结果

如果：

```text
MissingSet 非空
```

且每个缺失证券都能确认本应有数据：

```text
BLOCK
+
为每个连续范围建立 DataGap
```

不能：

```text
少10只 / 全市场5500只 = 99.8%
所以通过
```

核心事实数据不按百分比掩盖已确认缺失。

# 30. 复权因子变化

因子变化本身：

```text
不是 BLOCK
```

因为公司行为可能造成正常跳变。

需要：

```text
记录历史版本
使复权缓存 STALE
```

不能设“涨幅超过X%就是坏因子”的拍脑袋规则。

# 32. daily_basic 与 daily 的 close 一致性

两个来源字段理论上表达：

```text
同一证券同一交易日收盘价
```

正式检查：

```text
abs(close_basic - close_daily) <= tolerance
```

第一版 tolerance：

```text
不写固定人民币分值
```

使用：

```text
来源显示精度允许的数值比较
```

具体实现优先：

```text
标准化到相同浮点值后直接比较
```

若真实环境出现稳定微小舍入差异，再以证据确定 tolerance。

不提前拍脑袋定 0.01 元。

# 37. 分钟缺口不能简单按“每天240条”

真实验收中 2026-07-24 的样本得到：

```text
241条
```

因此 P4 正式禁止写死：

```text
1分钟A股每天必须240条
```

质量判断必须根据：

```text
平台正式分钟时间网格
+
接口时间标签语义
+
交易日特殊安排
```

生成 ExpectedMinuteGrid。

---

# 38. ExpectedMinuteGrid

由正式市场时段规则生成。

第一版不把时间点数量硬编码到质量规则参数。

结构：

```text
exchange_code
trade_date
frequency
expected_timestamps
rule_version
```

后续若交易制度调整，只升级市场时段规则，不改数据。

---

# 39. 分钟停牌处理

有停牌证据的时间段：

```text
从 ExpectedMinuteGrid 中排除
```

无停牌证据的缺失分钟：

```text
DataGap
```

禁止：

```text
用上一分钟填充
```

---

# 40. 分钟日线聚合一致性

对于完整分钟数据，可执行跨表检查：

```text
minute open(first)
minute high(max)
minute low(min)
minute close(last)
```

与日线：

```text
open/high/low/close
```

比较。

但第一版不能把：

```text
分钟 amount/volume 汇总
```

强制与日线直接做绝对相等 BLOCK，直到真实数据验证：

```text
集合竞价
盘后交易
接口覆盖范围
```

完全一致。

因此第一版：

```text
OHLC一致性 = BLOCK候选
量额一致性 = WARN观察
```

待样本验证后再升级规则。

同一：

```text
security_code
+
report_period
```

出现多个版本：

```text
不是重复数据错误
```

只要：

```text
content_hash不同
公告信息合理
版本可追溯
```

就必须保留。

---

# 44. 财务报告期检查

正式检查：

```text
report_period
```

必须是合法日期。

第一版不强制：

```text
只能 03-31 / 06-30 / 09-30 / 12-31
```

作为 BLOCK。

原因：

```text
来源可能包含特殊报告期或公司类型差异
```

先记录 WARN：

```text
NON_STANDARD_REPORT_PERIOD
```

真实运行有证据后再决定是否收紧。

---

# 45. 跨表证券一致性

所有股票级 CLEAN 数据：

```text
security_code
```

必须能够映射到：

```text
security_master
或
security_master_history
```

如果完全不存在：

```text
BLOCK
```

如果只是当前 master 已退市，但历史存在：

```text
正常
```

---

# 46. 跨表交易日一致性

日级市场事实：

```text
stock_daily
stock_adj_factor
stock_daily_basic
stock_suspend
stock_limit_price
```

的 `trade_date` 必须能够在对应正式交易日历中解释。

注意：

```text
stock_suspend
```

本身是停复牌事件，仍然需要合法市场日期语义。

---

# 47. 多来源一致性

未来存在主/备来源时：

```text
PRIMARY
SECONDARY
```

质量层可以比较：

```text
证券集合
关键字段
日期覆盖
```

但第二来源不能直接覆盖第一来源。

冲突产生：

```text
SOURCE_CONFLICT
```

严重级别由 DataItem 规则确定。

---

# 48. TIMELINESS 质量

Timeliness 不直接以 Tushare 网站的目标更新时间做绝对 BLOCK。

来源文档当前说明例如：

```text
daily：交易日约15～16点入库
daily_basic：交易日约15～17点更新
suspend_d：不定期
```

这些只能作为：

```text
调度参考
```

正式平台质量使用：

```text
expected_business_time
+
RawBatch实际到达时间
+
当前运维策略
```

判断。

---

# 49. 延迟状态

第一版延迟状态：

```text
ON_TIME
LATE
UNKNOWN
```

其中：

```text
UNKNOWN
```

用于来源本身没有稳定更新时间的接口，例如：

```text
suspend_d
```

不能把“不定期更新”判成每天迟到。

---

# 50. LINEAGE 门禁

任何正式 CLEAN 发布单元必须能回答：

```text
来自哪些 RawBatch
由哪个 CleanRun 生成
使用哪个 mapping_version
使用哪个 normalization_version
使用哪个 quality_rule_version
QualityRun 结果是什么
```

任一核心引用缺失：

```text
BLOCK
```

---

# 51. 质量规则版本

统一：

```text
quality_rule_version
```

示例第一版：

```text
quality-v1
```

规则内容变化：

```text
升级版本
```

不能修改旧版本语义。

---

# 52. 规则升级后

新质量规则上线后：

```text
不修改 RAW
```

对受影响范围执行：

```text
QUALITY_RERUN
```

如果新规则发现原正式 CLEAN 有 BLOCK 问题：

```text
标记受影响资产不可用于新任务
保留历史证据
启动修复
```

不能静默删除历史记录。

# 53. 下游读取门禁

后续 DataContext 默认只返回：

```text
PUBLISHED
AND
_quality_status IN ('PASS','WARN')
```

其中：

```text
WARN
```

必须能够让调用方知道存在警告。

# 54. BLOCK 数据的下游行为

被 BLOCK 的最新候选：

```text
不进入正式 CLEAN
```

因此下游看到的是：

```text
上一版正式好数据
```

或：

```text
明确“当前无正式可用数据”
```

不能返回半成品候选。

# 55. WARN 的下游行为

WARN 数据仍可使用，但：

```text
DataContext
Report
AI
```

必须能够读取：

```text
warning_count
warning_types
```

不能把 WARN 当成完全无问题的 PASS。

# 56. 质量问题与运维动作

标准闭环：

```text
QualityIssue OPEN
↓
判断问题类型
├─ 缺源数据 → BACKFILL
├─ 来源失败 → RETRY
├─ RAW有但标准化规则错 → RERUN
├─ 规则本身错误 → 升级规则 + RERUN
└─ 来源真实异常 → 人工复核
↓
REPAIRING
↓
重新清洗
↓
重新质量检查
↓
通过
↓
RESOLVED
```

# 60. P4.5 正式决策

本文件确认：

1. 质量维度固定为 SCHEMA / UNIQUENESS / VALIDITY / COMPLETENESS / CONTINUITY / CONSISTENCY / TIMELINESS / LINEAGE；
2. 规则严重级别为 INFO / WARN / BLOCK；
3. 第一版不使用质量总分决定是否发布；
4. 任一 BLOCK 失败即可阻断对应发布单元；
5. QualityRun 与 QualityIssue 分离；
6. DataGap 只描述“应有但缺失”的数据范围；
7. Gap 只有补采、清洗、复检全部完成后才能关闭；
8. BLOCKED 新候选不能覆盖已有正式 CLEAN；
9. 全市场日线完整度优先比较 ExpectedSet 与 ActualSet，不用百分比掩盖已确认缺口；
10. 新股、退市、停牌必须从 ExpectedSet 逻辑中正确处理；
11. 无法精确判断历史交易资格时 WARN，不制造假缺口；
12. 复权因子缺失只阻断复权派生，不阻断未复权行情；
13. daily_basic 与 daily 做跨表 close 一致性校验；
14. 分钟完整性必须基于版本化 ExpectedMinuteGrid，不写死“每天240条”；
15. 分钟停牌时段从预期时间网格中排除；
16. 分钟 OHLC 可与日线交叉校验；
17. 分钟成交量/成交额在真实覆盖口径确认前只做 WARN 观察；
18. 财务多版本不是重复错误；
19. 财务可用日期必须晚于有效公告日期；
20. 正式 CLEAN 血缘断裂属于 BLOCK；
21. 来源理论更新时间只用于调度参考，质量以平台实际时间证据为准；
22. WARN 数据可发布但必须对下游显式可见；
23. BLOCK 候选禁止下游读取；
24. 质量修复继续复用 P3 的 BACKFILL / RETRY / RERUN / Worker 恢复体系；
25. 第一版质量规则版本命名 `quality-v1`。
