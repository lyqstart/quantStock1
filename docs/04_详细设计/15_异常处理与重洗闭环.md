# 2. 总体原则

P4 不新建第二套修复基础设施。

继续使用 P3 已经真实验证的：

```text
PostgreSQL任务事实
Scheduler
Worker
Lease
Heartbeat
Retry
Backfill
幂等
Audit
Worker失联恢复
```

P4 新增的是：

```text
问题分类
↓
修复动作选择
↓
任务关联
↓
重新清洗
↓
重新质量检查
↓
问题关闭
```

因此：

```text
P4 = 在P3运行基础设施上增加数据治理闭环
```

---

# 3. 一条正式异常闭环

标准闭环：

```text
QualityRun
↓
发现问题
↓
QualityIssue = OPEN
↓
判断问题类型
↓
选择修复动作
↓
创建受控任务
↓
QualityIssue = REPAIRING
↓
执行修复
↓
重新清洗
↓
重新质量检查
↓
验证问题是否消失
├─ 是
│  ↓
│ RESOLVED
│
└─ 否
   ↓
继续OPEN / REPAIRING
或停止自动修复等待人工处理
```

关键原则：

```text
修复任务SUCCEEDED
≠
质量问题RESOLVED
```

只有新的质量证据证明问题已经消失，才能关闭。

---

# 4. 问题先分类，再决定动作

禁止：

```text
发现任何问题
→ 一律Retry
```

正式分类：

```text
执行失败
来源临时失败
来源范围缺失
RAW已有但需要重新标准化
来源数据需要定向重新获取
质量规则变化
规则代码错误
来源真实异常
人工业务判断
```

不同问题必须走不同修复动作。

---

# 5. P3 run_type 继续作为唯一运行语义

继续使用已经确定的：

```text
INITIALIZE
INCREMENTAL
BACKFILL
REPAIR
RETRY
RERUN
PROBE
MIGRATION
```

P4 不新增：

```text
QUALITY_RETRY
CLEAN_RETRY
QUALITY_RERUN
```

这类重复 run_type。

任务执行阶段由：

```text
TaskDefinition / handler / stage
```

表达。

因此：

```text
RERUN
```

可以是：

```text
重新执行Clean
重新执行Quality
重新执行Clean + Quality
```

但它们仍然属于同一个“重新运行”业务语义。

---

# 6. RETRY 的正式定义

RETRY 只解决：

```text
原任务逻辑和数据范围都正确
但执行过程中发生临时失败
```

典型：

```text
网络超时
临时连接失败
来源服务临时不可用
数据库连接瞬时失败
Worker中断后人工再次执行
```

RETRY：

```text
不扩大数据范围
不修改业务规则
不修改来源身份
不改变发布语义
```

---

# 7. RETRY 不解决什么

以下不能靠无限 RETRY：

```text
权限不足
Token错误
接口不存在
Schema变化
字段无法解析
数据业务键非法
质量BLOCK
已确认的数据缺口
规则代码错误
```

这些问题需要：

```text
BACKFILL / REPAIR / RERUN / 代码修复 / 人工处理
```

---

# 8. BACKFILL 的正式定义

BACKFILL 解决：

```text
应该存在的数据范围
当前 RAW 根本没有完整获取
```

典型：

```text
某交易日日线缺一批证券
某股票缺一段历史日期
分钟存在明确时间缺口
初始化历史区间遗漏
```

BACKFILL 的输入必须来自明确范围：

```text
DataGap
或
人工指定 scope
```

---

# 9. BACKFILL 必须最小范围

禁止：

```text
发现600000.SH缺1天
→ 重跑全市场10年
```

正式原则：

```text
能精确到证券
就不扩大到全市场

能精确到日期
就不扩大到整月

能精确到分钟时间段
就不扩大到整年
```

这样降低：

```text
数据源压力
数据库写入量
修复风险
修复时间
```

---

# 10. REPAIR 的正式定义

REPAIR 用于：

```text
已确认某个数据范围存在业务缺陷
需要执行有针对性的修复流程
```

典型：

```text
来源返回过截断数据，需要重新分页
某批RAW来源异常，需要重新抓取
来源历史修订，需要定向刷新
某个DataGap需要结合多个接口修复
```

REPAIR 与 BACKFILL 的区别：

```text
BACKFILL
= 缺的数据补回来

REPAIR
= 已知错误的数据范围按修复方案重建
```

---

# 11. RERUN 的正式定义

RERUN 解决：

```text
RAW可以继续使用
但处理规则或检查规则需要重新执行
```

典型：

```text
mapping_version升级
normalization_version升级
quality_rule_version升级
修复清洗代码后重新处理
修复质量规则后重新检查
```

RERUN：

```text
原则上不重新请求外部数据源
```

除非修复方案明确要求来源刷新，此时应使用 REPAIR。

---

# 12. 动作选择矩阵

| 问题 | 正式动作 |
|---|---|
| 网络/临时服务失败 | `RETRY` |
| Worker LOST | Worker自动接管；必要时 `RETRY` |
| RAW缺日期/证券/时间范围 | `BACKFILL` |
| 已知RAW批次有来源缺陷 | `REPAIR` |
| 来源历史修订需要定向刷新 | `REPAIR` |
| mapping规则修正 | `RERUN` |
| normalization规则修正 | `RERUN` |
| quality规则修正 | `RERUN` |
| 权限/认证失败 | 停止自动修复，人工处理 |
| Schema不兼容 | 停止自动修复，升级代码/映射后 `RERUN` |
| 来源真实业务异常 | 人工复核 |
| 多来源冲突 | 人工复核或按正式来源策略处理 |

# 13. QualityIssue 与任务必须关联

一个 QualityIssue 可以经历多次修复。

因此不能只在 Issue 上保存：

```text
last_task_id
```

第一版增加轻量关联关系：

```text
quality.issue_task_link
```

建议字段：

```text
issue_task_link_id UUID PRIMARY KEY
issue_id UUID NOT NULL
task_id UUID NOT NULL
action_type varchar(16) NOT NULL
created_at timestamptz NOT NULL
created_by varchar(128) NOT NULL
```

唯一约束：

```text
(issue_id, task_id)
```

---

# 14. 为什么需要 issue_task_link

它必须能够回答：

```text
这个问题尝试修过几次？
每次用了什么动作？
哪个任务失败了？
哪个任务成功了？
最终是哪次修复解决的？
```

不能靠翻日志猜。

---

# 15. 修复任务的幂等键

自动修复任务必须有稳定幂等键。

建议输入：

```text
issue_id
+
action_type
+
repair_scope
+
source_binding_version
+
mapping_version
+
normalization_version
+
quality_rule_version
```

同一个问题、同一个规则版本、同一个修复范围：

```text
只允许一个有效修复任务
```

避免 Scheduler 每轮扫描都重复创建。

---

# 16. 自动修复状态

QualityIssue 状态继续使用 P4.5 已确认的：

```text
OPEN
REPAIRING
RESOLVED
ACCEPTED
```

另外增加运行控制字段：

```text
repair_attempt_count
auto_repair_exhausted
next_repair_at
last_repair_task_id
```

不再增加第二套复杂状态机。

---

# 17. OPEN

问题存在。

可能是：

```text
尚未分类
等待自动修复
等待人工处理
自动修复已耗尽
```

具体原因通过：

```text
issue_type
auto_repair_exhausted
next_repair_at
```

表达。

---

# 18. REPAIRING

至少存在一个与该 Issue 关联的有效修复链：

```text
PENDING
RUNNING
VALIDATING
```

Issue 才能进入：

```text
REPAIRING
```

修复任务结束后不能自动直接：

```text
REPAIRING → RESOLVED
```

必须等质量复检。

---

# 19. RESOLVED

只有满足：

```text
新的 QualityRun 已完成
+
对应规则重新执行
+
原问题条件已经不存在
```

才能：

```text
RESOLVED
```

必须记录：

```text
resolved_at
resolution_type
resolved_by_quality_run_id
```

---

# 20. ACCEPTED

只允许用于：

```text
WARN级问题
```

或明确不影响正式业务的数据事实。

例如：

```text
历史证券area字段长期缺失
```

可以人工：

```text
ACCEPTED
```

但：

```text
BLOCK问题默认不能 ACCEPTED 后强制发布
```

P4 第一版不开放“人工绕过BLOCK门禁”。

---

# 21. 修复预算

任何自动修复都必须有预算。

不能：

```text
失败
→ retry
→ retry
→ retry
→ 永远循环
```

预算来源：

```text
TaskDefinition
SourceBinding
QualityRule
```

配置：

```text
max_attempts
backoff_policy
cooldown
```

具体数值由接口和规则配置确定，不在治理文档里给所有接口写同一个拍脑袋次数。

---

# 22. 自动修复耗尽

达到配置预算后：

```text
auto_repair_exhausted = true
QualityIssue 保持 OPEN
停止自动创建新任务
```

系统必须：

```text
在运维界面显式展示
```

不能继续后台无限重试。

---

# 23. 临时错误退避

RETRY 使用：

```text
指数/分级退避
+
来源限频约束
```

但：

```text
RateLimiter
```

仍然是统一来源请求控制点。

修复逻辑不能绕过 RateLimiter。

---

# 24. 同一问题只允许一条活跃修复链

一个 Issue 同时只能存在一条：

```text
PENDING/RUNNING/VALIDATING
```

修复链。

如果当前已经有活跃任务：

```text
新自动修复请求直接复用/跳过
```

不能并发创建两套修复任务相互覆盖。

---

# 25. DataGap 的修复

DataGap：

```text
OPEN
↓
BACKFILL / REPAIR 创建
↓
REPAIRING
↓
RAW到账
↓
CLEAN重新生成
↓
Quality重新检查
↓
VERIFYING
↓
缺口消失
↓
RESOLVED
```

---

# 26. DataGap 与 QualityIssue 的关系

一个 Gap 可以：

```text
关联一个或多个 QualityIssue
```

例如：

```text
某交易日缺600000.SH日线
```

可以同时触发：

```text
COMPLETENESS issue
CONTINUITY issue
```

但实际缺口只需要一个：

```text
DataGap
```

避免重复补采同一范围。

---

# 27. 修复任务成功后的动作

修复任务 SUCCEEDED 后，根据动作类型进入下一步：

## RETRY / BACKFILL / REPAIR

```text
RAW变化
↓
触发对应 Clean RERUN
↓
QualityRun
```

---

## Clean RERUN

```text
候选CLEAN变化
↓
QualityRun
```

---

## Quality RERUN

```text
直接重新QualityRun
```

不必重复访问外部数据源。

---

# 28. 修复链必须自动串联

正式目标：

```text
BACKFILL成功
```

不能依赖人工再执行：

```text
“现在请运行clean”
```

系统应根据任务结果：

```text
自动创建下一阶段任务
```

整个链由关联ID追溯。

---

# 29. 修复链 trace_id

一个问题从发现到解决使用同一治理追踪链：

```text
QualityIssue
↓
Repair Task
↓
CleanRun
↓
QualityRun
↓
Issue Resolution
```

这些对象必须能够通过：

```text
trace_id
```

或明确外键关系串起来。

---

# 30. 重洗不能直接覆盖正式 CLEAN

RERUN 先生成：

```text
新的 Clean Candidate / CleanBatch
```

不能：

```text
边转换
边UPDATE正式CLEAN
```

标准流程：

```text
旧正式CLEAN
保持可用

新Candidate
↓
QualityRun
├─ PASS/WARN
│   ↓
│ 原子切换
│
└─ BLOCK
    ↓
  丢弃正式发布资格
  旧CLEAN继续有效
```

---

# 31. CleanBatch 的发布状态

建议：

```text
CANDIDATE
VALIDATING
PUBLISHED
BLOCKED
SUPERSEDED
```

---

## 31.1 CANDIDATE

清洗完成，尚未进入正式数据。

---

## 31.2 VALIDATING

正在执行质量规则。

---

## 31.3 PUBLISHED

成为当前正式 CLEAN 发布单元。

---

## 31.4 BLOCKED

质量不允许发布。

---

## 31.5 SUPERSEDED

曾经正式发布，但已经被更新的正式批次替代。

仍保留追溯。

---

# 32. 原子发布

一个发布单元必须事务化：

```text
写入/更新正式CLEAN
+
切换CleanBatch状态
+
登记血缘
+
登记质量状态
```

任何一步失败：

```text
整个发布回滚
```

不能出现：

```text
CLEAN更新了一半
Batch却显示PUBLISHED
```

---

# 33. 普通事实数据重洗

例如：

```text
stock_daily
stock_daily_basic
stock_limit_price
```

同一业务主键：

```text
新标准值 = 旧标准值
```

则：

```text
UNCHANGED
```

不做无意义 UPDATE。

---

# 34. 普通事实发生变化

来源修订后：

```text
新标准值 != 旧标准值
```

质量通过后：

```text
更新当前正式CLEAN
```

同时保留：

```text
旧RawBatch
新RawBatch
旧content_hash
新content_hash
旧CleanBatch
新CleanBatch
```

以便解释变化来源。

---

# 35. 财务重洗

财务数据不采用普通覆盖。

如果：

```text
同报告期
content_hash变化
```

则：

```text
新增历史版本
```

质量通过后：

```text
新的版本获得新的历史可用关系
```

旧版本继续保留。

---

# 36. 复权因子重洗

`stock_adj_factor`：

```text
同证券同交易日因子变化
```

质量通过后：

```text
更新当前正式因子
新增 stock_adj_factor_history 版本
标记受影响复权派生资产 STALE
```

不能只更新因子却不通知派生资产。

---

# 37. mapping_version 升级

字段映射变化：

```text
mapping-v1
→
mapping-v2
```

处理：

```text
RAW不变
↓
按受影响DataItem/日期范围创建RERUN
↓
生成新Candidate
↓
quality-v?检查
↓
通过后发布
```

---

# 38. normalization_version 升级

例如：

```text
成交量单位规则修正
证券代码标准化修正
日期解析修正
```

这是高风险重洗。

必须：

```text
先小样本验证
↓
再受控范围RERUN
↓
质量比较
↓
最后扩大范围
```

不能直接全库覆盖。

---

# 39. quality_rule_version 升级

例如：

```text
quality-v1
→
quality-v2
```

如果 CLEAN 业务值不变：

```text
优先只执行 Quality RERUN
```

不重复：

```text
访问来源
重写CLEAN
```

---

# 40. 规则升级采用分批推进

正式顺序：

```text
1. 单证券/单日样本
2. 单交易日全市场
3. 小范围历史
4. 全目标历史
```

每一步必须：

```text
质量通过
+
差异可解释
```

才进入下一步。

---

# 41. 重洗差异报告

每次规则升级 RERUN 必须产生差异统计：

```text
old_rows
new_rows
unchanged_rows
changed_rows
added_rows
removed_rows
blocked_rows
warning_rows
```

对于变化记录至少能按范围查询：

```text
业务主键
旧hash
新hash
变化字段
```

---

# 42. 删除不能作为默认重洗动作

禁止：

```text
DROP旧CLEAN
TRUNCATE旧CLEAN
重新全量生成
```

作为默认方案。

原因：

```text
失去正式可用旧版本
放大失败影响
难以回滚
```

只允许在明确初始化环境、无正式下游依赖时使用全量重建。

---

# 43. 质量规则发现旧数据有问题

如果：

```text
quality-v2
```

发现以前 `quality-v1` 已发布的数据存在 BLOCK 问题：

```text
不能修改历史事实说“当时从没发布过”
```

正式处理：

```text
原发布历史保留
↓
当前资产门禁标记受影响范围不可用于新任务
↓
创建QualityIssue
↓
修复
↓
新版本发布
```

---

# 44. 已运行研究任务的可追溯性

如果某次历史研究使用过后来发现有问题的数据：

```text
不回写修改研究结果
```

而是标记：

```text
输入数据版本已发现质量问题
```

以后 P5/P6 的研究结果必须记录：

```text
使用的数据版本
```

这样才能判断是否需要重算。

---

# 45. 人工复核权限

人工不能直接修改 RAW 或 CLEAN 业务行。

正式人工动作：

```text
查看问题
重新分类问题
触发BACKFILL
触发REPAIR
触发RERUN
暂停自动修复
恢复自动修复
接受WARN
补充处理说明
```

# 49. 自动修复触发点

```text

├─ 可自动修复
│   ↓

│
```

不要求 Scheduler 高频扫描日志文本来猜问题。

```text
治理元数据
```

# 53. 防止问题风暴

如果一个根因导致：

```text
5000只股票
同一交易日
同一种错误
```

不能创建：

```text
5000个全市场BACKFILL任务
```

正式要求：

```text
Issue可以行级/证券级记录
RepairPlan按可安全合并的scope聚合
```

例如：

```text
2026-07-27 全市场日线来源截断
```

创建：

```text
1个 trade_date 修复任务
```

而不是每只证券一个任务。

---

# 54. 修复范围聚合不能掩盖问题

修复任务可以合并范围：

```text
多个Issue
→ 一个Repair Task
```

但 `issue_task_link` 必须保留：

```text
每个Issue
↓
关联到这个Task
```

修复后逐个复检 Issue。

---

# 55. 防止修复循环

同一个 Issue 如果：

```text
相同 action_type
相同 scope
相同来源版本
相同规则版本
```

已经执行成功，但复检仍失败：

```text
不能自动再重复同一动作
```

正式：

```text
auto_repair_exhausted = true
```

等待：

```text
规则变化
来源变化
人工选择新方案
```

---

# 56. 成功但无变化

例如：

```text
BACKFILL成功
但RAW仍没有缺失数据
```

这是：

```text
修复任务执行成功
但问题未解决
```

Issue：

```text
继续OPEN
```

并停止重复相同自动动作。

---

# 57. 修复任务失败

任务 FAILED：

```text
Issue不关闭
```

处理：

```text
如果失败可重试
→ RETRY预算内处理

如果不可重试
→ Issue保持OPEN
→ auto_repair_exhausted=true或等待人工
```

```text
3. 原rule_code重新检查
4. 原scope不再命中问题
```

# 67. P4.6 正式决策

本文件确认：

1. P4 修复继续复用 P3 已验证的 PostgreSQL + Scheduler + Worker 基础设施；
2. 不建立第二套修复队列和第二套任务状态机；
3. RETRY 只处理原任务逻辑正确的临时执行失败；
4. BACKFILL 只处理明确数据缺口；
5. REPAIR 处理已知缺陷范围的针对性重建；
6. RERUN 处理已有RAW上的规则重跑；
7. P4 不新增 CLEAN/QUALITY 专用 run_type；
8. QualityIssue 与修复任务通过 `quality.issue_task_link` 建立多次修复追溯；
9. 自动修复任务必须有幂等键；
10. 同一Issue同时只允许一条活跃修复链；
11. 自动修复必须有预算，耗尽后停止循环；
12. 修复任务SUCCEEDED不能直接关闭Issue；
13. Issue必须经过重新清洗/重新Quality验证后才能RESOLVED；
14. DataGap必须在质量复检确认缺口消失后才能关闭；
15. RERUN先产生Candidate，不能直接覆盖正式CLEAN；
16. 新Candidate BLOCK时旧正式CLEAN继续保持；
17. CleanBatch正式状态采用 CANDIDATE / VALIDATING / PUBLISHED / BLOCKED / SUPERSEDED；
18. 正式发布必须事务化；
19. 普通事实只有内容变化才更新正式值；
20. 财务版本变化新增版本，不覆盖历史；
21. 复权因子变化建立history并使相关派生资产STALE；
22. mapping/normalization/quality规则升级均使用受控RERUN；
23. 规则升级先样本、再单日、再历史范围逐步扩大；
24. 每次重洗必须产生差异报告；
25. 不以TRUNCATE + 全量重建作为默认重洗方案；
26. 人工不能直接修改RAW/CLEAN业务事实；
27. 人工可以触发修复、暂停自动修复、接受WARN；
28. 第一版不提供BLOCK强制发布后门；
29. 所有人工写动作必须审计；
30. 自动修复策略进入 RepairPolicy，不散落为Worker硬编码；
31. 多个Issue可以合并成一个安全范围的修复任务，但必须逐Issue保留关联；
32. 相同修复方案执行成功但问题仍存在时，禁止无限重复；
33. 日志不是治理事实库，状态必须进入PostgreSQL；
34. P4 第一批必须真实验证完整异常修复闭环。
