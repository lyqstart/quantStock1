# 3. 存储设计总原则

第一版采用：

```text
普通 PostgreSQL
+
TimescaleDB 仅用于真正的大时间序列表
```

禁止：

```text
所有表都分区
所有表都建 hypertable
所有查询字段都加索引
```

目标是：

```text
最小复杂度
+
明确收益
+
可维护
```

# 4. 表类型分级

第一版把表分为四类：

```text
A. 小型管理表
B. 日级/低频业务事实表
C. 高频分钟事实表
D. 运行与治理事实表

```

# 7. 为什么日线第一版不分区

按当前 A 股规模，日线虽然长期可达到千万级甚至更高，但当前服务器和 PostgreSQL 能够处理这一量级。

提前按：

```text
年
月
交易所
```

切大量分区会增加：

```text
迁移复杂度
索引维护复杂度
SQL规划复杂度
运维复杂度
```

但当前还没有真实性能证据证明必须分区。

因此正式规则：

```text
先建正确主键和必要索引
↓
持续测量
↓
真实出现性能或维护证据
↓
再决定是否分区
```

---

# 8. 日级表未来分区触发条件

只有出现至少一种真实证据时才评估分区：

```text
单表索引明显无法驻留合理工作集
典型查询持续超过P4/P5服务目标
VACUUM/维护时间成为明确问题
历史删除/归档需要按大范围日期高频执行
单表规模已经影响备份恢复
```

不能使用：

```text
“千万行听起来很多”
```

作为分区依据。

---

# 9. C类：分钟事实表

分钟数据是 P4 当前唯一明确的超大规模时间序列。

包括：

```text
raw.tushare_stk_mins
clean.stock_minute
```

正式目标：

```text
TimescaleDB hypertable
```

时间维度：

```text
trade_time
```

---

# 10. 分钟表不做证券哈希分区

第一版不增加 TimescaleDB space partition：

```text
security_code hash partition
```

原因：

```text
当前单服务器
单PostgreSQL实例
单主要磁盘
4核CPU
没有分布式节点
```

增加空间分区无法带来当前已证明的分布式收益，反而增加维护复杂度。

第一版：

```text
只按 trade_time 时间维度管理 chunk
```

---

# 11. 分钟 chunk interval 不在设计阶段拍脑袋写死

当前 P3 只完成：

```text
1只股票
1个交易日
241条
```

真实全市场 1m 的：

```text
平均每交易日行数
实际表字节数
实际索引字节数
压缩比
写入速度
典型查询速度
```

尚未通过新系统实测。

因此 P4 不写死：

```text
chunk = 1天
chunk = 7天
chunk = 1个月
```

正式确定方法：

```text
先采集真实全市场小范围分钟样本
↓
测每交易日表+索引实际字节数
↓
测典型查询
↓
选择 chunk interval
↓
记录为 StoragePolicy 版本
```

---

# 12. chunk interval 选择原则

选择目标：

```text
活跃chunk索引工作集能够被内存有效缓存
单chunk不能大到维护和重压缩成本过高
chunk数量不能多到规划和元数据成本过高
```

最终 interval 必须由基准测试证据记录。

---

# 13. CLEAN 分钟主键/唯一性

`clean.stock_minute` 业务唯一性：

```text
(security_code, frequency, trade_time)
```

TimescaleDB 唯一索引必须包含：

```text
trade_time
```

满足时间分区约束。

# 14. 分钟第一版核心索引

第一版只保留真正确定的查询路径：

```text
(security_code, frequency, trade_time DESC)
```

用于：

```text
单股票时间区间
股票列表时间区间
最近N分钟
```

---

# 15. 分钟暂不增加全市场时间截面大索引

暂不默认建立：

```text
(trade_time, security_code)
```

原因：

```text
这是超大索引
会明显增加写入与存储成本
```

只有 P5 DataContext / P6 Feature 的真实查询证明：

```text
高频按某一分钟全市场截面读取
```

是核心路径时才评估建立。

---

# 16. 不建立重复索引

如果主键/唯一索引已经覆盖某查询前缀：

```text
不再建立等价索引
```

每增加一个索引都必须回答：

```text
服务哪个正式查询？
EXPLAIN证据是什么？
增加多少存储？
增加多少写入成本？
```

```text

```

# 28. RAW 非分钟数据生命周期

第一批以下 RAW：

```text
stock_basic
trade_calendar
stock_daily
adj_factor
daily_basic
suspend_d
stk_limit
income
fina_indicator
```

数据量相对可控。

第一版：

```text
长期保留
不启用自动删除
```

原因：

```text
支持重洗
支持规则升级
支持质量追溯
支持来源修订调查
```

---

# 29. RAW 分钟数据生命周期

分钟 RAW 是最大容量风险。

第一版原则：

```text
不在尚未测量实际容量时承诺永久在线保留全部RAW分钟历史
```

同时：

```text
P4首次上线不启用自动删除
```

先完成容量测量和归档验证。

---

# 30. 为什么分钟 RAW 不能直接永久承诺

全市场分钟数据长期增长可能达到：

```text
数亿行/年
```

具体实际体积必须由 quantStock1 实测。

当前单服务器 SSD 容量有限，且旧项目已经存在大体量数据。

因此：

```text
永久保留CLEAN分钟
```

与：

```text
永久在线保留所有RAW分钟
```

必须分开决策。

```text

交易日历

复权因子
每日指标
停复牌
涨跌停
财务

```

第一版均属于长期研究资产：

```text
不设置自动删除期限
```

---

# 32. CLEAN 分钟使用压缩降低长期成本

`clean.stock_minute` 历史 chunk 在进入稳定历史区间后：

```text
启用 TimescaleDB 压缩/列式历史存储能力
```

目标：

```text
近期数据：易写、易修复
历史数据：高压缩、主要读取
```

---

# 33. 压缩时间不能拍脑袋固定

不能在设计阶段写死：

```text
7天后压缩
30天后压缩
```

需要先观察：

```text
历史修订频率
分钟补采频率
修复窗口
压缩/解压成本
```

然后确定：

```text
HOT_MUTABLE_WINDOW
```

并进入 StoragePolicy 版本。

---

# 34. 压缩后仍允许受控修复

历史数据压缩不代表：

```text
永远不能改
```

如果需要 REPAIR / RERUN：

```text
定位受影响chunk
↓
受控解压/修改
↓
质量验证
↓
重新压缩
```

全过程必须审计。

---

# 35. 不创建5套分钟历史副本

继续执行 P4.1/P4.2 决策：

```text
长期基础粒度 = 1min
```

默认不永久保存：

```text
1m
5m
15m
30m
60m
```

五套完整历史。

其他周期：

```text
由1m确定性聚合
```

只有真实性能证据出现后才允许物化特定周期。

# 36. 暂不默认建立 Timescale Continuous Aggregate

P4 不提前建立：


因为：

```text

```

# 38. 行级质量明细需要控制体量

如果一次全市场问题产生大量行级异常：

```text
不能把几百万条重复错误文本永久塞入QualityIssue
```

正式策略：

```text
Issue保存问题身份和范围
明细采用结构化scope/样本/关联表
重复问题按fingerprint聚合
```

既保留可追溯性，又避免质量库本身失控。

# 42. AUDIT 生命周期

`audit` 属于正式操作追溯。

第一版：

```text
长期保留
不自动删除
```

尤其：

```text
人工补采
重洗
质量接受
暂停/恢复
数据归档/删除
```

必须永久可追溯到当前存储策略允许的范围。

---

# 43. MIGRATION 生命周期

`migration` 保存旧 quantStock → quantStock1 的迁移事实。

迁移完成后：

```text
不再增长
但长期保留迁移记录
```

旧 quantStock 不能因此成为 quantStock1 运行依赖。

---

# 44. 存储位置原则

正式活动数据库：

```text
优先使用SSD
```

备份盘：

```text
用于备份/归档职责
```

P4 不采用：

```text
为了多一点空间
把一个活跃PostgreSQL实例随意拆成跨磁盘tablespace
```

当前单机架构优先保持：

```text
数据库存储简单
故障边界清晰
```

---

# 45. 备份不能当作扩展在线磁盘

以下做法禁止：

```text
SSD满了
→ 直接把部分活跃表挪到备份目录
→ 应用继续当在线库使用
```

归档数据如果需要恢复：

```text
必须有正式restore路径
```

---

# 46. 删除前必须先证明可恢复

任何正式数据删除/冷归档必须满足：

```text
归档成功
+
校验成功
+
恢复流程验证成功
+
审计记录成功
```

才能删除在线副本。

不能只因为：

```text
“备份文件看起来存在”
```

就删除正式数据。

---

# 47. StoragePolicy

P4 增加版本化治理对象：

```text
StoragePolicy
```

至少包含：

```text
policy_code
data_item
storage_class
partition_mode
chunk_interval
compression_enabled
hot_mutable_window
online_retention
archive_required
policy_version
enabled
```

没有适用值的字段：

```text
NULL
```

不能用假默认值填满配置。

---

# 48. 第一版 StorageClass

统一：

```text
HOT
WARM
ARCHIVED
```

含义：

```text
HOT      = 高频写入/修复
WARM     = 在线历史读取，低修改
ARCHIVED = 不在主查询路径，需恢复后读取
```

---

# 49. 当前第一版数据分类

```text
非分钟RAW             → HOT/WARM，长期在线
非分钟CLEAN           → HOT/WARM，长期在线
近期分钟RAW           → HOT
历史分钟RAW           → WARM，未来可归档
近期分钟CLEAN         → HOT
历史分钟CLEAN         → WARM + 压缩
QUALITY/OPS/AUDIT摘要 → WARM，长期在线
```

P4 第一版不立即执行 ARCHIVED 删除动作。

先建立策略和实测。

---

# 50. 磁盘保护阈值

沿用项目已确认容量阈值：

```text
< 70%  NORMAL
>=70%  WATCH
>=75%  WARNING
>=80%  RESTRICT
>=85%  PROTECT
```

阈值按：

```text
承载PostgreSQL正式数据的文件系统
```

计算。

---

# 51. NORMAL：低于70%

允许：

```text
正常增量采集
普通补采
已批准历史初始化
清洗/质量重跑
```

仍持续记录增长速度。

---

# 52. WATCH：达到70%

动作：

```text
产生容量告警
重新估算剩余可用天数
检查增长最快DataItem
检查压缩是否正常
```

不自动停止业务。

---

# 53. WARNING：达到75%

动作：

```text
禁止未经容量评估的新大型历史初始化
暂停非必要批量实验性导入
要求生成容量处置计划
```

正常：

```text
日级增量
关键补采
```

仍可继续。

---

# 54. RESTRICT：达到80%

动作：

```text
停止非必要历史BACKFILL
停止大规模分钟初始化
限制非关键RERUN
优先执行已验证压缩/归档
```

保留：

```text
最新正式市场数据
关键修复
数据库运维
```

---

# 55. PROTECT：达到85%

进入保护模式：

```text
禁止新的高容量分钟采集范围扩张
禁止大型历史初始化
禁止非关键重复重洗
```

仍应优先保证：

```text
数据库可用
核心日级增量
质量/审计事实
恢复操作
```

如果继续增长威胁数据库稳定：

```text
再由运维明确决定暂停具体DataItem
```

不能自动粗暴停止整个PostgreSQL。

---

# 56. 不按总磁盘百分比唯一判断

除使用率外，还必须记录：

```text
free_bytes
db_size_bytes
data_item_size_bytes
daily_growth_bytes
estimated_days_to_threshold
```

因为：

```text
80%的100GB
```

和：

```text
80%的2TB
```

风险不同。

# 58. 全市场分钟历史初始化前置门槛

在启动全市场分钟历史初始化前，必须完成：

```text
1. 真实全市场若干交易日样本采集
2. RAW实际bytes/day
3. CLEAN实际bytes/day
4. 索引实际bytes/day
5. 压缩后bytes/day
6. 单日清洗耗时
7. 单日质量检查耗时
8. 单股票时间区间查询性能
9. 估算目标历史范围总容量
10. 估算达到70/75/80/85%阈值的时间
```

没有这些证据：

```text
禁止一次性全历史灌入
```

# 59. 容量估算必须留安全余量

容量规划不能：

```text
空闲1TB
预计数据990GB
→ 允许导入
```

必须保留：

```text
数据库运行空间
WAL
索引重建
VACUUM
迁移
临时文件
备份/恢复操作
```

因此历史初始化审批使用：

```text
PROTECT阈值
```

而不是把磁盘用到100%。

---

# 60. 索引建设原则

第一版每张事实表只建立：

```text
业务唯一性
核心按证券查询
核心按交易日查询
point-in-time必要索引
```

不建立：

```text
“也许以后能用”的索引
```

---

# 61. 索引新增流程

后续新增索引必须有：

```text
真实慢查询
SQL
EXPLAIN/EXPLAIN ANALYZE
当前耗时
目标查询频率
预计索引大小
新增后写入影响
```

验证有效后再进入 Alembic。

---

# 62. 禁止生产直接手工CREATE INDEX后不留迁移

所有正式索引变化：

```text
必须进入Alembic
+
文档
+
测试
```

生产临时诊断索引如果建立：

```text
必须明确临时身份并及时删除
```

---

# 63. VACUUM / ANALYZE 原则

第一版依赖 PostgreSQL 正常：

```text
autovacuum
autoanalyze
```

不建立：

```text
每天固定VACUUM FULL
```

这样的高风险默认任务。

---

# 64. 禁止周期性 VACUUM FULL

`VACUUM FULL`：

```text
需要重写表
需要额外空间
会产生锁影响
```

只在真实膨胀证据和维护窗口下人工批准。

不能作为“数据库保养”常规动作。

---

# 65. 大批量重洗与表膨胀

P4 已确定：

```text
内容不变不UPDATE
新Candidate先验证再发布
```

这也是降低表膨胀的重要规则。

大范围 RERUN 前后必须测：

```text
table size
dead tuples
index size
```

# 69. 不破坏血缘

# 72. 备份与归档不是同一概念

```text
Backup
= 整体灾难恢复

Archive
= 数据生命周期迁出
```

不能因为有数据库备份就认为：

```text
某个DataItem可以安全从在线库删除
```

归档必须支持按范围恢复。

---

# 73. RAW 与 CLEAN 的备份优先级

灾难恢复层面：

```text
CLEAN可由RAW重建
```

但：

```text
RAW如果来自不可重复获取的历史来源
可能无法重新获取
```

因此不能简单认为：

```text
CLEAN重要
RAW不重要
```

正式备份策略在部署/运维阶段结合 RPO/RTO 确定。

# 78. P4.7 正式决策

本文件确认：

1. 普通管理表、日级事实、财务事实第一版使用普通 PostgreSQL；
2. 日级表第一版不提前做原生日期分区；
3. 只有真实性能/维护证据出现后才评估日级分区；
4. `raw.tushare_stk_mins` 和 `clean.stock_minute` 是第一批明确的 TimescaleDB hypertable 目标；
5. 分钟 hypertable 第一版只使用 `trade_time` 时间维度，不增加证券哈希空间分区；
6. chunk interval 必须通过真实全市场分钟样本测量后确定；
7. 分钟业务唯一性为 `(security_code, frequency, trade_time)`；
8. 分钟第一版只建立明确服务证券时间序列查询的核心索引；
9. 不提前建立全市场分钟截面超大索引；
10. `stock_daily`、`adj_factor`、`daily_basic`、`limit_price` 等使用“证券+日期主键”和“日期+证券”二级索引；
11. 财务增加报告期和 `available_from_trade_date` 的 point-in-time 查询索引；
12. 非分钟 RAW 第一版长期在线保留，不自动删除；
13. CLEAN 第一版均长期保留；
14. 分钟 RAW 不在容量未测量时承诺永久在线保留全部历史；
15. P4 首次上线不自动删除分钟 RAW，先完成容量和恢复验证；
16. 历史 CLEAN 分钟允许使用 TimescaleDB 压缩能力；
17. HOT_MUTABLE_WINDOW 必须根据真实修订/补采频率确定，不拍脑袋固定；
18. 继续只长期保存 1min 基础粒度，不默认保存五套分钟周期副本；
19. P4 暂不默认建立 Continuous Aggregate；
20. Quality、Audit、迁移和关键运行摘要长期保留；
21. 日志不是治理事实库，可独立滚动；
22. 不通过跨磁盘tablespace扩展当前活跃数据库复杂度；
23. 备份盘不能直接充当活跃数据库扩展盘；
24. 删除在线数据前必须验证归档可恢复；
25. 正式增加版本化 StoragePolicy；
26. 存储等级统一为 HOT / WARM / ARCHIVED；
27. 沿用 70/75/80/85% 磁盘保护阈值；
28. 75% 起禁止未经评估的大型历史初始化；
29. 80% 起限制非必要历史补采、分钟初始化和大规模重洗；
30. 85% 进入保护模式，优先保证核心日级增量、数据库和治理事实；
31. 容量判断同时使用百分比、剩余字节、增长速度和到阈值天数；
32. 全市场分钟历史初始化前必须实测 bytes/day、索引、压缩比、写入和查询性能；
33. 索引新增必须有真实 SQL 和 EXPLAIN 证据；
34. 所有正式索引通过 Alembic 管理；
35. 不把 VACUUM FULL 作为周期维护任务；
36. 数据删除/归档必须走受控任务并先 dry-run；
37. 未解决 QualityIssue/DataGap 相关数据不得删除；
38. RAW 归档后血缘必须继续指向可恢复 archive reference；
39. Backup 和 Archive 是两种不同职责；
40. 第一版 storage policy 命名在实施阶段确定并进入数据库元数据。
