# 3. 追溯的基本原则

正式追溯依赖：

```text
稳定ID
+
明确外键/关联表
+
规则版本
+
内容哈希
+
时间
```

日志不是正式血缘。

`trace_id` 也不是外键的替代品。

正式原则：

```text
外键/对象ID
= 精确事实关系

trace_id
= 一整条业务处理链的聚合查询键
```

# 11. 为什么 CleanRun 必须记录代码身份

规则版本只说明：

```text
采用什么业务规则
```

不能完整回答：

```text
是哪一版程序实际执行
```

因此每次 CleanRun 同时记录：

```text
app_version
code_revision
```

其中：

```text
app_version
= 平台语义版本

code_revision
= Git提交身份
```

未来出现问题时能够回到准确代码证据。

# 12. CleanBatch 是 CLEAN 输出版本单元

正式新增：

```text
clean.clean_batch
```

CleanBatch 表达：

```text
某个 DataItem
某个明确发布范围
使用某组 RAW 输入
按照某版规则
生成的一版标准数据候选/正式结果
```

---

# 13. CleanBatch 与 CleanRun 的区别

```text
CleanRun
= 过程

CleanBatch
= 结果版本
```

例如 Worker 失联：

```text
CleanRun #1 = LOST
CleanRun #2 = SUCCEEDED
```

最终只可能产生：

```text
一个有效 CleanBatch
```

不能把运行次数等同于数据版本次数。

# 16. lifecycle status 与当前质量门禁分开

一个 CleanBatch 可能：

```text
2026-07-28
在 quality-v1 下正式 PUBLISHED

2026-08-10
quality-v2 重新检查后发现 BLOCK
```

不能篡改历史说：

```text
它从来没有PUBLISHED过
```

因此：

```text
status
= 历史发布生命周期

current_quality_run_id
= 当前最新质量判断
```

未来 DataContext 判断是否可用于新任务时：

```text
既看正式发布身份
又看当前有效质量门禁
```

# 17. CleanBatch 的 scope 必须明确

CleanBatch 不能只是：

```text
“stock_daily一批”
```

必须明确发布范围。

例如：

```text
stock_daily:
trade_date=2026-07-27

stock_minute:
security_code=000001.SZ
frequency=1min
trade_date=2026-07-24

financial_income:
security_code=000001.SZ
request_range=2024-01-01..2026-07-27
```

机器字段：

```text
scope_key
scope_json
```

---

# 18. scope_key 用于稳定检索，不承担全部语义

`scope_key`：

```text
稳定
规范化
可索引
```

例如：

```text
trade_date:20260727
```

或：

```text
security:000001.SZ|freq:1min|date:20260724
```

复杂结构保留在：

```text
scope_json
```

不能只保存自由文本 reason。

# 19. CleanBatch 与 RawBatch 是多对多



```text

```

分别请求时，一个正式 security_master 快照可能来自多个 RawBatch。

因此不能在 CleanBatch 上只放：


单字段。

# 23. 正式 CLEAN 行的基础血缘

普通 CLEAN 表按照 P4.2 继续保留：

```text
_clean_batch_id
```

并由：

```text
business key
+
clean_batch_id
```

定位对应的 RAW 行。

例如：

```text
clean.stock_daily
security_code=000001.SZ
trade_date=2026-07-27
_clean_batch_id=B1
```

追溯：

```text
B1
↓
CleanBatchInput
↓
RawBatch集合
↓
在这些RawBatch中
按 ts_code + trade_date
定位原始行
```

# 24. 为什么普通单来源数据不额外建立每行 lineage 表

对于：

```text
stock_daily
adj_factor
daily_basic
limit_price
```

当前转换基本是：

```text
一个RAW业务记录
→
一个CLEAN业务记录
```

如果再为每一行保存：

```text
clean_row_id
raw_row_id
lineage_id
```

会重复大量可由：

```text
_clean_batch_id + business key
```

确定的信息。

第一版不这样做。

```text
无法通过业务键确定来源行
```

这些不是普通路径。

# 33. 行级 content hash

RAW 已经保存：

```text

```

```text

```

原因：

```text

```


# 34. CLEAN 当前值修订不能失去旧事实

普通 CLEAN 表保存：

```text

```

来源历史修订后可能发生 UPDATE。

如果只更新当前表：

```text

```

不满足可追溯要求。

# 37. 为什么 change 只记录发生变化的行

如果每天全市场 5500 条日线：

```text
重复采集结果完全相同
```

就没有理由复制 5500 条历史。

正式策略：

```text
无变化
→ 只保留新的输入/运行血缘

有变化
→ 只记录真正改变的业务键
```

这在可追溯和存储成本之间取得平衡。

---

# 38. old_values / new_values 使用原则

对于普通低频事实修订：

```text
可以保存发生变化字段的旧/新值
```

不要求把整行所有字段重复一遍。

例如：

```json
changed_fields = ["close", "amount_cny"]

old_values = {
  "close": 10.12,
  "amount_cny": 1234567
}

new_values = {
  "close": 10.13,
  "amount_cny": 1234999
}
```

---

# 39. 分钟批量规则升级造成大规模变化时

如果一次 normalization 规则升级造成：

```text
数百万分钟行都变化
```

不能机械地为每行保存巨大 JSON 历史副本。

此类变更优先：

```text
保留旧CleanBatch身份
+
旧RawBatch
+
旧规则版本
+
新CleanBatch
+
新规则版本
+
批次差异统计
```

只对：

```text
异常行
抽样验证
来源真实修订行
```

建立详细 `clean_change`。

---

# 40. 可重建性原则

P4 正式要求：

```text
历史标准数据至少能够确定性重建
```

重建所需证据：

```text
RawBatch
mapping_version
normalization_version
app_version
code_revision
CleanBatch scope
```

因此即使普通当前表只保存最新值，也不能失去生成旧版本所需的输入和规则身份。

---

# 41. Git 提交是规则执行证据之一

`code_revision` 必须指向：

```text
quantStock1 Git commit
```

项目仓库必须长期保留已正式执行版本的提交历史。

禁止：

```text
线上运行临时代码
但Git没有对应提交
```

否则历史 CleanBatch 无法完整复现。

# 100. P4.8 正式决策

本文件确认：

1. P4 继续继承 P2 的 `DataSource → SourceBinding → CollectRun → RawBatch → CleanBatch → DataSnapshot` 主链；
2. P4 不引入独立血缘平台或图数据库；
3. `RawBatch` 继续作为 RAW 最小批次身份；
4. RAW 行现有 `_raw_batch_id`、`_collect_run_id`、`_content_hash` 等字段继续有效；
5. CleanRun 是运行事实，正式放在 `ops.clean_run`；
6. CleanRun 必须记录 `app_version` 和 Git `code_revision`；
7. CleanBatch 是标准数据结果版本，正式放在 `clean.clean_batch`；
8. CleanRun 和 CleanBatch 严格区分“执行过程”和“数据版本”；
9. CleanBatch 使用 `CANDIDATE / VALIDATING / PUBLISHED / BLOCKED / SUPERSEDED` 生命周期；
10. CleanBatch 历史发布身份和当前 Quality 门禁分开表达；
11. CleanBatch 必须保存明确 scope；
12. CleanBatch 与 RawBatch 是多对多关系；
13. 正式新增 `clean.clean_batch_input`；
14. input role 使用 `PRIMARY / SUPPLEMENT / VALIDATION / MIGRATION`；
15. 普通单来源 CLEAN 行通过 `_clean_batch_id + business key` 定位 RAW，不建立冗余全量行级 lineage；
16. 多来源字段合并、冲突裁决等特殊情况使用 `clean.clean_row_source`；
17. 分钟表只保留 `_clean_batch_id` 作为行级血缘入口；
18. 分钟 CleanBatch 固定为“证券+频率+交易日”级发布单元，避免批次范围过粗；
19. CleanBatch 保存候选/正式批次内容 hash；
20. 内容 hash 正式采用 SHA-256；
21. 复杂对象 hash 使用版本化 canonical JSON；
22. 普通当前 CLEAN 发生真实修订时，使用稀疏 `clean.clean_change` 记录变更；
23. 无业务值变化时不生成 change 记录；
24. 低频来源修订可记录发生变化字段的 old/new values；
25. 大规模规则重洗不强制为每个分钟行复制 JSON 变更历史；
26. 历史标准结果必须能通过 RawBatch + 规则版本 + code_revision 确定性重建；
27. 正式执行版本必须存在对应 Git 提交；
28. QualityRun 正式放在 `quality.quality_run`；
29. 一个 CleanBatch 可以存在多个 QualityRun；
30. CleanBatch 同时记录 `published_quality_run_id` 和 `current_quality_run_id`；
31. QualityIssue 和 DataGap 都必须能追溯发现它们的 QualityRun；
32. 修复继续使用 `quality.issue_task_link` 连接 Issue 与任务；
33. `trace_id` 用于聚合业务链，但不能替代正式外键；
34. 财务历史、证券主数据历史、复权因子历史分别使用各自专门版本表表达；
35. 多来源最终值必须能说明哪个来源贡献了哪些字段；
36. 遗留迁移通过 MIGRATION input role 和 LegacyMigrationBatch 保持来源真实身份；
37. RawBatch 归档后 `raw_batch_id` 不改变；
38. 归档必须保存 location/checksum/format/restore policy；
39. P4 不实现完整 DataSnapshot，但必须为 P5 提供稳定 `clean_batch_id / quality_run_id`；
40. 未来 DataSnapshot 必须冻结实际使用的 CleanBatch 集合，不能只记录查询时间；
41. 下游 Feature/Analysis/Backtest/Signal 以后必须记录 `data_snapshot_id`；
42. AI 正式分析也必须能够关联数据版本；
43. 血缘 API 默认返回元数据和身份，不一次输出整批原始数据；
44. Audit 和 Lineage 分工明确：血缘回答“数据怎么来”，审计回答“谁做了什么”；
45. LINEAGE 完整性属于质量 BLOCK 规则；
46. P4 实施必须真实完成普通日线、多RawBatch、分钟、修复链、财务版本、因子版本等追溯验收。
