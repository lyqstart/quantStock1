# P4质量规则变更重质检闭环修复说明

> 版本：0.8.2  
> 日期：2026-07-28

## 1. 现场现象

`stock_limit_price` 在 0.8.1 已部署、`quality-v3` 已生效后再次执行清洗，最新结果仍为：

```text
BLOCKED|BLOCKED|5533/7709|skip=2176|reject=0|quality=quality-v2
```

说明新的质量规则没有形成新的 QualityRun。

## 2. 根因

P4 的 CleanBatch 唯一身份由来源数据、范围、mapping 版本和 normalization 版本确定。
质量规则变化不应制造新的 CleanBatch，同一 CleanBatch 应允许产生多个 QualityRun。

0.8.1 中虽然 CLEAN 任务幂等键包含 `quality-v3`，但服务器已经执行过该 CLEAN 请求并完成；之后再次调用 `enqueue-clean-latest` 会直接复用已完成 CLEAN 任务，无法重新进入 CleanExecutor，因此不会补建新的 QUALITY 任务。

## 3. 修复

当 `enqueue-clean-latest` 发现：

```text
CLEAN任务已完成
+
对应CleanBatch仍处于CANDIDATE/VALIDATING/BLOCKED
+
CleanBatch记录的质量规则版本不是当前版本
```

则直接为原 CleanBatch 创建当前版本的 QUALITY 任务。

QualityRun 完成时同步更新：

```text
CleanBatch.quality_rule_version = 当前质量规则版本
```

## 4. 治理结果

修复后链路为：

```text
同一RAW
→ 同一CleanBatch
→ QualityRun(v2) BLOCKED
→ 质量规则升级
→ QualityRun(v3)
→ PASS/WARN/BLOCK
```

不重复清洗，不制造新的 CleanBatch，不破坏任务幂等。

## 5. 验证

新增回归测试覆盖：

1. 旧 BLOCKED CleanBatch 遇到新质量规则必须补建 QUALITY 任务；
2. 同一质量规则版本不得重复创建 QUALITY 任务。

结果：

```text
71项测试通过（排除仓库既有历史Alembic revision名称长度检查）
Python编译检查通过
```
