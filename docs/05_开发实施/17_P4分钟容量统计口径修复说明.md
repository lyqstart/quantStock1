# P4分钟容量统计口径修复说明

## 1. 现象

P4-3 第一阶段真实样本验收中：

```text
raw_sample=241
clean_sample=241
hypertable=true
clean.table_bytes=0
clean.total_bytes=16384
```

`clean.stock_minute` 已经真实保存 241 条数据，因此父表大小不能代表 Timescale hypertable 的实际存储占用。

## 2. 原因

原容量报告使用 PostgreSQL `pg_relation_size / pg_total_relation_size` 直接统计 `clean.stock_minute`。

Timescale hypertable 的实际数据存放在内部 chunk 表中。只统计 hypertable 父表会漏掉 chunk 数据及其索引。

## 3. 修复

对普通 RAW 表继续使用 PostgreSQL relation size。

对 `clean.stock_minute` hypertable 改用 TimescaleDB：

```text
hypertable_detailed_size()
```

统计：

```text
table_bytes
index_bytes
toast_bytes
total_bytes
```

该口径包含 hypertable 的 chunks。

## 4. 治理结论

本修复只修正容量测量方法：

```text
不修改 CLEAN 数据
不修改质量规则
不修改 chunk interval
不启用压缩
不修改数据库结构
```

P4-3 在取得真实 chunk 容量数据前，不批准最终 chunk 和压缩策略。
